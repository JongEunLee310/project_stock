## Review Summary

시그널 페이지가 종목당 카드 하나(디자인 기준)로 표시되도록 `GET /signals`에 `view=current`
모드를 추가한 계약 확장입니다. 자산당 활성 시그널 중 dominant 1건만 반환하며, dominant 선정은
watchlist의 `WATCHLIST_STATUS_PRIORITY`를 재사용합니다. 기본값 `view=all`은 기존 동작을 그대로
유지해 하위호환을 보장합니다.

핵심 구현은 `repository.list_current_by_asset`입니다. `WATCHLIST_STATUS_PRIORITY`를 순회해
`{signal_type: rank}` dict를 만들고 SQLAlchemy `case(..., value=Signal.signal_type)`로 우선순위
rank를 산출합니다. `ROW_NUMBER() OVER (PARTITION BY asset_id ORDER BY rank asc, score desc,
created_at desc, id desc)` 윈도우로 자산별 1위를 표시하고 rank=1 행만 선택한 뒤, 바깥에서
`score desc, created_at desc, asset_id asc`로 정렬해 offset/limit을 적용합니다. 우선순위 정의가
`types.py` 한 곳에만 존재하도록 유지해 매핑 복제가 없습니다. `count_current`는 활성 시그널을 가진
distinct asset 수를 반환합니다.

service는 `view=current`일 때 current 경로로 분기하고 `include_expired`를 무시하며, expanded의
quote 조합 로직을 재사용합니다. router는 `view: str = Query(default="all")`를 추가했습니다. 미지의
`view` 값과 `all`·미지정은 모두 기존 all 경로로 흘러 안전합니다.

## Suggestions

**S1. `view` 파라미터가 문자열 자유값입니다**

`view: str = Query(default="all")`는 `current` 외 임의 문자열을 받아 조용히 all로 처리합니다.
현재 분기는 안전하지만, 오타(`curent` 등)가 400 대신 전체 목록을 반환해 호출자가 알아채기
어렵습니다. 후속에서 `Literal["all", "current"]` 또는 Enum으로 좁히면 계약이 명확해집니다.
심각도: 비차단·후속 검토.

**S2. current 정렬이 우선순위가 아닌 score 기준입니다**

collapse 후 목록 정렬은 설계대로 `score desc → created_at desc → asset_id asc`입니다. dominant
"선정"은 우선순위(RISK_ALERT 등) 기준이지만 "목록 순서"는 score 기준이라, 리스크 증가(우선순위
최상위)라도 score가 낮으면 목록 하단에 올 수 있습니다. FE가 카테고리/신뢰도로 재정렬해 소비하므로
현재는 문제없으나, 로드맵 2단계(우선순위 레일)에서 정렬 기준을 재확인하면 좋겠습니다.
심각도: 비차단·정보성.
