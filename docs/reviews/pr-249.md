# PR #249 로컬 리뷰 — fix: 분석 파이프라인 뉴스 수집을 쿼리 기반으로 정렬

리뷰어: Claude Code (Sonnet — 교차 모델 독립 리뷰. 구현에 관여하지 않음)

Cross-model 리뷰: 구현자는 Codex(gpt-5.5, effort medium), 핸드오프·설계 작성자는 VFF(Sonnet)입니다.
이 리뷰는 구현에 관여하지 않은 Sonnet이 독립 시점에서 수행했습니다.

## Review Summary

`NEWS_PROVIDER=rss` 환경에서 분석 파이프라인의 뉴스 수집이 구조적으로 0건이 되던 결함을
해소하는 PR입니다. 결함의 원인은 `app/adapters/factory.py:75`에서 RSS 어댑터가 빈 피드 목록으로
생성되는데, 기존 분석 파이프라인이 피드 목록 순회 경로(`adapter.fetch(symbols)`)로 수집했기
때문입니다. 이 경로에서는 피드가 없으면 결과도 없습니다.

수정 방향은 분석 파이프라인의 수집 경로를 매시 수집 잡(`collect_news_job`)과 동일한 쿼리 기반
경로(`adapter.fetch_query(asset.name, asset.market.upper())`)로 정렬하는 것입니다. 수집 잡
`app/domains/raw_news/ingestion_service.py:51`이 `adapter.fetch_query(name, normalized_market)`을
사용하는 것과 완전히 동일한 인수 형식이며, 여기서 `normalized_market`은 `market.upper()`입니다.

기존 `_RecordingNewsAdapter` 래퍼와 `RawNewsService.collect_and_save` 호출을 제거하고, 대신
`RawNewsService.save_with_symbol`을 각 결과에 대해 직접 호출해 반환값이 `None`이 아닌 결과(신규
저장분)만 모아 `_create_new_items`에 전달하는 구조로 교체했습니다. `save_with_symbol`의 내부
`create_or_skip`이 URL 기반 중복 제거를 수행하므로, 기존 증분 동작이 그대로 유지됩니다.
`_create_new_items`는 이미 저장된 `RawNewsEvent`를 `get_by_url`로 조회해 `raw_news_event_id`를
채우는 구조인데, 호출 시점에 `new_results`가 방금 저장된 이벤트만 담고 있으므로 이 조회도
정합하게 동작합니다.

테스트 파일(`tests/test_analysis_flow.py`)의 픽스처 어댑터 두 개(`StaticNewsAdapter`,
`FailingNewsAdapter`)가 `fetch_query` 경로로 전환되었으며, `fetch()`를 호출하면
`AssertionError`를 던지는 가드가 추가되어 분석 파이프라인이 피드 경로를 사용하지 않음을
테스트 자체가 강제합니다. 신규 테스트 `test_watchlist_analysis_flow_uses_mock_query_results`는
`MockNewsAdapter`를 실제로 관통해 URL 리터럴을 포함한 구체적인 계약 값을 검증하며, 픽스처
URL 패턴은 `app/adapters/news/mock.py:23–43`의 실제 구현에서 도출한 것입니다.

변경 파일은 `app/domains/analysis/service.py`, `tests/test_analysis_flow.py`,
`docs/knowledge/product-workflow.md`, `docs/designs/248-analysis-query-news.md`,
`.codex/tasks/task-164-analysis-query-news.md` 다섯 개이며, 핸드오프 스코프 두 파일에 설계·핸드오프
문서 신규 추가가 더해진 구성입니다. 보호 파일 접촉 없음, 스코프 이탈 없음을 확인했습니다.

## Suggestions

**S1. 리스트 컴프리헨션 내 부수 효과 — 가독성 개선 권장**

`service.py:98–107`의 `new_results` 생성 코드는 `if` 절에서 `raw_news_service.save_with_symbol`을
호출해 DB 쓰기를 수행합니다. Python 리스트 컴프리헨션에서 `if` 절의 부수 효과는 문법적으로
유효하고 동작도 정확하지만, `if` 절이 필터 역할과 저장 역할을 동시에 수행한다는 사실을 한눈에
파악하기 어렵습니다. 예를 들어 `save_with_symbol` 반환값이 없다고 착각하거나, 루프 안에서
저장이 일어난다는 사실을 놓치기 쉽습니다. 명시적 루프와 `append`로 저장 호출과 필터를 분리하면
의도가 더 명확해집니다. 머지 차단 수준은 아니며, 이번 PR 내 수정이나 후속 정리 어느 쪽이든
무방합니다. 심각도: 비차단·권장.

**S2. `docs/designs/069-news-normalizer.md` 구버전 아키텍처 참조 잔존**

기존 설계 문서 `docs/designs/069-news-normalizer.md:14`에서 `_RecordingNewsAdapter`를 현재
아키텍처의 일부인 것처럼 서술합니다. 이번 PR로 해당 클래스가 제거되었으므로 이 서술은
구버전 아키텍처에 대한 역사적 기술이 됩니다. `docs/designs/` 내 역사적 문서이므로 오동작
위험은 없지만, 이후 문서를 참조하는 개발자가 혼선을 겪을 수 있습니다. 후속 PR에서 과거
시제로 수정하거나 "이 클래스는 PR #249에서 제거됨" 주석을 추가하면 충분합니다. 심각도:
비차단·후속 정리 권장.

## Questions

**Q1. `NEWS_PROVIDER=rss` 로컬 테스트 격리 공백 — 후속 이슈 필요 여부 확인**

PR 설명에서 로컬 `.env`가 `NEWS_PROVIDER=rss`인 상태로 pytest를 실행하면 기존 worker 테스트
1건이 실제 Google RSS를 호출해 실패한다고 명시하고, 이것이 본 PR과 무관한 기존 격리 공백이라는
판단을 밝히고 있습니다. 이 판단은 타당합니다. `patch_worker_session` 픽스처가 `autouse=True`로
`get_news_adapter`를 `MockNewsAdapter`로 패치하므로 CI 환경(.env 없음)에는 영향이 없으며,
CI가 완전히 통과하는 것으로 확인됩니다. 다만 로컬 개발 환경에서 `NEWS_PROVIDER=rss` 설정 시
반복적으로 테스트가 실패할 수 있으므로, 해당 격리 공백을 별도 이슈로 등록해 후속 트랙으로
관리하는 것이 적절한지 확인을 요청드립니다.
