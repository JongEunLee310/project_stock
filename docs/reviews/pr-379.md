# PR #379 로컬 리뷰 — 뉴스 인텔리전스 이벤트 상세 계약 (#306)

## Review Summary

뉴스·공시 인텔리전스(에픽 #307) 2차의 첫 단위로, `GET /api/v1/news-insights/events/{event_id}`를 추가합니다. base=dev 단일 PR이며 커밋은 1건입니다. 2차 설계문서(`docs/designs/307-news-intelligence-phase2.md`)도 이 PR에서 처음 추가됩니다. 단일 관심사(이벤트 상세)이므로 Part 분할 없이 이어서 설명합니다.

신규 테이블 없이 1차 모델(`ExtractedEvent`·`EventEvidence`·`SourceDocument`·`TopicInsight`)을 재사용합니다. `service.get_event_detail`이 이벤트를 조회하고, `event_evidence`→`source_documents`로 근거 문서를, `TopicInsight.key_evidence`의 event_id 참조로 관련 토픽을 연결합니다. `schema.py`에 `EventDetailResponse`(importance{score·level·explanation}·sentiment{direction·score}·affected_symbols·evidence·related_topics)를 추가했고, 미존재 이벤트는 `app/core/error_codes.py`에 추가한 `NEWS_INSIGHT_EVENT_NOT_FOUND`로 404 처리합니다. 라우트는 기존 `get_current_user`·`success` 엔벨로프를 재사용합니다.

이번 리뷰는 설계 §3.1 계약 일치, 1차 모델 재사용의 정확성, 범위 이탈 여부를 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. `affected_symbols`가 이벤트당 최대 1개 — 모델 제약, 이번 범위에서 허용.** `ExtractedEvent`에는 `primary_symbol` 단일 필드만 있어 이벤트당 영향 종목이 0~1개로 투영됩니다. 설계 §3.1은 `affected_symbols`를 리스트로 두므로 계약 자체는 지켜지며, 다종목 영향은 신규 테이블(event-symbol 매핑)이 필요해 이번 범위 밖입니다. 실추출 파이프라인 도입 시 확장 지점으로 남깁니다.

**S2. `app/core/error_codes.py` 도메인 에러 코드 1건 추가 — 기존 패턴 준수 additive.** `NEWS_INSIGHT_EVENT_NOT_FOUND`를 추가했습니다. #304의 `NEWS_INSIGHT_TOPIC_NOT_FOUND`와 동일 패턴이며 기존 코드에 영향이 없습니다.

## Questions

**Q1. 라우트 등록 순서 — `/events`와 `/events/{event_id}` 충돌 없음(확인 완료).** 리스트 `/events`와 상세 `/events/{event_id}`는 경로 깊이가 달라 FastAPI 매칭이 충돌하지 않습니다. 리뷰 중 확인해 해소했습니다.

## Final Recommendation

머지 가능합니다. 설계 §3.1의 응답 구조(importance explanation·affected_symbols·evidence·related_topics)와 404 처리가 구현과 일치함을 확인했습니다. 범위는 이벤트 상세 하나로 지켜졌고 #368·#369·#370과 신규 테이블은 후속으로 남겼습니다. Protected Files 변경은 없으며 core 변경은 error 코드 1건뿐입니다. 신규 테이블·마이그레이션이 없어 회귀 위험이 낮습니다. 추가된 테스트는 상세 응답·404를 덮습니다. Blocking은 없고, Suggestions(S1·S2)는 각각 모델 제약과 기존 패턴 준수 additive이며, Questions(Q1)는 리뷰 중 확인으로 해소됐습니다.
