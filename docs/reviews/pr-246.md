# PR #246 로컬 리뷰 — feat: compose에 RQ worker·scheduler 서비스 추가

리뷰어: Claude Code (Sonnet — 교차 모델 독립 리뷰. 구현에 관여하지 않음)

Cross-model 리뷰: 구현자는 Codex(gpt-5.5, effort medium), 핸드오프 작성자는 VFF(Sonnet)입니다.
이 리뷰는 구현에 관여하지 않은 Sonnet이 독립 시점에서 수행했습니다.

## Review Summary

`docker-compose.yml`에 `worker`·`scheduler` 서비스를 추가해, 선행 PR #244(분석 트리거 연결)로
큐잉된 잡이 로컬 스택에서 실제로 소비되는 공백을 해소하는 PR입니다. Python 코드 변경은 전혀 없으며,
변경 범위는 `docker-compose.yml` 서비스 정의 2개 추가, `README.md` 실행 안내 갱신,
`docs/knowledge/product-workflow.md` 스케줄러 섹션 보완으로 한정됩니다.

두 신규 서비스는 기존 `backend` 서비스와 동일한 빌드 컨텍스트(`build: .`)·`environment`
(DATABASE_URL·REDIS_URL)·`env_file`(.env, required: false)·`volumes`(`.:/app`, `/app/.venv` 익명
볼륨)·`depends_on`(postgres·redis healthcheck 의존) 구성을 그대로 따릅니다. 기존 `backend`·
`postgres`·`redis` 서비스 정의는 변경이 없습니다.

`command` 전략에 주목할 점이 하나 있습니다. 핸드오프 Background는 "backend 이미지의 실행 관례는
uv 기반이므로 `uv run rq worker ...` 형태를 따른다"고 서술했으나, 실제 Dockerfile을 확인하면 런타임
이미지(`FROM python:3.12-slim`)에는 `uv` 바이너리가 포함되지 않습니다(빌더 스테이지에서만 `pip install
uv`를 실행하고, 런타임 스테이지에는 `.venv`만 복사합니다). `backend` 서비스도 `uvicorn ...`을
`uv run` 없이 직접 호출하며, 이는 Dockerfile의 `ENV PATH="/app/.venv/bin:$PATH"` 설정 덕분에
`.venv/bin/uvicorn`이 바로 접근되기 때문입니다. 구현은 이 실제 구조를 반영해 `rq worker`와
`rq cron`을 `uv run` 없이 직접 호출했으며, PR 설명에도 그 이유가 명시되어 있습니다. 핸드오프
Background의 "uv 기반" 서술은 런타임 이미지의 실제 PATH 구성을 반영하지 못한 미흡한 기술이었고,
구현 단계에서 올바르게 교정되었습니다.

`command`의 `$$REDIS_URL` 이스케이프도 정상입니다. Compose YAML에서 `$$`는 리터럴 `$`로 치환되어,
컨테이너 셸에 전달될 때 `$REDIS_URL`이 컨테이너 환경변수로 올바르게 확장됩니다.

설계 문서 생략의 타당성을 함께 확인했습니다. 이 PR은 신규 도메인·신규 외부 의존성·아키텍처 결정이
없고, compose 실행 형상을 기존 ADR-003 결정(RQ cron 기반 스케줄러)에 맞춰 반영한 구성 변경입니다.
`design-record-policy.md`가 규정하는 설계 문서 작성 조건에 해당하지 않으므로, 설계 문서 생략 판단은
타당합니다.

## Suggestions

**S1. `restart` 정책 미설정 — worker 크래시 시 자동 복구 없음**

`worker`·`scheduler` 서비스에 `restart` 정책이 지정되어 있지 않습니다. `backend`도 동일하게
정책이 없어 일관성은 있지만, worker는 잡 처리 중 처리되지 않은 예외가 프로세스를 종료시키면
Redis 큐에 잡이 남은 채 소비가 멈추는 상황이 발생할 수 있습니다. `restart: unless-stopped`를
추가하면 재기동이 자동화되어 운영 편의성이 높아집니다. 현 단계에서 로컬 개발 환경 용도라면
허용 가능한 상태이지만, 후속 과제로 검토할 것을 권장합니다. 심각도: 비차단·권장.

**S2. `product-workflow.md` 추가 문장과 앞뒤 단락 사이에 빈 줄 없음**

`docs/knowledge/product-workflow.md` 스케줄러 섹션의 diff를 보면, 새로 추가된 세 줄(로컬 compose
경로 안내)이 앞 문장("…실행한다.")과 뒤 문장("수동 실행 경로…") 사이에 단락 구분 없이 이어집니다.
내용의 정확성에는 영향이 없으나 가독성이 떨어집니다. 앞뒤로 빈 줄을 추가하거나 별도 단락으로
분리하면 읽기가 편해집니다. 심각도: 비차단·편집 권장.

## Questions

**Q1. `sh -c 'exec rq ...'` 패턴 — 의도 확인 요청**

두 서비스의 `command`가 모두 `sh -c 'exec rq ...'` 형태를 사용합니다. `exec`가 `sh`를 `rq`
프로세스로 대체하기 때문에, `rq`가 컨테이너 PID 1이 되어 Docker의 SIGTERM을 직접 수신합니다.
RQ worker는 SIGTERM을 받으면 현재 잡을 완료한 뒤 종료하는 graceful shutdown을 지원하므로
신호 처리 측면에서 올바른 패턴입니다. 그러나 핸드오프에는 `exec` 사용에 대한 명시적 언급이
없습니다. 의도적으로 선택한 패턴인지 확인 요청드립니다 — 의도된 것이라면 현 상태를 유지하면
됩니다.

## Documentation Impact

`README.md`와 `docs/knowledge/product-workflow.md` 두 문서가 모두 갱신되었으며, 실제 compose
구성과 내용이 일치합니다.

README는 Docker Compose 섹션 도입부에 worker·scheduler가 함께 기동됨을 추가하고,
"worker에는 코드 자동 재시작이 없어 코드 변경 시 컨테이너 재시작 필요" 사항을 명시했습니다.
"스케줄러는 아직 스켈레톤"이라는 낡은 서술도 현행화되었습니다.

`product-workflow.md` 스케줄러 섹션에는 Docker Compose로 기동하면 worker·scheduler가 함께 뜬다는
내용이 추가되었습니다. 기존 `uv run rq cron ...` 실행 경로(비 Docker 직접 실행 경로)는 변경되지
않아, 두 실행 맥락이 공존하는 구조로 일관됩니다.

ADR은 기존 ADR-003의 실행 형상 반영이므로 신규 작성이 불필요합니다. Failure Record도 불필요합니다.

## Final Recommendation

Blocking 소견이 없습니다. 핸드오프 Requirements 4개 항목을 모두 충족합니다. Dockerfile 상의
런타임 PATH 구조를 실제로 확인해 `uv` 부재를 검증했고, `rq` 직접 호출 방식이 올바른 구현임을
확인했습니다. `$$REDIS_URL` 이스케이프, `ANALYSIS_SCHEDULE_ENABLED` env 전달 경로, 기존 서비스
무변경, 보호 파일 미접촉, 스코프 이탈 없음을 모두 확인했습니다. CI가 652개 테스트로 완전히 통과했습니다.

S1(restart 정책)·S2(단락 구분)는 후속 개선 권장 사항이며 머지 차단 요건이 아닙니다.
Q1은 `exec` 패턴 의도 확인을 위한 질문으로, 의도된 선택이라면 현 코드를 그대로 유지하면 됩니다.

이 리뷰는 Sonnet(구현 비관여)이 독립 교차 모델 시점으로 수행했습니다.
