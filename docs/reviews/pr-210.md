# PR #210 로컬 리뷰 — feat: 스케줄러 실 주기 연결·cloud LLM 일일 호출 상한 가드 (#208·#209)

## Review Summary

스케줄러 스켈레톤을 실 주기 실행으로 완성하고 LLM cloud 경로에 일일 호출 상한 가드를 추가하는
PR입니다. 커밋 3건으로 구성됩니다. 첫째(설계 079·핸드오프 문서), 둘째(BE #208 스케줄러
cron), 셋째(BE #209 호출 상한 가드)이며 같은 브랜치에서 순차 구현됐습니다.

**Part A — 스케줄러 cron 연결(BE #208, Decision EEE·FFF·GGG).** `app/scheduler/cron_config.py`가
신설되어 모듈 임포트 시점에 `default_scheduler_registry`를 순회하며 `enabled=True`인 항목에
`rq.cron.register(func, "default", cron=...)`를 호출합니다. 스케줄러 프로세스는
`uv run rq cron app/scheduler/cron_config.py -u $REDIS_URL`로 독립 기동합니다.
`ManualSchedulerRunner`는 enqueue 전담으로 재작성되었고, 자체 `JobRun` 기록이 제거되었습니다.
수집 잡이 `start→succeed/fail`을 스스로 기록하므로 이중 기록을 방지하는 것이 목적입니다.
레지스트리는 `mock_collection`(cron `*/15 * * * *`)을 삭제하고 `price_collection`
(`collect_prices_job`, `10 22 * * 1-5`)·`news_collection`(`collect_news_job`, `0 * * * *`)
두 잡으로 교체됐습니다. 수동 실행 endpoint의 응답 계약이 `job_run_id: int / status="success"`에서
`job_id: str / status="queued"`로 변경됩니다.

**Part B — cloud LLM 일일 호출 상한 가드(BE #209, Decision HHH).** `app/adapters/llm/budget.py`에
`DailyCallBudget`이 신설됩니다. Redis 키 `llm:cloud_calls:{YYYYMMDD}`(UTC)를 INCR하고
`LLM_DAILY_CALL_LIMIT`을 초과하면 `LLMBudgetExceededError`(`LLMCallError` 하위)를
raise합니다. 첫 INCR 시 TTL을 2일로 설정합니다. `LLMGateway`는 CLOUD 라우팅 시에만
`call_budget.consume()`을 호출하며, 팩토리는 `LLM_PROVIDER=cloud`이고 `LLM_DAILY_CALL_LIMIT`이
설정된 경우에만 budget을 부착합니다. 빈 문자열(`""`)을 `None`으로 파싱하는
`field_validator`가 `config.py`에 추가되어 `.env` 파일에서 비워두면 무제한으로 동작합니다.

설계 Decision EEE–HHH와 구현의 일치 여부를 축으로 리뷰했습니다.

## Blocking

## Suggestions

**S1. `DailyCallBudget.consume()`의 INCR→EXPIRE 비원자성 — 낮은 위험, 후속 판단 사항.**
`budget.py`의 `consume()` 구현에서 `redis.incr(key)` 후 `count == 1`일 때만
`redis.expire(key, ...)` 를 호출합니다. 이 두 호출 사이에 프로세스가 크래시되면 해당 날짜의
키가 TTL 없이 Redis에 잔존할 수 있습니다. 다음 날에는 날짜가 바뀐 새 키를 사용하므로
카운터가 누적되지는 않지만, 해당 날짜 키는 Redis에 영구 잔류할 수 있습니다. Redis Lua
스크립트(INCR + EXPIRE를 단일 원자 트랜잭션으로)로 해결할 수 있으나, 초기 budget 구현
단계에서 해당 크래시 시나리오의 발생 확률과 영향이 모두 낮으므로 현재 범위에서 허용
가능하다고 판단합니다. 운영 관찰 이후 Redis 인프라 성숙 시점에 원자화를 검토하는 것을
권고합니다.

**S2. `call_budget.consume()`이 `client.complete_json()` 호출 전에 위치하여 클라이언트
실패 시에도 카운트가 소비됨 — 설계상 허용된 보수적 카운팅, 운영 시 인지 필요.**
`gateway.py`에서 `call_budget.consume()`은 `privacy_gate.guard()` 통과 후, 실제
`client.complete_json()` 호출 전에 위치합니다. 따라서 LLM API 네트워크 오류·타임아웃 등
클라이언트 측 실패 시에도 카운터가 증가합니다. 이는 의도적인 보수적 카운팅으로
해석할 수 있습니다(PrivacyGate 실패는 카운트하지 않는 것은 올바릅니다). 다만 LLM API
장애 기간에 예산이 성공 완료 없이 소진될 수 있으므로, 운영자가 이 동작을 인지하고 있어야
합니다. `LLM_DAILY_CALL_LIMIT` 설정 시 이 특성을 `docs/backend-v0.2.md` 또는 `.env.example`
주석에 한 줄 덧붙이면 운영 참고 정보가 됩니다.

## Questions

**Q1. `/api/v1/worker/scheduler/jobs/{job_name}/run` 응답 계약 변경에 대한 FE 저장소 영향
확인 여부.**
`docs/api/frontend-api-spec.md`는 이번 PR에서 갱신됐습니다(`job_run_id → job_id`,
`status: success → queued`). 설계 079 §3.5와 PR 설명에서 "내부 ops endpoint라 하위
호환 부담이 없다"고 명시하고 있으나, FE 저장소의 admin 화면이나 내부 도구에서 이
endpoint를 호출한다면 계약 변경의 영향을 받습니다. orchestrator가 리뷰 시점에 FE 저장소
(`project_stock_FE/src`)를 검색해 `scheduler`·`job_run_id`·worker endpoint 호출이 없음을
확인했으므로 Q1은 해소됐습니다.

## Final Recommendation

머지해도 좋다고 판단합니다. 설계 Decision EEE–HHH와 구현의 일치를 항목별로 확인했습니다.
`cron_config.py` 임포트 시 `rq.cron.register`가 두 잡의 올바른 cron 표현식과 함께 호출됨을
테스트로 검증했습니다. `ManualSchedulerRunner`는 enqueue만 수행하고 자체 `JobRun` 기록이
없음을 `FakeQueue` 스텁으로 단언했습니다. `default_scheduler_registry` 등록 함수 집합이
정확히 `{collect_prices_job, collect_news_job}`임을 화이트리스트 회귀 테스트로 확인했고,
§15의 주기 잡 LLM 혼입 차단이 단언 수준에서 보장됩니다. `DailyCallBudget`의 상한 이하·초과
케이스, 게이트웨이 CLOUD 시 consume 호출·LOCAL 시 미호출, 빈 문자열 → `None` 파싱이 모두
테스트로 덮여 있습니다. Protected Files(수집 잡 본체·`router.py`·`privacy.py`·`prompts/`·
`domains/`·`alembic/versions/`)가 변경되지 않음을 diff에서 확인했습니다. Blocking 없음,
S1·S2는 후속 관찰 사항, Q1은 FE 저장소 검색으로 해소됐습니다. 최종 머지 권한은
개발자에게 있습니다.
