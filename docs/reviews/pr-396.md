# PR #396 로컬 리뷰 — 에이전트 파이프라인 집계 지표 확장 (#394)

## Review Summary

개요 화면의 에이전트 파이프라인 패널에서 `—`로 비어 있던 집계 세 칸 중 두 개를 채우는 PR입니다.
커밋 두 건으로 구성되며, 두 번째는 로컬 리뷰가 잡은 산출 정의 오류를 고칩니다. 모델·마이그
레이션 변경은 없고 기존 컬럼에서 파생합니다.

**Part A — 두 필드 추가(#394, `docs/designs/394-agent-pipeline-metrics.md`).** `AgentRunsResponse`에
`collected_sources`(int)와 `average_run_duration_seconds`(int | None)를 더했습니다. 전자는
`source_documents`의 고유 `source_name` 개수, 후자는 완료된 run 최근 20건의
`finished_at - started_at` 평균(초)입니다. 두 집계 모두 `NewsInsightsRepository`에서 DB 측으로
수행하고 `AgentRunRecords`에 실어 서비스로 넘깁니다. 평균 산출은 SQLite(`julianday`)와
PostgreSQL(`extract(epoch)`)의 시간 차 연산이 달라 dialect로 분기합니다.

**Part B — `collected_sources` 산출 정의 정정(리뷰 지적).** 초안은 최근 run의
`started_at` ~ `finished_at` 구간에 `collected_at`이 들어오는 문서로 한정했습니다. 이 정의가
틀렸습니다. run은 자기가 도는 동안 들어온 문서가 아니라 **그 전에 쌓인 문서를 처리**하므로, run
구간으로 자르면 처리 대상과 무관한 집합을 세게 됩니다. 시간 조건을 제거하고 회귀 테스트를
더했습니다.

이번 리뷰는 산출 정의가 실제 데이터에서 성립하는지, 만들지 않기로 한 지표를 정말 만들지
않았는지, dialect 분기의 위험, 계약 하위호환을 축으로 봤습니다.

## Blocking

None. (초안의 정의 오류는 리뷰 중 지적해 Part B에서 해소했습니다. 아래 Q1 참조.)

## Suggestions

**S1. dialect 분기의 PostgreSQL 경로가 테스트에서 한 번도 실행되지 않는다 — 실제 위험, 다만 이
PR에서 늘어난 위험은 아님.** 테스트는 SQLite로 돌고 운영은 PostgreSQL이므로, `extract(epoch)`
경로는 배포 전까지 검증되지 않습니다. 표본이 20건으로 묶여 있어 **행을 가져와 파이썬에서
평균을 내면 분기 자체가 사라집니다.** 20건은 전량 적재라 부를 규모가 아닙니다. 핸드오프에서
제가 "집계는 DB 측에서 수행한다"고 적은 것이 이 분기를 부른 원인이므로, 지시가 과했습니다.
지금 값을 다시 계산해 바꿀 만큼 급하지는 않으나, 이 파일을 다시 열 때 단순화할 후보로 둡니다.

**S2. `active_topics`가 응답에 남지만 화면에서는 쓰이지 않는다 — 의도된 유지.** 재구성된 개요
화면의 지표 스트립은 `수집 소스·처리 건수·이벤트 추출·평균 처리 지연·정확도` 5종이라
`active_topics`가 빠졌습니다. 계약에서 제거하지 않은 것은 의도이며 설계 문서 §5에 근거가
있습니다. 제거는 되돌리기 어렵고 다른 소비자가 생길 수 있습니다.

**S3. 시드 기준 `collected_sources`가 `2`다 — 값이 아니라 데이터 부족의 문제.** 설계 이미지의
`1,248`과 자릿수가 다릅니다. 시드에 문서가 두 건뿐이기 때문이고 산출식의 문제가 아닙니다.
실제 수집 경로가 생기기 전까지(#391) 이 지표는 시드 규모를 그대로 반영합니다.

## Questions

**Q1. 산출 정의가 실제 데이터에서 성립하는가.** 확인했고 성립하지 않아 정정했습니다. 초안 정의로
구현한 뒤 시드로 조회하니 `collected_sources`가 `0`이었습니다. 시드의 문서는 기준 시각 1시간
55분·1시간 25분 전에 수집되고 run은 15분 전에 시작해 2분 전에 끝나 겹치는 구간이 없습니다.
화면에는 `수집 소스 0`이 뜨는데 이는 출처가 없다는 **거짓 진술**이며, 값을 모른다는 `—`보다
나쁩니다. 첫 구현이 이 상태를 `test_agent_runs_returns_seeded_metrics_and_zero_sources_without_documents`
라는 이름으로 단언까지 하고 있었습니다 — 시드에는 문서가 있으므로 이름도 사실과 달랐습니다.
설계 문서 §2를 고치고 재작업했으며, 지금은 run 구간 밖에서 수집된 문서도 세어지는지 확인하는
회귀 테스트(`test_agent_runs_counts_sources_collected_outside_latest_run`)가 있습니다.

**Q2. 만들지 않기로 한 지표를 정말 만들지 않았는가.** 확인해 해소했습니다. `정확도`에 해당하는
필드가 스키마·응답 어디에도 없습니다. 화면은 계속 `—`로 둡니다. 정의가 없는 상태에서 숫자를
만들면 근거 없는 신뢰를 화면에 새기게 되므로, 비워 두는 편이 맞습니다.

**Q3. 계약이 하위호환인가.** 확인해 해소했습니다. 기존 일곱 필드의 이름·타입·의미가 그대로이고
두 필드가 추가만 됐습니다. 기존 `agent-runs` 테스트의 단언이 그대로 통과합니다.

**Q4. `average_run_duration_seconds`가 `null`과 `0`을 구분하는가.** 확인해 해소했습니다. 완료된
run이 하나도 없을 때만 `null`이고 0으로 대체하지 않습니다. 전용 테스트가 있습니다.

**Q5. 화면 라벨과 계약 이름의 차이를 어떻게 할 것인가.** 해소하지 못했습니다. 화면은
`평균 처리 지연`이라 적고 계약은 처리 **소요 시간**을 줍니다. 목표 처리 시간이 정의된 적이
없어 지연이라 부를 근거가 없으므로 계약 이름을 실측값에 맞췄습니다. 라벨 정정은 프론트엔드
표현 변경이라 이번 범위 밖이고, 지금은 프론트엔드 디자인이 동결 상태입니다. 어느 쪽을 언제
맞출지는 개발자 판단이 필요합니다.

## Documentation Impact

이번 PR에서 갱신된 문서는 두 건입니다.

- `docs/designs/394-agent-pipeline-metrics.md`(신규) — 산출 정의 정본. §2에 run 구간으로 자르지
  않는 이유를, §4에 `정확도`를 만들지 않는 이유를 담았습니다.
- `docs/designs/307-news-intelligence-phase2.md` §3.6 — 응답 필드 목록에 두 필드를 더하고 산출
  정의는 위 문서를 참조하게 했습니다.

ADR은 불요합니다. 기존 테이블에서 파생하는 응답 필드 추가이고 와이어 컨벤션도 그대로입니다.
다만 `정확도`를 정의 없이 만들지 않는다는 판단은 새 결정이 아니라 ADR-009(사실·추론 분리)의
연장이므로 별도 ADR을 세우지 않았습니다.

Failure Record는 불요합니다. Q1의 정의 오류는 같은 라운드 안에서 리뷰가 잡아 고쳤고, 실패한
접근을 대체한 것이 아니라 초안을 수정한 것입니다. 다만 **설계 단계에서 시드 데이터로 값을
한 번 계산해 봤다면 핸드오프 전에 걸렸을 오류**라는 점은 기록해 둘 값이 있습니다. 산출 정의를
쓸 때 실제 데이터로 결과를 확인하는 습관을 품질 프로세스 정책에 반영할지는 별도 판단
사안입니다.

## Final Recommendation

머지 가능합니다. 핸드오프의 요구를 항목별로 확인했습니다. 두 필드가 실제 계산값으로 나오고
상수가 아니며, 모델·마이그레이션 변경이 없고, `active_topics`를 포함한 기존 필드가 모두
보존됐습니다.

범위는 지켜졌습니다. `정확도` 관련 필드를 만들지 않았고, 시드 데이터 값을 고치지 않았으며,
다른 엔드포인트·도메인은 건드리지 않았습니다. Protected Files는 없습니다.

테스트는 완료 run 없음(`null`), 문서 없음(`0`), 중복 출처를 1로 세는 경우, 표본 20건 상한,
그리고 **run 구간 밖에서 수집된 문서도 세어지는 경우**를 덮습니다. 마지막 하나가 Part B가 고친
결함의 회귀 방지 자리입니다. 필드 존재만 확인하는 단언은 없고 모두 값을 검사합니다.

Blocking은 없습니다. S1은 이 PR이 늘린 위험이 아니며 다음에 이 파일을 열 때의 단순화 후보이고,
S2·S3은 의도된 유지와 데이터 규모의 문제입니다. Q1은 리뷰 중 지적해 재작업으로 해소했고,
Q2·Q3·Q4는 확인해 해소했으며, **Q5는 화면 라벨과 계약 이름을 언제 맞출지에 대한 개발자 판단이
필요한 항목**입니다.

최종 머지 권한은 개발자에게 있습니다.
