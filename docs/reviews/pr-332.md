## Review Summary

ADR-013 / `docs/designs/alert-rule-event-unified.md`가 위임한 알림 통합 모델의 첫 단계(B1)로,
`AlertRule`·`AlertEvent`·`AlertDelivery`·`NotificationChannel` 4개 모델과 enum, 중앙 등록
(`app/db/models.py`), Alembic 마이그레이션 1건, 단위 테스트를 추가합니다. 서비스·라우터·엔진은
범위 밖으로 정확히 제외했고, 기존 `alerts`·`alert_candidates`·`watchlists` 모델은 손대지
않았습니다.

모델 필드·타입·제약은 설계 §1 표와 일치합니다. int PK + `ForeignKey`, `DateTime(timezone=True)`
+ `server_default=func.now()` 등 기존 도메인 관례를 따르고, `AlertRule`은 `TimestampMixin`을,
`AlertEvent`는 `triggered_at`/`read_at`을 직접 두어 설계대로 created/updated 없이 발생·읽음
시각만 갖습니다. enum 10종은 설계 §2와 값까지 일치합니다(`AlertMetric.TOPIC_IMPACT_SCORE`
포함). `alert_events`의 `UniqueConstraint(user_id, dedup_key)`가 모델·마이그레이션 양쪽에
반영됐고, 마이그레이션의 컬럼 nullability·server_default·FK·index가 모델 정의와 정확히
대응합니다. 마이그레이션은 4테이블을 생성하고 FK 역순(notification_channels → alert_deliveries
→ alert_events → alert_rules)으로 drop하며, `down_revision`이 직전 head(`c3d4e5f60068`)에
연결돼 단일 head를 유지합니다.

테스트는 모델 기본값·`UniqueConstraint` 위반·마이그레이션 up/down을 격리 SQLite로 검증합니다.

## Non-blocking

**Q1. postgres 대상 `alembic upgrade head` 미실행 → 해소됨.**
구현 시점에는 codex 샌드박스(네트워크·DB 차단)에서 실행 불가라 격리 SQLite로 up/down만
검증됐다. 리뷰 중 실행 중인 compose postgres(`stock_db`)에 직접 적용해 확인했다:
`c3d4e5f60068 → c3d4e5f60069` 정상 적용, 신규 4테이블(`alert_rules`·`alert_events`·
`alert_deliveries`·`notification_channels`) 생성, `uq_alert_events_user_dedup` 제약·`alert_rules`
16컬럼 확인. 참고로 compose는 마이그레이션을 자동 적용하지 않으므로(backend는 uvicorn만 실행),
배포 환경에서도 동일하게 수동 `alembic upgrade head`가 필요하다.

**S1. `condition`·`channels`·`triggered_value`·`evidence`·`message`가 NOT NULL이고
server_default가 없습니다.** 설계 의도(모든 이벤트가 근거·값을 자체 보유)에 부합하나, 후속
B2(규칙 생성)·B5(엔진)에서 이 필드들을 항상 채워야 합니다. 특히 `evidence`는 근거가 없을 때도
빈 리스트를 명시해야 합니다. B3/B5 계약·서비스 기본값에 반영하면 됩니다. 본 PR 수정 대상은
아닙니다.

**S2. `AlertEventStatus` enum은 정의만 있고 모델은 `read_at` 파생으로 읽음 상태를
표현합니다.** 설계대로이며(상태는 파생 뷰), B3 목록/필터 projection에서 사용할 예정입니다.
현재 미사용은 의도적입니다.
