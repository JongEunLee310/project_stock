## Review Summary

이슈 #278의 목표인 벤치마크 실수집·실파생 전환을 완수합니다. 변경은 7개 파일 +734줄로, 기존 mock 템플릿(`_END_DATE` · `_POINT_COUNTS` · 결정적 생성식)을 제거하고 `stock_price_bars`(interval `1d`) 기반의 누적 수익률 파생으로 교체합니다.

핵심 구조는 세 레이어로 나뉩니다. 첫째, `app/domains/benchmark/sector_map.py`(신규)는 yfinance sector 명칭 11종을 SPDR ETF 심볼로 매핑하는 상수 테이블과 `resolve_sector_etf` 헬퍼를 담으며, universe resolver와 benchmark service가 공유합니다. 둘째, `app/domains/prices/repository.py`에 `get_daily_closes(symbol, market, start) -> list[tuple[date, Decimal]]`이 추가되어 interval `1d` 종가를 timestamp 오름차순으로 반환합니다. 셋째, `BenchmarkService.get_comparison`은 세 시리즈의 종가를 각 1회 쿼리해 dict로 캐싱한 뒤 `_common_dates`에서 교집합·범위 필터·정렬을 수행하고 `_series`에서 누적 수익률을 파생합니다.

설계 문서 `docs/designs/278-benchmark-real-derivation.md`와 대조한 결과는 다음과 같습니다. 기준일을 `datetime.now()` 없이 공통 거래일의 최댓값으로 구하는 방식, 시작일 = 기준일 - range 델타(1M 31 / 3M 92 / 6M 183 / 1Y 366일), 날짜 축 = 공통 거래일 교집합 오름차순, `return_percent = (close / 첫 공통일 close - 1) * 100` quantize 0.01 모두 설계와 일치합니다. 데이터 부족 폴백(어느 시리즈든 bars 없으면 세 시리즈 모두 `points: []`, 구조·순서·label 유지)도 `_common_dates`의 교집합 공집합 경로를 통해 자연스럽게 처리됩니다. 수집 유니버스 확장(`_benchmark_targets`: QQQ 고정 + 섹터 ETF + SPY 폴백, 중복 제거)도 설계에 명시된 대로 구현되었습니다. API 계약(`app/domains/benchmark/schema.py`)은 변경되지 않았으며, alembic · yfinance 어댑터 · 다른 도메인도 불변입니다.

테스트는 `test_benchmark.py`(신규 4개 케이스)와 `test_price_ingestion.py`(신규 3개 케이스), `test_api_contract.py`(픽스처 bars 추가)로 구성됩니다. 누적 수익률 단언의 기대값은 픽스처 종가에서 손계산한 값으로 주석으로 출처가 명시되어 있습니다.

## Blocking

**B1. `get_daily_closes`를 항상 `start=None`으로 호출해 `start` 필터가 실제로 활용되지 않음**

심각도: Blocking — 잠재적 성능 회귀. `app/domains/benchmark/service.py` 57–60행에서 `self.price_repo.get_daily_closes(symbol, market, start=None)`으로 세 시리즈 모두 전체 기간 종가를 메모리에 적재한 뒤 `_common_dates`에서 범위를 필터합니다. `uq_price_bars_symbol_market_interval_ts` 복합 인덱스가 존재하지만 `start=None`이면 timestamp 컬럼 범위 조건이 없어 인덱스 전체 스캔이 됩니다. 히스토리가 짧은 현재 단계에서는 무해하지만, 이슈 #281(5년 히스토리) 데이터가 적재되면 종목당 1,250+ 행 × 3 시리즈를 매 요청마다 메모리에 올리는 구조가 됩니다. 설계 문서는 `start: date | None` 시그니처를 명시하면서 "벤치마크 서비스는 이 헬퍼만 사용한다"고 했으나, 실제 호출 시점에 start를 계산해 넘기는 지침은 없어 구현이 항상 `None`으로 갔습니다.

수정 방향: `get_comparison`에서 `start=None`을 넘기기 전에 보수적 하한(`reference_date_estimate - max_delta`)을 계산해 start로 전달하거나, `_common_dates`의 로직을 쿼리 레이어로 내려 `start`를 활용하도록 바꿔야 합니다. `start`를 전달하더라도 이후 `_common_dates`에서 기준일 기반 재필터를 수행해야 하므로, 가장 단순한 방법은 `start = possible_reference_date_floor = now - max_delta * 1.1` 형태로 충분히 이른 날짜를 먼저 전달하는 것입니다. 단 `now()` 의존 없이 하한을 정하려면 별도 설계가 필요하므로, 현 단계에서의 대안으로는 `_RANGE_DELTAS` 최대값(366일)을 기준으로 `reference_date - timedelta(days=366)` 수준의 보수적 start를 추정값으로 넘기고, `_common_dates`의 실제 기준일 계산은 유지하는 방식을 권장합니다.

## Suggestions

**S1. 자산 심볼이 QQQ일 때 같은 종가 데이터를 두 번 쿼리함**

심각도: 비차단 · 성능 개선 여지. `series_specs`의 ASSET 시리즈와 INDEX 시리즈가 각각 ("QQQ", "NASDAQ")로 구성되는 경우 `get_daily_closes`가 동일 symbol+market 조합으로 두 번 호출됩니다(`app/domains/benchmark/service.py` 57–60행). dict 키가 `BenchmarkSeriesKind` enum으로 달라 덮어쓰기는 없으므로 결과는 정확하지만, DB 쿼리가 2회 발생합니다. 빈도 높은 종목에서 쿼리 중복을 피우려면 `(symbol, market)` 기준으로 먼저 캐싱한 뒤 kind별로 참조하는 방식을 고려할 수 있습니다. 현 단계에서 QQQ를 자산으로 가진 유저가 벤치마크를 조회하는 빈도가 낮을 것으로 예상되므로 후속 라운드에서 처리해도 충분합니다.

**S2. `_common_dates`가 `closes_by_kind` 비어 있을 때 `set.intersection(*[])` TypeError 발생**

심각도: 비차단 · 방어 코딩 여지. `set.intersection(*(set(closes) for closes in closes_by_kind.values()))`는 `closes_by_kind`가 빈 dict이면 `TypeError: descriptor 'intersection' requires a 'set' object but received a 'generator'`가 발생합니다(`app/domains/benchmark/service.py` 77행). `series_specs`가 항상 3원소를 가지므로 현재 런타임에서 이 경로에 도달할 수 없지만, 단위 테스트로 `_common_dates({}, range_)`를 호출하면 예외가 납니다. 빈 guard(`if not closes_by_kind: return []`)를 추가하거나 `functools.reduce`로 교체하는 것을 권장합니다.

**S3. `test_get_benchmark_comparison_returns_empty_points_when_a_series_is_missing`의 default range 의존**

심각도: 비차단 · 가독성 개선 여지. `client.get(f"/api/v1/assets/{asset_id}/benchmark-comparison")` 호출에 `range` 파라미터가 없어 기본값 3M에 의존합니다(`tests/test_benchmark.py` 565행). 이 테스트의 목적은 bars 부재 시 빈 배열 반환 여부이므로 range와 무관한데, 파라미터 생략이 기본값 검증과 혼합되어 의도가 덜 명확합니다. `params={"range": "3M"}`을 명시하거나, 다른 range 테스트와 교차 검증을 추가하지 않더라도 주석으로 의도를 밝히면 충분합니다.

## Questions

**Q1. `_benchmark_targets`의 SPY 판정 로직이 `sector == None`인 자산의 섹터 ETF를 수집 유니버스에 포함하는지 여부**

`resolve_sector_etf(None)`은 `("SPY", "NYSE", "S&P 500")`을 반환하고 `_benchmark_targets`는 `symbol == "SPY"`이면 `needs_fallback = True`로 표시하고 `mapped_targets`에는 추가하지 않습니다(`app/domains/prices/universe.py` 49–51행). 이 결과 sector=None 자산이 워치리스트에 있으면 SPY가 수집 유니버스에 들어가고, 해당 자산의 벤치마크 비교 시 SECTOR_ETF 시리즈가 SPY 데이터를 사용합니다. 설계 문서와 일치하나, sector=None이 "섹터 불명"과 "아직 채워지지 않은 자산"을 구분하지 않습니다. 향후 sector 데이터 보강 시 SPY 폴백이 섹터가 없는 자산에 계속 적용되는 것이 의도인지 확인을 권장합니다.

**Q2. `get_daily_closes`가 반환하는 `Decimal`의 정밀도가 DB 저장 자릿수(NUMERIC(20, 4))와 파생 quantize(0.01) 간 충돌 여부**

`test_get_daily_closes_filters_start_interval_and_orders`의 단언이 `Decimal("102.0000")` 형태(4자리)인 것으로 보아 DB 저장 자릿수는 NUMERIC(20, 4)로 추정됩니다(`tests/test_price_ingestion.py` 657–658행). `_series`에서 `(closes[date] / initial_close - 1) * 100`을 quantize(0.01)로 반올림하므로, 4자리 Decimal로 나눗셈이 이루어진 뒤 quantize합니다. 정밀도 손실 위험은 낮지만, 나눗셈 컨텍스트 기본값(`decimal.getcontext().prec = 28`)에서 중간 연산이 28자리로 처리되므로 현재 구조는 안전합니다. 다만 이 가정이 명시적이지 않으므로 서비스 주석이나 설계 문서에 단위·정밀도 가정을 남겨 두면 좋겠습니다.

## Documentation Impact

설계 문서 `docs/designs/278-benchmark-real-derivation.md`와 구현이 대체로 일치합니다. 다만 B1(start=None 전달)은 설계 문서에서 헬퍼 시그니처만 정의하고 호출 방식을 명시하지 않아 발생한 공백으로, 수정 후 설계 문서의 "조회 헬퍼" 항목에 "호출 시 보수적 start 하한을 전달한다"는 내용을 보완하는 것이 적절합니다. alembic 변경이 없으므로 스키마 변경 기록은 불필요합니다. sector=None 폴백 의미에 관한 Q1은 향후 sector 데이터 보강 설계 문서에서 다루면 충분합니다.

## Final Recommendation

B1(start=None 전달로 인한 인덱스 미활용)이 Blocking으로 분류됩니다. 현재 데이터 규모에서는 기능·정확성에 영향이 없으나, 이슈 #281(5년 히스토리) 수집이 예정된 상황에서 start를 전달하지 않는 채로 머지하면 히스토리 적재 후 요청당 전체 기간 스캔이 고착됩니다. 이 시점에 수정하는 것이 훨씬 저비용입니다.

파생 정확성(기준일·시작일·공통 날짜 교집합·누적 수익률 수식·quantize) 및 폴백 처리(빈 시리즈·SPY 대체)는 손계산과 테스트 모두 정확합니다. API 계약·enum·3시리즈 고정 순서·오류 코드·기본값 3M은 변경 없이 보존되었습니다. 범위 통제(schema.py · alembic · yfinance 어댑터 · 다른 도메인 불변)도 확인됩니다. B1 수정 후 재검증을 권장합니다.

최종 머지 권한은 개발자에게 있습니다.
