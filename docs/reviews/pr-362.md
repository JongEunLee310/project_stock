# PR #362 로컬 리뷰 — 판단 기록 2차 복기·버전 (#358·#359)

## Review Summary

판단 기록 재설계 2차의 복기(review)와 버전 관리(revise)입니다. 두 커밋 모두 #349에서 만든 스키마 위에서 동작하며 신규 마이그레이션이 없습니다.

**Part A — 복기(#358, ADR-016 §6).** `POST`/`GET /api/v1/decision-logs/{id}/reviews`를 추가합니다. `decision_reviews` 테이블에 복기를 저장하며, 판단 품질(`process_quality`)과 투자 결과(`result_metrics`)를 별도 자유 JSON 필드로 분리합니다. `DecisionLogService.create_review`는 소유 판단을 확인하고, `DRAFT` 판단이면 409 `DECISION_LOG_INVALID_STATE`로 막고, 그 외에는 판단 상태를 `REVIEWED`로 전이하며 `decision_logs.reviewed_at`이 null일 때만 스탬프해 최초 복기 시각을 보존합니다. 한 판단에 복수 복기를 허용하고 목록은 최신순입니다.

**Part B — 버전(#359, ADR-016 §5).** `POST /api/v1/decision-logs/{id}/revise`를 추가합니다. `DecisionLogRepository.revise`는 원본의 본문 필드를 복제한 새 `DRAFT`를 만들고, `decision_evidence`·`decision_risks`·`decision_review_triggers`를 새 레코드로 복제하며(JSON `snapshot`·`condition`은 `deepcopy`로 참조 분리), `decision_snapshots`는 복제하지 않습니다. 원본은 `superseded_by_id`만 새 판단 id로 세팅하고 나머지는 불변입니다. 원본이 `DRAFT`/`CANCELLED`이거나 이미 대체됐으면 409입니다. 새 판단 + 부속 + 원본 링크를 단일 트랜잭션으로 커밋합니다.

이번 리뷰는 상태 전이·소유권 가드, 품질/결과 분리, 원본 불변·부속 복제의 정확성을 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. revise가 복제하는 재검토 트리거의 `status`/`triggered_at` 승계 — 현재 허용, 경미.** `repository.revise`는 원본 트리거의 `status`·`triggered_at`을 그대로 복제합니다. 새 판단은 `DRAFT`이고 확정(`activate`) 시 `DATE` 트리거가 `PENDING`으로 재등록되므로 날짜 트리거는 실질 영향이 없습니다. 비-`DATE` 트리거가 `TRIGGERED` 상태로 승계될 수 있으나, 이벤트 트리거 감시는 아직 미구현(#360)이라 현재 동작에 영향이 없습니다. #360 착수 시 revise 복제에서 트리거 상태를 `PENDING`으로 초기화할지 함께 정리하면 됩니다.

## Questions

**Q1. `{id}/reviews`·`{id}/revise` 리터럴 subpath가 파라미터 라우트와 충돌하지 않는가.** `POST`/`GET {id}/reviews`, `POST {id}/revise`는 기존 `GET`/`PATCH /{decision_log_id}`, `POST /{decision_log_id}/activate`와 subpath·method가 구분됩니다. 라우트 등록에서 별도 경로로 매칭됨을 확인해 해소됐습니다.
