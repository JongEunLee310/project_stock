# PR #286 로컬 리뷰 — feat: PER 5년 배수 히스토리 산출 — 중앙값·백분위 실파생 (#281)

리뷰어: Claude (value-for-fable / Sonnet)
날짜: 2026-07-13

## Review Summary

이 PR은 `valuation-metrics` 응답에서 null로 남겨 두었던 `five_year_median`·`percentile`을
PER 1종에 한해 실파생으로 전환합니다. 구현은 세 축으로 나뉩니다.

첫째, 가격 수집 경로에 `range_value` 파라미터를 `PriceIngestionService` → `collect_prices_job`까지 관통시켜 `"5Y"` 백필을 가능하게 하면서 기존 `"3M"` 기본값은 유지합니다. 둘째, 순수 함수 모듈 `app/domains/valuation/history.py`를 새로 추가해 TTM EPS 슬라이딩 윈도 → PER 시계열 → 중앙값·백분위 산출을 DB와 무관하게 처리합니다. 셋째, `ValuationService.get_metrics`에 `PriceBarRepository`·`EarningsRepository`를 추가 주입하고, PER metric 행에만 파생 결과를 채웁니다.

API 계약(`schema.py`)·모델(`model.py`)·마이그레이션은 변경되지 않았고, 설계 문서 Files 절 밖의 변경도 없습니다. 픽스처 수치를 직접 계산해 검증한 결과 모든 테스트 단언이 올바른 값을 주장하고 있습니다.

## Suggestions

**S1. `build_ttm_eps_series` 내 방어 필터 제거 가능 (`app/domains/valuation/history.py:31`)**

`any(eps is None ...)` 체크에서 `continue`한 뒤 아래 `sum` 제너레이터에 `if eps is not None` 필터가 중복됩니다. `continue` 이후에는 윈도 내 None이 없음이 보장되므로 필터는 불필요합니다. 동작에 영향을 주지는 않으나, 실제로는 도달하지 않는 필터가 남아 있어 코드를 읽는 사람이 "아직 None이 남을 수 있다"는 인상을 받을 수 있습니다. 현 범위에서는 허용되는 수준이며, 후속 정리 시 제거를 고려할 수 있습니다.

**S2. `_five_years_ago` 윤년 처리 — 2월 29일 예외만 처리 (`app/domains/valuation/service.py:110-114`)**

현재 구현은 `ValueError` 발생 시 `day=28`로 고정합니다. 오늘이 2월 29일인 경우(윤년)에만 트리거되고, 그 결과 2월 28일로 반올림하는 동작은 설계 문서의 "시계열이 비어도 안전해야 한다" 요건을 충족합니다. 동작은 정확하며 현 범위에서 변경이 필요하지 않습니다. 다만, 예외 처리보다 `timedelta(days=365*5)` 또는 `dateutil.relativedelta`를 사용하면 의도가 더 명확해집니다. 의존성 추가가 수반되므로 지금은 현행 유지가 합리적입니다.

**S3. 서비스 통합 테스트 — 종가·실적 부재 케이스 추가 권장 (`tests/test_valuation.py`)**

설계 Test 절에 "종가·실적 부재 시 null" 케이스를 명시했으나, 이를 직접 검증하는 신규 테스트가 없습니다. 기존 `test_get_valuation_metrics_without_snapshot_returns_null_values`는 스냅샷 부재 케이스를 커버하지만, `_per_history`가 관측치 부족(`median_and_percentile` None 반환)이나 종가 전체 부재 상황에서 PER에도 null을 유지하는 경로는 미커버입니다. 단위 테스트로 간접적으로는 검증되지만, 서비스 레이어를 끝까지 관통하는 시나리오로 확인해 두면 향후 `_per_history` 변경 시 회귀를 더 빠르게 잡을 수 있습니다.
