# PR #383 로컬 리뷰 — 뉴스 인텔리전스 이벤트 캘린더·에이전트 처리 현황 계약 (#370)

## Review Summary

뉴스·공시 인텔리전스(에픽 #307) 2차의 마지막 단위로, 개요 화면의 두 패널 `GET /calendar`(이벤트 타임라인)와 `GET /agent-runs`(에이전트 처리 현황)를 추가합니다. 브랜치는 #369(#382)·#368(#381)·#380·#306(#379) 위에 스택돼 있으나 PR base는 dev이며 커밋은 1건입니다. 이 PR로 BE 2차(#306·#368·#369·#370 + 2차 모델 골격)가 완료됩니다.

**Part A — 이벤트 캘린더(#370, 설계 §3.5).** `service.get_calendar`가 2차 골격 `market_events`를 window·market·topic_id 기준으로 조회하고, `market_event_topics` 조인으로 `related_topic_ids`를 조립합니다. item은 `scheduled_at`·`event_kind`(MarketEventKind)·`title`·`symbol`·`market`·`importance`·`related_topic_ids`입니다. 라우트는 `window`(필수, `^[1-9]\d*[hd]$`)·`market`(필수, 정규화 upper)·`topic_id`(선택)를 받습니다.

**Part B — 에이전트 처리 현황(#370, 설계 §3.6).** `get_agent_runs`가 최근 run의 `last_processed_at`·`processed_documents`·`extracted_events`·`active_topics`·`stages`[{name·status·delayed}]·`analysis_version`·`has_delay`를 반환합니다. 라우트 description에 명시된 대로 "검증 가능한 처리 집계·단계 상태만" 반환하며 비공개 추론 과정은 노출하지 않습니다(스펙 §3.8 준수).

이번 리뷰는 설계 §3.5·§3.6 계약 일치, 캘린더-토픽 조인, 처리 현황의 투명성 원칙(집계·단계만)을 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. `agent-runs`가 최신 run 단건 요약 — 설계 의도에 부합.** `GET /agent-runs`는 목록이 아니라 최근 run 요약을 반환합니다. 설계 §3.6이 "최근 run 요약"으로 정의하므로 부합하며, 처리 이력 목록이 필요해지면 별도 확장 지점으로 남깁니다.

**S2. `calendar`의 `market` 필수화 — #368과 일관된 결정.** 캘린더도 `market`을 필수로 두었습니다. 시장 스코프가 명확해지는 합리적 선택이며 #368 investor-flows와 일관됩니다.

## Questions

**Q1. Stacked 브랜치 머지 순서.** 브랜치가 #382·#381·#380·#379 위에 있어 이 PR diff는 하위 머지 전까지 그 변경을 포함합니다. PR base는 dev이므로 #379 → #380 → #381 → #382 → #383 순서로 머지하면 diff가 각 단위로 자동 정리됩니다. 코드 판단이 아니라 머지 순서 확인 사항입니다.
