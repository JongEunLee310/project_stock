## Review Summary

이 PR은 PR #283–#291 로컬 리뷰에서 나온 비차단 후속 소견 8건을 설계 문서 `docs/designs/309-review-followup-round.md` §1 표를 기준으로 한 라운드에 정리합니다. 와이어 계약(응답 스키마·판정 규칙) 변경은 없으며, 7번 항목만 태스크 결과 dataclass에 필드를 additive로 추가합니다.

8개 항목을 표와 대조한 결과는 다음과 같습니다.

1. `app/api/v1/endpoints/assets.py` — earnings-summary description을 "deterministic mock"에서 "derived from collected reports"로 정정. 반영됨.
2. `app/domains/valuation/history.py` — `if any(eps is None ...): continue`로 이미 None을 걸러낸 뒤에 도달 불가능하던 `if eps is not None` 필터를 제거하고, `cast(list[Decimal], eps_values)`로 타입을 명시. mypy 통과로 캐스팅 타당성이 확인됩니다. 반영됨.
3. `app/domains/signals/repository.py` — `prev_captured_at`에만 `type_coerce`를 쓰는 이유를 "DateTime LAG needs an explicit SQL type for dialect result conversion." 한 줄 주석으로 명시. PR #291 S2에서 지적한 정확한 위치에 붙어 있습니다. 반영됨.
4. `app/domains/benchmark/service.py` — `(symbol, market)`를 키로 하는 `closes_by_target` 캐시를 도입해 ASSET·INDEX·SECTOR_ETF가 동일 대상을 가리킬 때 `get_daily_closes` 중복 호출을 제거. `closes_by_kind[kind]`가 캐시된 dict 객체를 공유하지만 `_common_dates`·`_series`는 모두 읽기 전용이라 별칭(aliasing)에 의한 부작용은 없습니다. `test_get_benchmark_comparison_reuses_duplicate_symbol_market_closes`가 monkeypatch로 호출 횟수를 기록해 (QQQ, NASDAQ)·(XLK, NYSE) 각 1회임을 검증합니다. 반영됨.
5. `app/adapters/market/mock.py` — `fcf_yield=_ratio(seed, -50, 150, 10)` 위에 "Negative yield intentionally covers companies that consume cash." 주석 추가. `_ratio` 계산식 기준 실제 범위가 [-5.0, 10.0)이므로 설계 문서가 명시한 음수 범위 의도와 일치합니다. 반영됨.
6. `docs/knowledge/workflow.md` — "Codex Implementation" 절에 `tests/conftest.py`의 두 단계(env 변수 + import 후 `settings` 객체) provider 격리로 인해 별도 env 접두사 없이 `uv run pytest`가 통과한다는 사실을 한 줄 보강. 반영됨.
7. `app/domains/earnings/ingestion_service.py` — `EarningsIngestionResult`에 `report_success_count`·`report_failure_count`·`event_success_count`·`event_failure_count` 4개 필드를 추가하고, `reports_saved` 플래그로 예외 발생 시점이 리포트 저장 단계인지 이벤트 수집 단계인지 구분해 카운트합니다. 기존 `success_count`/`failure_count`/`saved_count` 증가 지점은 손대지 않아 기존 집계 의미가 그대로 유지됩니다. `EarningsRepository.upsert`/`upsert_event`가 호출마다 개별 `commit()`하므로, 이벤트 단계 실패 시의 `self.db.rollback()`이 이미 커밋된 리포트 저장을 되돌리지 않고, `report_success_count` 증가 시점과 실제 DB 커밋 시점이 어긋나지 않습니다. `test_ingestion_skips_empty_and_failed_targets`·`test_ingestion_counts_event_collection_failure`·신규 `test_ingestion_counts_empty_events_separately` 3개 테스트로 기존 집계 회귀 없음과 신규 카운터 동작을 모두 검증합니다. 반영됨.
8. `docs/designs/230-yfinance-real-providers.md` — `as_of`가 "조회 시각"이 아니라 "loader가 조회해 캐시에 저장한 시각"이며 cache hit 시 TTL 60초 이내의 과거 시각일 수 있음을 명문화. 같은 문서의 Redis TTL 캐시(quote 60초) 설계와 일치합니다. 반영됨.

변경 파일은 위 8건에 해당하는 코드/테스트 9개 파일과, 이번 라운드 자체의 설계 문서·핸드오프 태스크 문서 2개(`docs/designs/309-review-followup-round.md`, `.codex/tasks/task-192-review-followup-round.md`)로 총 12개이며, 범위 밖 변경은 없습니다.

## Suggestions

**S1. 7번에서 추가한 리포트/이벤트 세분 카운터가 아직 어디에도 소비되지 않습니다.**

`app/worker/jobs/earnings.py`의 `collect_earnings_job`은 `EarningsIngestionService(db).collect_and_save(...)`의 반환값을 받지 않고 버립니다. 이는 이번 PR이 만든 문제가 아니라 prices/valuation/news 등 다른 수집 job에도 동일하게 있는 기존 패턴이며, `JobRunService.succeed`도 결과 payload를 받는 인자가 없어 현재는 "운영 리포트"에 반영할 통로 자체가 없습니다. 설계 문서가 요구한 범위(카운터 분리 + 회귀 없음 + 이벤트 실패 테스트)는 정확히 충족되었으므로 이번 라운드에서 막을 사유는 아니지만, 새로 나뉜 카운터가 실제로 PR #287 S1이 말한 "운영 리포트의 혼동 해소"에 쓰이려면 `JobRunService`가 결과 payload를 받는 확장과 `collect_earnings_job`에서의 배선이 후속으로 필요합니다.
