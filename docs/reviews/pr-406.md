# PR #406 로컬 리뷰 — 뉴스 이벤트 추출 배관·골격 추출기 (#398)

## Review Summary

1단계(#397)로 `PENDING` 적재된 `source_documents`에서 사건을 뽑아 `extracted_events`·
`event_evidence`로 생성하는 추출 경로를 만드는 PR입니다. 트래킹 #391의 2단계이며, 설계는
`docs/designs/398-extraction-events-evidence.md`에 확정돼 있습니다. 단일 커밋으로 신규 모듈
하나(`extraction.py`)와 테스트 여섯 건을 더합니다. 모델·스키마·마이그레이션 변경은 없습니다.

이번 단계의 방침은 **배관·계약 우선**입니다. 실제 LLM 추출은 후속 #405로 분리했고, 이 PR은
추출기 Port(`EventExtractor`)·파이프라인 배관(`extract_events`)·골격 규칙 추출기·근거 연결·
`event_fingerprint` 멱등·`processing_status` 전이를 세웁니다. 골격 추출기는 규칙 미매칭 문서에
이벤트를 만들지 않고, 점수(sentiment·importance·confidence)는 중립 placeholder로 둡니다.

이번 리뷰는 근거 연결(모든 이벤트가 근거를 갖는지)이 실제로 강제되는지, 멱등과 문서 단위
원자성이 성립하는지, 값을 지어내지 않는 원칙이 지켜지는지, 범위 밖(LLM·군집·스키마)을
건드리지 않았는지를 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. 문서마다 `commit`을 호출한다 — 문서 단위 원자성을 위한 선택이나 대량·주기 실행에서는
비용이 된다.** `extract_events`는 문서 하나를 처리할 때마다 `commit`합니다(정상 경로 line 213,
실패 경로 line 224). 이는 한 문서의 이벤트·근거·상태 전이를 원자적으로 묶고 실패를 그 문서에
가두는 올바른 설계입니다. 다만 원천이 수천 건 이상이고 주기 실행이 붙는 시점(#402·#405)에는
문서별 커밋이 부담이 될 수 있어, 그때 배치 경계를 재검토할 후보입니다. 현재 규모·수동 실행
전제에서는 문제가 아닙니다.

**S2. 서로 다른 문서가 같은 사건을 보도하면 별도 이벤트로 생성된다 — 이번 범위 밖(군집
#399).** `event_fingerprint`가 근거 문서의 `content_hash`를 포함하므로, 같은 사건이라도 다른
문서에서 나오면 fingerprint가 달라 각각 이벤트가 됩니다. 여러 문서를 하나로 묶는 것은 군집
단계(#399)의 책임이며 설계 §2에도 그렇게 명시돼 있습니다. 이 PR의 멱등은 "같은 문서의 같은
사건을 중복 생성하지 않는다"까지가 범위이고, 그 범위는 정확히 지켜졌습니다.

## Questions

**Q1. 근거 없는 draft 하나가 문서의 유효 이벤트까지 막는 것이 의도인가.** 확인했고 의도된
원자성으로 판단합니다. `_validate_evidence`(line 236)는 이벤트를 하나라도 만들기 전에 draft
전체를 검증하므로, 한 문서가 낸 draft 중 근거 없는 것이 하나라도 있으면 그 문서 전체가
`FAILED`가 되고 부분 생성이 없습니다. 골격 규칙 추출기는 항상 `PRIMARY` 근거를 넣어 이
경로가 발생하지 않지만, 실 LLM 추출기(#405)가 근거 없는 출력을 냈을 때 문서를 부분 적재
없이 통째로 실패시키는 것은 "근거 없는 이벤트를 만들지 않는다"는 원칙에 부합합니다. 테스트
(`..._rolls_back_document_and_marks_failed`)가 이 원자성을 유효/무효 draft 혼합으로 덮습니다.

## Final Recommendation

머지 가능합니다. 설계 §2~7의 Port·골격 추출기·근거 연결·멱등·상태 전이를 항목별로
확인했습니다. 모든 이벤트가 최소 1건의 근거를 갖도록 `_validate_evidence`가 강제하고, 규칙
미매칭 문서는 이벤트 없이 `EXTRACTED`로 전이하며, 점수는 중립 placeholder로 두어 값을
지어내지 않습니다.

범위는 지켜졌습니다. LLM 호출을 붙이지 않았고(#405), 군집을 만들지 않았으며(#399),
스키마·모델·마이그레이션과 수집 로직을 건드리지 않았습니다. Protected Files는 없습니다.

테스트는 규칙 매칭 시 전 필드 값 단언, 미매칭 시 이벤트 0건·`EXTRACTED` 전이, 재요청 시
fingerprint 멱등 스킵, 이미 처리된 문서 제외, 빈 큐, 그리고 문서 단위 원자성 실패를 덮습니다.
필드 존재만 확인하는 단언은 없습니다.

Blocking은 없습니다. S1·S2는 이 PR이 늘린 위험이 아니라 후속(#402·#399)의 후보이고, Q1은
확인해 의도된 원자성으로 정리했습니다.
