## Suggestions

**S1. `EarningsRepository`가 `app/adapters/market/yfinance.py`의 `period_from_end`를 직접 import함**

심각도: 비차단 · 아키텍처 명확성 개선 여지. `app/domains/earnings/repository.py` 7행에서 `from app.adapters.market.yfinance import period_from_end`를 가져옵니다. 도메인 레이어가 특정 어댑터 구현체 파일을 직접 참조하는 구조로, 이 의존 방향은 다른 도메인 repository가 `adapters.market.base`(추상 레이어)만 참조하는 패턴과 다릅니다. `period_from_end`는 순수 함수이므로 `app/domains/earnings/utils.py` 혹은 `base.py`에 두고 양쪽에서 참조하면 어댑터 교체 시 도메인 코드를 건드리지 않아도 됩니다. 현재 유니버스에서 provider가 교체될 가능성은 낮으나, `yfinance.py`가 리팩터링되면 repository까지 수정이 전파됩니다.

**S2. `collect_earnings_job`에서 `symbols` 직접 전달 시 market이 NASDAQ으로 하드코딩됨**

심각도: 비차단 · 범위 한정적. `app/worker/jobs/earnings.py` 13행에서 `symbols`가 직접 전달될 때 `[(symbol.upper(), "NASDAQ") for symbol in symbols]`로 market을 고정합니다. 이는 PR #284(S1)에서 지적된 `collect_valuation_job`과 동일한 패턴입니다. `/jobs/earnings` API를 통해 KOSPI 종목을 수동 트리거할 때 market이 무조건 NASDAQ으로 설정됩니다. 현 단계는 `symbols=None`(유니버스 자동 해소) 경로가 주 경로이므로 즉각 차단은 아닙니다만, `EarningsJobRequest`에 `market` 필드를 추가하거나 `(symbol, market)` 쌍 전달 방식을 검토하는 것이 적절합니다.

**S3. `app/api/v1/endpoints/assets.py`의 `earnings-summary` endpoint description이 구 mock 문구를 유지함**

심각도: 비차단 · 문서 정합성. `assets.py` 205행의 `description="Return a deterministic mock quarterly earnings summary for an asset."`이 이번 PR 범위 밖에서 수정되지 않아 실수집 전환 후에도 "mock"을 언급합니다. 해당 파일은 이번 diff에 포함되지 않았으므로 이번 PR의 구현 결함은 아니나, 후속 정리 이슈로 등록하거나 이 PR에서 함께 정정하는 것을 권장합니다.

**S4. `ingestion_service.py`에서 빈 리스트 반환과 실제 예외를 동일하게 `failure_count`로 집계함**

심각도: 비차단 · 명확성 개선 여지. `app/domains/earnings/ingestion_service.py` 31행에서 provider가 빈 리스트를 반환할 때 `failure_count += 1`로 처리합니다. 심볼 조회 결과가 없는 경우(데이터 미제공)와 네트워크 오류(예외)가 동일 카운터로 합산되어 로그 분석 시 원인 구분이 어렵습니다. 설계 §3의 "실패 스킵·집계" 요건에는 부합하나, `not_found_count`를 별도로 두거나 로그 레벨을 달리하면 운영 가시성이 개선됩니다.

## Questions

**Q1. `_closest_estimate` 방식이 발표 지연/선행 시나리오에서 오매칭될 수 있는지**

`app/adapters/market/yfinance.py` 274–279행의 `_closest_estimate`는 `period_end`와 가장 가까운 발표일의 estimate를 선택합니다. 일반적인 발표 패턴(분기 종료 후 3–6주 내 발표)에서는 정합하나, 발표가 크게 지연되거나 다음 분기 발표일이 이전 분기 종료일에 매우 근접한 경우 인접 분기의 estimate가 선택될 수 있습니다. 설계 §2에서 "period_end와 가장 가까운 발표일 기준"으로 명시하고 있어 설계 허용 범위이지만, 향후 특이 종목(조기 발표·대폭 지연)에서 estimate 오매칭 사례가 발생하면 period 라벨 기반 정확 매칭으로 교체하는 것을 검토할 시점이 생길 수 있습니다. 현재 유니버스에서의 실 데이터 매칭 품질을 모니터링하는 것을 권장합니다.

**Q2. `EarningsReport` 픽스처에서 `updated_at`을 생성자 직접 전달로 고정하는 패턴의 DB 저장 보장 여부**

`tests/test_research_coverage.py` 197행에서 `updated_at=earnings_updated_at`을 EarningsReport 생성자에 직접 전달합니다. `TimestampMixin`의 `updated_at`은 `server_default=func.now()`로 선언되어 있어 ORM 생성자에서 명시적 값을 전달할 때 실제 INSERT 값이 대체되는지 여부는 SQLAlchemy 구현에 따라 다릅니다. 이 패턴은 PR #284에서도 동일하게 사용했으며 CI 통과로 검증된 전례가 있으므로 기능적 문제는 없는 것으로 판단되나, 명시적으로 확인해두는 것이 좋습니다.
