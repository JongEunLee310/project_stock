## Review Summary

`GET /api/v1/research-queue`를 신설한 PR입니다. 기존 테이블의 배치 집계만으로 자산별 리서치 상태(`ResearchStatus`), 완성도(`completeness_pct`), `key_issue`, `stance`·`headline`, `last_updated_at`, 필터 4종, 상단 요약 카운트를 한 번에 반환합니다. 신규 테이블과 마이그레이션은 없습니다.

구현 구조는 설계 §4.6·§4.7의 시그니처를 그대로 따릅니다. 신규 도메인 `app/domains/research_queue/`(schema·service·repository)와 엔드포인트 1개가 추가됐고, 기존 파일 중에서는 `app/api/v1/router.py`·`tests/test_api_contract.py`·`docs/api/frontend-api-spec.md` 세 파일만 수정됐습니다. 기존 도메인의 동작 변경은 없습니다.

핵심 설계 결정은 N+1 회피입니다. `list_queue`는 활성 자산 목록을 한 번에 가져온 뒤 뉴스·리포트·가격·재무·밸류에이션·시그널을 테이블별 배치 집계 쿼리로 처리하고, Python에서 `asset_id` 기준으로 병합합니다. `earnings_upcoming` 필터가 없으면 SELECT가 10개로 고정되며, 이를 `test_query_count_does_not_grow_with_asset_count`에서 SQLAlchemy 이벤트 훅으로 실측합니다.

판정 규칙은 설계 §4.1의 우선순위(NEEDS_ATTENTION → INSUFFICIENT → COLLECTING → STALE → ANALYZED) 순서와 정확히 일치합니다. 완성도 4축(NEWS는 `asset_id` 기준, PRICE·EARNINGS·VALUATION은 `symbol+market` 기준)도 §4.2의 배점 방식(레코드 1건 이상 = 25점)과 동일합니다. 필터 경계 처리는 `earnings_upcoming`에서 `event_date >= today AND <= today+30`을 DB 레이어에서 처리하고, `recently_updated`는 `datetime.combine(utc_now().date(), datetime.min.time(), tzinfo=UTC)`로 오늘 UTC 자정을 계산합니다. 알 수 없는 `filter` 값은 FastAPI의 `ResearchQueueFilter` enum 파싱 단계에서 422로 거부됩니다.

## Suggestions

**S1. `_build_summary`와 `_apply_filter`에서 `utc_now()`를 각각 호출해 자정 경계 불일치 가능성이 있습니다.**

`service.py`에서 `_build_summary`는 `updated_today_count`를 계산할 때 `utc_now()`를 호출하고, `_apply_filter`의 `recently_updated` 분기에서도 독립적으로 `utc_now()`를 호출합니다. 두 호출 사이에 UTC 자정이 지나는 극단적 상황에서 `updated_today_count`와 `recently_updated` 필터 결과가 서로 다른 날 기준으로 계산될 수 있습니다. 테스트에서는 `monkeypatch`로 고정되어 있어 문제가 드러나지 않으나, 실운영에서 자정 직전 요청 시 드물게 불일치가 발생할 수 있습니다. `list_queue` 진입 시점에 `today_start`를 한 번만 계산해 두 메서드에 인수로 전달하면 해소됩니다. 현재 스코프를 벗어나지 않는 수준의 변경이므로 후속 정리로 처리해도 무방합니다.

심각도: 낮음 (자정 경계 극단 케이스에만 해당, 기능 정확성에는 영향 없음).

**S2. `Signal.signal_type`이 `String(20)` 컬럼이라 미지 타입 입력 시 `_top_signal_type`의 `min(signal_types)` fallback이 알파벳 최솟값을 반환합니다.**

`_top_signal_type`은 `WATCHLIST_STATUS_PRIORITY`에서 순서대로 일치하는 타입을 찾고, 없으면 `min(signal_types)`를 반환합니다. `Signal.signal_type`이 DB 레이어에서 `String(20)`으로 열려 있어 `SignalType` enum 외 문자열이 들어올 수 있고, 이 경우 예측하기 어려운 값이 `signal_type` 응답 필드로 노출됩니다. `None`을 반환하거나 `SignalType` 파싱에 실패하는 경우를 `None`으로 처리하면 방어적으로 동작합니다. 실운영에서 발생 가능성은 낮지만, 계약 응답 필드의 값이 FE에 직접 노출되는 만큼 후속 정리 시 함께 검토를 권장합니다.

심각도: 낮음 (미지 시그널 타입이 DB에 없는 한 미발생).

## Questions

**Q1. `last_updated_at`이 `None`이면서 `completeness_pct >= 70`인 자산이 `ANALYZED`로 분류되는 동작이 설계 의도인지 확인이 필요합니다.**

`_derive_status`에서 STALE 조건은 `last_updated_at is not None and as_utc(last_updated_at) < utc_now() - 30days`입니다. `last_updated_at`이 `None`이면 STALE 조건을 건너뛰어 `ANALYZED`를 반환합니다. 이 경우는 가격·재무·밸류에이션 데이터는 있지만 뉴스·리포트·시그널이 전혀 없는 자산에서 발생 가능하며, 설계 §4.1에는 `None` 처리에 대한 명시가 없습니다. 현재 구현은 "데이터 소스가 없으면 staleness를 판정하지 않는다"는 보수적 해석으로, 논리적으로 타당합니다. 그러나 이 케이스를 `STALE`이나 별도 상태로 분류해야 하는 요구가 있다면 후속 이슈에서 설계를 보완하는 편이 적합합니다. 개발자의 확인을 요청합니다.
