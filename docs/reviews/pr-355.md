# PR #355 로컬 리뷰 — 판단 기록(Decision Log) 재설계 1차 (#348·#349·#350·#351·#352)

## Review Summary

판단 기록 도메인을 단일 테이블 저널에서 구조적 저널로 재설계하는 백엔드 1차입니다. ADR-016이 ADR-006을 supersede하며, 다섯 커밋이 설계문서 확정부터 모델·API까지를 순서대로 쌓습니다.

**Part A — 설계·모델(#348·#349, ADR-016).** `docs/decisions/ADR-016-...md`와 `docs/designs/348-decision-log-redesign.md`가 6테이블 계약을 정본으로 고정하고, ADR-006과 기존 `decision-log-domain.md`에 supersede를 표기했습니다. 구현은 `app/domains/decision_logs/model.py`를 `DecisionLog`(재편) + `DecisionEvidence`·`DecisionRisk`·`DecisionReviewTrigger`·`DecisionSnapshot`·`DecisionReview` 5신규 테이블로 나누고, `types.py`에 enum 10종을 정의합니다. 마이그레이션 `alembic/versions/c3d4e5f6006a_redesign_decision_logs.py`는 기존 `decision_logs`를 drop 후 재생성하며, `llm_analysis_runs.related_decision_log_id` FK를 미리 NULL 처리·재구성해 참조 무결성을 지킵니다. 기존 `ticker`→`symbol`/`target_id`, `reason`→`rationale`, `decision_status`→`status` 매핑은 리비전 주석에 남겼습니다.

**Part B — API(#350·#351·#352, 설계 §4).** 생성은 중첩 `evidence`/`risks`/`review_triggers`를 단일 트랜잭션으로 저장하고, `supporting_reasons`/`counter_arguments` 문자열 배열을 `decision_evidence`(SUPPORTING/CONTRADICTING)로 정규화합니다. `POST /{id}/activate`가 상태 `DRAFT→ACTIVE` 전이·`activated_at`/`decided_at` 스탬프·DATE 트리거 등록·요청 스냅샷 저장을 수행하고, DRAFT가 아니면 409 `DECISION_LOG_INVALID_STATE`를 냅니다. `GET /overview`가 기존 `GET /stats`를 대체하며 총계·주간·review_due·active·유형분포를 DB 집계로 산출합니다. `GET /review-queue`와 목록 6종 필터(`target_type`·`symbol`·`decision_type`·`status`·`risk_type`·`review_due_before`)를 추가하고, 목록·큐 응답을 경량 `DecisionLogListItem`으로 바꾸면서 `risks`·`review_at`을 배치 로딩해 목록 SELECT를 상수 회수로 고정했습니다.

이번 리뷰는 설계 계약(ADR-016·§2~§6) 준수와 스코프 통제, 다중 테이블 트랜잭션·집계의 정확성을 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. 목록 N+1을 #352에서 해소 — 확인 완료, 조치 불요.** #350 시점에는 목록이 중첩 포함 `DecisionLogResponse`를 행마다 만들어 evidence·risks·triggers를 개별 쿼리로 로딩했습니다. #352가 목록·큐를 경량 `DecisionLogListItem`으로 바꾸고 `list_risk_types_by_decision`·`list_review_at_by_decision` 배치 로딩(각각 1쿼리)으로 교체해 페이지 크기와 무관한 상수 쿼리로 고정했습니다. 단건 상세는 중첩을 유지합니다. 설계 §4.3과 일치합니다.

**S2. `REVIEW_DUE` 자동 전이 부재 — 설계상 2차 범위, 인지 필요.** `review-queue`와 `overview.review_due_count`는 PENDING DATE 트리거의 `scheduled_at <= now`를 조회 시점에 계산합니다. 상태를 `REVIEW_DUE`로 실제 전이시키는 스케줄러/잡은 없어, `active_count`가 `ACTIVE`+`REVIEW_DUE`를 합산해도 현재는 사실상 `ACTIVE`만 셉니다. 조건 감시·상태 전이는 설계와 핸드오프에서 2차(#353)로 명시한 범위라 1차에서는 정상입니다.

**S3. `created_this_week`를 롤링 7일로 확정 — 문서화됨, 허용.** 설계의 "이번 주"를 주 경계·타임존 모호성을 피해 `created_at >= now - 7d`로 확정했습니다. `repository.aggregate_overview`에 사유 주석이 있고 설계문서 §4.3에도 반영돼, 감사 가능한 결정입니다.

## Questions

**Q1. 기존 `decision_logs` 데이터 drop의 안전성.** 마이그레이션이 기존 테이블을 이관 없이 재생성합니다. 확인 결과, 이 도메인은 그동안 테스트·mock 수준으로만 쓰였고(ADR-016 전제, 재설계 전 코드도 실적재 없음) 운영 실데이터 이관 대상이 아닙니다. `llm_analysis_runs`의 판단 참조도 NULL 처리로 정합을 지킵니다. 재생성 전략과 참조 처리는 리비전 주석에 남아 있어 해소됐습니다.

## Final Recommendation

머지 가능합니다. 다섯 커밋이 설계문서 확정 → 모델·마이그레이션 → CRUD·activate → overview → review-queue·필터 순으로 ADR-016 계약을 항목별로 구현했음을 확인했습니다. enum 10종·6테이블·상태 전이·에러코드·엔드포인트가 설계 §2~§6과 일치하고, 스코프는 1차 경계를 지켜 2차 요소(복기·버전·이벤트 트리거·자동 연결)는 들어오지 않았습니다.
