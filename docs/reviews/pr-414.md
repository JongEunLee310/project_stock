# PR #414 로컬 리뷰 — 뉴스 인텔리전스 파이프라인 러너·실행 기록 (#402)

## Review Summary

1~4단계(수집·추출·군집·해석)를 순차 실행하고 그 실행을 `agent_runs`·`agent_run_stages`로
기록하는 파이프라인 러너를 만드는 PR입니다. 트래킹 #391의 6단계이자 마지막 단계이며, 설계는
`docs/designs/402-pipeline-runner-agent-runs.md`에 확정돼 있습니다. 단일 커밋으로 신규 모듈
하나(`pipeline.py`)와 테스트 세 건을 더합니다. 모델·스키마·마이그레이션 변경은 없습니다.

앞 단계들과 달리 "LLM vs 골격" 선택이 없는 오케스트레이션입니다. 두 스키마 제약을 반영했습니다
— 단계별 처리 건수·소요 시간은 `agent_run_stages`에 자리가 없어 agent_run 레벨 요약만 기록하고
(단계별 메트릭은 후속 #413), `AgentStage` 7종 중 실제 수행하는 COLLECT·EXTRACT·CLUSTER·LINK만
기록합니다.

이번 리뷰는 stage가 실제 수행 단계만 기록되는지, 집계가 단계 result에서 실측인지, 단계 실패
시 run이 정직하게 `FAILED`로 남는지, `agent_run`이 이력으로 append되며 4단계 멱등이 재실행
처리량 0을 보장하는지, 그리고 `active_topics` 산출이 기존 지표와 어떻게 관계되는지를 축으로
봤습니다.

## Blocking

None.

## Suggestions

**S1. `active_topics` 산출이 `repository.active_topic_clusters`와 상태 집합은 같으나 시간 창
조건이 없고, 상태 집합 상수가 두 곳에 중복 정의됐다 — run 스냅샷 지표로는 타당한 선택.**
`_count_active_topics`는 `lifecycle_status ∈ {EMERGING, RISING, ACTIVE}`로 집계합니다. 이는
`repository.py`의 `active_topic_clusters`와 상태 집합이 같지만, 후자에 있는 `last_activity_at`
시간 창(overview 추이 비교용) 조건이 없습니다. `agent_run.active_topics`는 run 시점 스냅샷
지표이므로 시간 창이 없는 편이 오히려 맞습니다. 다만 (1) 두 "active" 지표가 같은 상태 집합을
쓰면서 시간 필터가 달라 값이 다를 수 있다는 점, (2) 상태 집합 상수가
`ACTIVE_TOPIC_LIFECYCLE_STATUSES`(pipeline)와 repository 양쪽에 중복 정의돼 향후 상태 집합
변경 시 두 곳을 동기화해야 한다는 점은 남겨 둡니다. 지금 값이 틀린 것은 아닙니다.

**S2. 단계마다 `commit`을 호출한다 — 오케스트레이션 특성상 자연스럽다.** run 생성·각 stage
기록·run 갱신이 각각 커밋되고, 4단계 함수도 내부에서 커밋합니다. 단계 단위로 실행·기록을
확정하고 실패를 그 단계에 가두기 위한 구조이며, 실패 시 `rollback`이 미커밋분만 되돌리고 이미
커밋된 앞 단계·stage·run은 보존됩니다. 현재 규모에서 문제가 아닙니다.

## Questions

**Q1. 실행 트리거가 없는데 러너를 어떻게 호출하는가.** 확인해 정리했습니다. 이번 단계는
`run_pipeline` 함수가 진입점이고, 수동 실행·테스트에서 호출합니다. 스케줄러·주기 실행 연결은
설계 §2에서 이번 범위 밖으로 두었습니다(데이터 수집 파이프라인 마일스톤·#413에서 다룸).
골격 파이프라인의 검증 목적에는 함수 진입점으로 충분합니다.

## Documentation Impact

설계 문서 `docs/designs/402-pipeline-runner-agent-runs.md`는 이 브랜치의 선행 커밋에서 이미
작성됐고, 이 PR은 그 설계를 구현합니다. 추가 문서 변경은 없습니다.

ADR은 불요합니다. 스키마를 변경하지 않고 기존 고정 모델에 실행 기록을 채우며, 러너는 기존

다룹니다. Failure Record도 불요합니다. 부재하던 실행 기록 경로를 만든 작업입니다.

## Final Recommendation

머지 가능합니다. 설계 §2~5의 러너·stage 매핑·집계·실행 이력을 항목별로 확인했습니다. stage는
실제 수행하는 COLLECT·EXTRACT·CLUSTER·LINK 4종만 기록되고, 집계는 추출 result와 DB 상태에서
실측하며, 단계 실패 시 run·stage가 `FAILED`로 남고, `agent_run`이 이력으로 append돼 4단계
멱등이 재실행 처리량 0을 보장합니다.

범위는 지켜졌습니다. 스키마·모델·마이그레이션을 변경하지 않았고(단계별 메트릭은 #413), 4단계
함수·서비스·스케줄러를 건드리지 않았습니다. Protected Files는 없습니다.

테스트는 정상 실행의 집계·stage 구성 값 단언, 단계 실패 시 run·stage `FAILED`, 재실행 append와
멱등 처리량 0을 덮습니다. 필드 존재만 확인하는 단언은 없습니다.

Blocking은 없습니다. S1은 run 스냅샷 지표로 타당한 선택이며 상수 중복만 남겨 둘 관찰이고, S2는
오케스트레이션 특성이며, Q1은 확인해 진입점을 정리했습니다.

이 PR로 트래킹 #391의 파이프라인 6단계(수집·추출·군집·해석·수급일정·처리현황)가 모두 닫힙니다.
각 단계는 배관·계약·골격 우선으로 세웠고, 실 알고리즘·외부 공급원·스키마 확장은 후속
(#403·#405·#407·#409·#411·#413)으로 분리했습니다.

최종 머지 권한은 개발자에게 있습니다.
