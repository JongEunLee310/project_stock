## Review Summary

에이전트 2의 분석 결과를 Obsidian 노트로 남기고 에이전트 1의 일일 브리프에 연결하는 PR입니다. 커밋은
핸드오프와 Codex 구현으로 구성됩니다. Codex 실행은 모델 용량 초과로 두 번 끊겼습니다. 두 번째 실행에서
구현과 테스트는 끝났고 최종 보고만 남지 않아, orchestrator가 diff와 검증을 직접 확인했습니다.

**Part A — 분석 노트(설계 464 §6.1).** `render_filing_analysis_note`는 frontmatter, 섹션별 변화(중요도 순과
종류 라벨), `limitations`, 통계 표, 근거 각주를 씁니다. 두 섹션의 번호가 겹치므로 각주 이름에 섹션 접두사를
붙입니다(`[^RF-A1]`, `[^BIZ-M3]`). 쓰기는 기존 `_write_new`를 재사용합니다. 노트는 리포트·신호 단계 뒤에
쓰며, 쓰기 실패는 `note_failures`에만 남습니다.

**Part B — 일일 브리프 연결(설계 464 §6.2).** 에이전트 1이 브리프 기간(직전 브리프 `created_at` 또는 48시간
전부터 실행 시각까지)의 `FILING_ANALYSIS` 리포트를 조회해 `filing_analyses`에 담습니다. LLM 스냅샷은 바뀌지
않습니다. 일일 노트는 `## 가격·신호` 앞에 `## 새 연간보고서 분석` 섹션과 분석 노트 wikilink를 씁니다.
`filing_analyses`는 기본값이 빈 목록이라 기존에 저장된 브리프 JSON도 그대로 읽힙니다.

이번 리뷰는 실제 노트 형식, 기존 브리프와의 호환, 실패 격리를 축으로 봤습니다.

## Suggestions

**S1. 브리프 연결의 wikilink는 이름 충돌 접미사를 반영하지 않습니다 — 경미, 허용.** `note_path`를
`filings/{SYMBOL}/FY{연도}-10-K`로 계산하므로, 같은 노트가 이미 있어 `-2`가 붙은 경우에는 링크가 원래 노트를
가리킵니다. 분석은 보고서당 한 번이라 충돌은 수동으로 지우고 재분석할 때만 생깁니다. 핸드오프에서 가정으로
정한 동작입니다.

**S2. 분석 콘텐츠 하나를 읽지 못하면 그 종목의 브리프 전체가 실패합니다 — 경미, 관찰.** 에이전트 1은 연결할
리포트마다 `FilingAnalysisContent.model_validate`를 호출하며, 이 오류를 따로 잡지 않습니다. 같은 코드베이스가
저장한 JSON이라 지금은 문제가 없습니다. 다만 나중에 분석 콘텐츠 스키마를 바꿀 때는 기존 데이터와의 호환을
함께 확인해야 합니다.

## Questions

**Q1. 실제 노트가 의도대로 만들어지고 브리프에 연결되는가 — 리뷰 중 확인해 해소했습니다.** 실 DB
복제본과 실제 LLM, 임시 vault를 썼습니다. 기존 분석 리포트를 지우고 분석부터 다시 실행했습니다.

- 분석: 3종목 분석, 신호 3건, 알림 3건, 노트 3개, 노트 실패 0건
- 일일 리서치: 4종목 처리, 노트 5개(종목 4개와 인덱스)
- NVDA 분석 노트: 위험요인 12개·사업 7개 변화가 중요도 순으로 정리됐습니다. 통계 표에 잘린 수 31이
  보이고, 각주마다 원문 발췌와 SEC 링크가 붙었습니다.
- NVDA 일일 노트: `## 새 연간보고서 분석`에 `[[stock-agent/filings/NVDA/FY2026-10-K|10-K FY2026]]` 링크와
  중요도가 들어갔습니다.

재실행 결과는 #478 리뷰 때와 세부 중요도가 조금 다릅니다(예: NVDA Groq 라이선스 위험이 HIGH에서 MEDIUM).
LLM 출력의 변동이며, 최고 중요도와 핵심 변화는 같았습니다.
