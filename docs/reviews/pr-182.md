## Review Summary

LLM 데이터 파이프라인 3단계로, 지금까지 분석 도메인에 묶여 있던 뉴스 정규화를 명시적
`NewsNormalizer`로 분리해 뉴스 수집 잡에 배선한 PR입니다. `app/domains/news/normalizer.py`의
`NewsNormalizer`는 DB·세션에 의존하지 않는 순수 컴포넌트로, symbol의 제공자 접두/접미
(`NASDAQ:AAPL.O` → `AAPL`) 제거·대문자화, market 대문자·trim, URL의 fragment·trailing slash
제거와 host 소문자화, `published_at`의 tz-naive → UTC 보정을 담당하고 `RawNewsEvent`를
`NewsItemCreate`로 매핑합니다. 부수효과가 있는 asset 해소·`NewsItem` 저장·상태 전이는
`NewsNormalizationService`에 응집해, 설계 Decision H(순수/부수효과 분리)를 정확히 지켰습니다.

수집 잡 경로(`NewsIngestionService._collect_target`)는 raw 저장(`save_with_symbol`)이 성공한
직후에만 정규화를 호출하고, 정규화가 성사된 raw 행의 `processing_status`를 `normalized`로
전이시킵니다. 이는 2단계에서 만든 컬럼의 첫 writer이며, 가격 파이프라인이 raw 저장 직후 검증·정규화를
인라인 수행하는 구조와 대칭입니다. asset을 해소하지 못한 경우(symbol/market 부재 또는 매칭 asset
없음)에는 `NewsItem`을 만들지 않고 raw 행을 `fetched`로 남겨(경고 로그) 설계 Decision J를
반영했고, `failed`로 표시하지 않아 4단계 검증 의미와 충돌하지 않습니다. URL canonical 중복 시에도
`NewsItem`을 중복 생성하지 않고 raw 행만 `normalized`로 전이시켜 멱등합니다.

`PriceNormalizer`는 기존 `prices/ingestion_service.py`의 인라인 canonicalization(symbol/market
upper, `_as_utc`)을 추출한 것으로, 기존 `_as_utc`가 새 컴포넌트로 위임하도록만 바뀌어
behavior-preserving입니다. 보호 파일(`app/domains/analysis/*`, `app/domains/ingestion/*`의
`ProcessingStatus`, `app/domains/raw_prices/*` 등)은 변경되지 않았고, 분석 플로우
`_create_new_items`는 설계 Decision K대로 손대지 않았습니다.

## Suggestions

- **S1 · 분석 플로우와의 이중 생성 경로**: 수집 잡과 `analysis/service.py._create_new_items`가 둘 다
  `NewsItem`을 만들 수 있습니다. 두 경로 모두 `exists_by_url`로 멱등하지만, 수집 잡이 먼저 canonical
  URL로 `NewsItem`을 만들면 분석 플로우가 원본 URL(canonical 아님)로 `exists_by_url`을 조회해
  중복으로 판단하지 못하고 다시 만들 여지가 있습니다. 반대로 canonical이 동일하면 건너뜁니다. 설계
  Decision K가 v0.1 수용으로 명시한 divergence이므로 이번 범위에서는 문제가 아니지만, 6단계
  ContextBuilder가 정규화 산출물을 소비할 때 두 경로를 수렴시키면서 dedup 키를 canonical URL로
  통일하는 것을 함께 확인하면 좋겠습니다.
- **S2 · normalized 판정 방식**: `_collect_target`이 `normalize_event` 반환값 대신 refresh된
  `event.processing_status == NORMALIZED`로 `normalized_count`를 집계합니다. `mark_normalized`가
  `NewsItem` 생성뿐 아니라 canonical URL 중복(NewsItem 미생성)에서도 호출되므로, 두 경우 모두
  normalized로 집계됩니다. 이는 "raw 행이 정규화 단계까지 처리됐다"는 상태 의미로는 일관적입니다.
  다만 집계 지표가 "새로 만든 NewsItem 수"를 뜻하지 않는다는 점은 3단계 소비처가 이 카운트를 볼 때
  유념할 부분입니다.

## Questions

- **Q1 · symbol canonicalization 규칙의 적용 범위**: `NewsNormalizer.canonicalize_symbol`은 `:` 뒤,
  `.` 앞을 취해 `NASDAQ:AAPL.O` → `AAPL`로 만듭니다. 이 규칙이 한국 종목 코드(`005930.KS` →
  `005930`)에도 맞게 동작하는지는 테스트로 확인됐습니다. 다만 수집 잡의 targets는 이미 asset·
  watchlist에서 온 정제된 symbol이라, 이 canonicalization이 실제로 교정 효과를 내는 입력이 어디서
  들어오는지(향후 외부 제공자 원본 표기)에 따라 규칙 강도를 조정할 수 있습니다. v0.1 범위로는
  현재 규칙이 타당합니다.
