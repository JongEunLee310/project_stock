## Review Summary

뉴스·공시 인텔리전스 3차 계약을 구현한 PR입니다. 커밋은 구현 본체(`뉴스 인사이트 3차 자금 흐름·설명 계약 구현`)와 리뷰 수정(`fix: fund-flow-outlook 미사용 market 파라미터 제거`) 두 건입니다. FE #267·#268이 소비할 계약을 seed mock 위에 고정합니다.

기존 `app/domains/news_insights/` 도메인에 3차를 확장합니다. enum 3종(`ScenarioKind`·`FundFlowDirection`·`FlowLikelihood`)을 `types.py`에, 테이블 4종(`fund_flow_outlooks`·`fund_flow_scenarios`·`topic_explanations`·`explanation_factors`)을 `model.py`에 추가했고 리스트형 필드는 JSON array 컬럼으로 저장합니다. 마이그레이션 `c3d4e5f6006d`는 phase2 head `c3d4e5f6006c` 위에 스택하며 단일 head를 유지합니다. `schema.py`에 3종 응답 projection, `repository.py`에 신규 테이블 조회와 CONTRADICTING evidence·counter_arguments 조회, `service.py`에 outlook 목록·시나리오 3종 정렬·explanation 조립을 추가했습니다. 라우트 3개(`/fund-flow-outlook`·`/topics/{id}/scenarios`·`/topics/{id}/explanation`)를 `news_insights.py`에 등록했습니다.

**Part A — 자금 흐름 전망·시나리오(#371, 스펙 §3.6·§5.9).** `fund_flow_outlooks`는 섹터별 방향(`FundFlowDirection` INFLOW/OUTFLOW/NEUTRAL)·수준(`FlowLikelihood`)·범위 라벨·기간·신뢰도·가정·위험을 담고 확정 예측을 만들지 않습니다. `fund_flow_scenarios`는 `(topic_id, analysis_version, scenario_kind)` unique로 버전당 낙관·기준·보수 3행을 저장하며, 서비스가 항상 3종 정렬 반환을 검증합니다. 금액은 라벨 문자열, weight는 0~1 가중치입니다.

**Part B — 인사이트 설명가능성·반대 관점(#372, 스펙 §5.10·§5.11).** `topic_explanations`(+`explanation_factors`)는 기여 요인 비율(합 ≈ 1.0)·메타(data_coverage·missing_data·limitations·confidence)·선반영 여부를 담습니다. 반대 관점은 신규 테이블 없이 1차 `topic_insights.counter_arguments`와 `event_evidence`의 `evidence_role=CONTRADICTING`를 재사용·구조화해 `counter_view`(counter_arguments·invalidation_conditions·already_priced_in·contradicting_evidence)로 조립합니다. 기여 비율은 seed·정량, LLM은 문장 서술만 담당하는 계약입니다.

이번 리뷰는 계약-설계 일치, 사실/추론 분리와 확정 예측 금지 원칙, 마이그레이션 단일 head, 미사용 파라미터 정리를 축으로 봤습니다.

## Suggestions

**S1. 데이터 없는 토픽의 `scenarios`·`explanation`이 `RuntimeError`(500) — 픽스처 단계에서 허용, 후속 완화 권장.** `get_topic_scenarios`·`get_topic_explanation`은 토픽이 존재하지만 3차 데이터가 없으면 `RuntimeError`를 던져 500이 됩니다. 현재 seed는 데모 토픽에만 3차 데이터를 넣으므로 다른 토픽 상세에서 이 두 패널은 500을 받습니다. 트렌드·근거 패널이 빈 데이터를 graceful하게 200으로 반환하는 것과 대비됩니다. FE가 패널별 부분 실패를 격리하므로 페이지 전체가 깨지지는 않지만, 정상 상태(아직 분석 안 된 토픽)를 오류로 표현하는 것은 부정확합니다. 실수집·실추출 단계 진입 시 빈 응답(빈 시나리오·빈 factors)이나 도메인 404로 완화하는 편이 낫습니다. 병합을 막지 않습니다.

**S2. seed 시나리오 weight 합의 의미 — 계약 문구로 충분, 저장 제약은 두지 않음이 타당.** 시나리오 weight는 근거 기준 가중치로 합이 100%가 될 수 있으나 통계적 확률로 과표현하지 않는다는 원칙을 계약·문서로 명시했습니다. DB 레벨 합계 제약을 두지 않은 것은 버전 누적·부분 저장을 허용하기 위한 합리적 선택입니다.

## Questions

**Q1. `market` 파라미터 처리.** 초기 구현은 `/fund-flow-outlook`이 `market` 쿼리를 수용하나 `fund_flow_outlooks`에 market 컬럼이 없어 필터가 무시됐습니다(계약이 오해를 부르는 상태). 설계문서 §3.1이 market 필터를 명시했으나 §2.1 테이블에 컬럼을 두지 않은 설계 불일치가 원인이었습니다. 리뷰 중 파라미터를 제거하고 설계문서 §3.1을 정정해 해소했습니다(필요 시 컬럼과 파라미터를 함께 추가). `uv run ruff` 통과·`test_news_insights` 23 passed로 회귀 없음을 확인했습니다.
