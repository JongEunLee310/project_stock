## Review Summary

6단계(#187)에서 Core slice로 빈 리스트로 남겨둔 `SymbolCard.recent_news`·`SymbolCard.signals`를
실제 배선한 6.5단계 PR입니다. `context_builder.py` 매핑 로직과 테스트만 변경했고, 계약
(`schema.py`)·소스 도메인(news·signals)·마이그레이션·route는 건드리지 않았습니다(설계 Decision JJ).

`build_symbol_context`는 자산이 해석될 때만 `NewsItemRepository.list_by_asset`와
`SignalRepository.list_by_asset(include_expired=False, limit=5)`를 읽어 각각 `RecentNewsItem`·
`SignalItem`으로 매핑합니다(Decision FF·II). nullable 소스는 required 계약에 안전하게 대체됩니다.
뉴스 `summary`는 `""`, `published_at`은 `created_at`, `trust_level`은 보수적 기본값 `"unknown"`으로
채우고(Decision GG), 시그널 `risk_level` 결손 시 `severity`를 `score` 버킷(70/40 → high/medium/low)
으로 파생합니다(Decision HH). 뉴스 repository가 `limit` 인자를 받지 않아 조회 후 `[:5]` slice로
제한하는데, 현재 수동 소수 심볼 범위에서는 문제가 아닙니다.

`data_quality.news_data_status`는 하드코딩 `MISSING`에서 실제 산출로 전환됐습니다. 번들 내 어느
심볼이든 `recent_news`가 있으면 `VALID`, 전무하면 `MISSING`이며, 상시 뉴스 경고 문구를 제거해
`MISSING`일 때만 표기하도록 정리했습니다. 가격·포트폴리오 상태·경고 규칙은 6단계 그대로 유지됩니다.

## Suggestions

- **S1 · 뉴스 조회 후 slice**: `NewsItemRepository.list_by_asset`가 `limit`을 받지 않아 자산의 전체
  뉴스를 읽은 뒤 `[:5]`로 자릅니다. 시그널 조회는 repository `limit`을 사용하는 것과 대비됩니다.
  뉴스가 대량 축적되는 시점에는 repository에 `limit`을 추가해 DB에서 제한하는 편이 낫습니다. 핸드오프
  범위(배치/성능 최적화 제외)와 일치하는 선택이라 이번 범위 문제는 아닙니다.
- **S2 · trust_level 기본값의 의미**: `trust_level`이 `NewsItem`에 미영속이라 전부 `"unknown"`으로
  채워집니다(Decision GG). 낙관적 값을 피한 안전한 선택입니다. 다만 소비 단계(7단계 프롬프트 변환)
  에서 `"unknown"`이 신뢰도 판단에 어떻게 반영되는지 명시해야 LLM이 미상 신뢰도를 과신하지 않습니다.
  출처 신뢰도 영속화는 수집·검증 단계 후속으로 남깁니다.
- **S3 · severity 버킷 임계**: `score >= 70 → high`, `>= 40 → medium`, 그 외 `low`의 휴리스틱입니다.
  `risk_level`이 있으면 우선하고 결손 시에만 파생하므로 합리적이나, 임계 근거는 상수 주석 외에는
  문서화돼 있지 않습니다. 시그널 룰 엔진(analysis)이 `risk_level`을 일관되게 채우기 시작하면 이
  파생 경로의 사용 빈도와 임계를 재검토하는 것을 권합니다.

## Questions

- **Q1 · 후속 범위**: 이번 6.5로 6단계 Core slice의 뉴스·시그널 배선이 마무리됩니다. 다음은 7단계
  LLM Gateway(번들→프롬프트 변환·`LLMContextBundle` 영속)로 이해하고 있는데, 그 전에 별도로 다룰
  항목(예: `trust_level` 영속화, 뉴스 repository `limit`)이 있는지 확인 부탁드립니다.
