## Review Summary

리서치 차트 1M·3M·6M·1Y 구간이 결측 봉 하나 때문에 전체 502로 실패하던 문제를
수정하는 버그픽스 PR입니다. `_bars_from_frame`(`app/adapters/market/yfinance.py:88`)의
row 루프에서 `PriceBarResult` 생성을 `try/except ValueError`로 감싸, 결측(NaN/None)
가격 필드 때문에 `_to_decimal`이 던지는 `ValueError`를 그 row에서만 잡아 `continue`로
건너뛰고 나머지 row는 그대로 append합니다. 결측이 없는 정상 프레임은 기존 로직과
동일한 경로를 그대로 통과하므로 변경 폭이 작고, 기존 `_to_decimal`의 시그니처나
다른 호출부(`_optional_decimal`, `_payload_from_frame` 등)는 건드리지 않았습니다.
테스트는 일부 결측(`test_yfinance_bars_skip_rows_with_missing_required_prices`,
OHLC/Adj Close 5개 필드를 `parametrize`로 각각 결측시켜 검증), 전부 결측
(`test_yfinance_bars_return_empty_when_all_rows_have_missing_prices`) 두 케이스를
새로 추가했고, 정상 프레임 회귀는 기존
`test_yfinance_provider_parses_history_without_network`가 `get_daily_bars` 전체
경로로 그대로 고정하고 있습니다.

다만 실제로 `_bars_from_frame`을 직접 호출해 보면, 이번 fix가 의도한 "OHLC 결측만
skip"의 범위를 벗어나는 부작용이 하나 확인됩니다(B1).

## Blocking

**B1. Volume만 NaN이고 OHLC가 정상인 봉이 통째로 skip되어 "volume 결측은 0 처리"
요구사항을 어깁니다.**

`volume=int(row.get("Volume") or 0)`는 이번 PR에서 손대지 않은 기존 코드이지만, 새로
추가된 `try/except ValueError`가 이 줄까지 함께 감싸면서 부작용이 생겼습니다.
`float("nan")`은 파이썬에서 truthy이므로 `nan or 0`은 `nan`으로 평가되고,
이어지는 `int(nan)`이 `ValueError: cannot convert float NaN to integer`를 던집니다.
현재 구현은 이 예외도 OHLC 결측과 구분 없이 잡아 `continue`하므로, OHLC/adjusted_close가
모두 정상인데 Volume만 NaN인 봉은 유효 봉임에도 결과에서 통째로 사라집니다.

직접 재현했습니다.

```
bars = _bars_from_frame(frame=FakeFrame(...OHLC 정상, Volume=nan...), ...)
# 결과: []  (기대: OHLC/adjusted_close 값을 가진 봉 1개, volume=0)
```

핸드오프 Implementation Scope는 "`volume` 결측은 기존처럼 `0` 처리를 유지한다"고
명시하고 있고, 이슈 #324의 완료 조건도 "유효한(OHLC·adjusted_close가 모두 온전한)
봉만 반환"이라고만 규정합니다. 즉 Volume 결측은 skip 사유가 아니라 0으로 대체해
봉을 유지해야 하는 필드인데, 현재 구현은 그 경계를 지키지 못합니다. 이전 코드에서도
`int(nan)`은 동일하게 예외를 던졌지만 당시엔 `_bars_from_frame`에 try/except가 없어
해당 예외가 그대로 전파되어 전체 502로 드러났습니다. 지금은 그 예외가 조용히
삼켜지면서 유효한 거래일 데이터가 차트에서 눈에 띄지 않게 빠지는 형태로 바뀌었으므로,
증상이 더 커진 것은 아니지만 발견하기는 더 어려워졌습니다. 실제 yfinance 데이터에서
Volume이 NaN으로 오는 봉(지수 티커, 거래정지일 등)이 존재할 수 있어 가상의 엣지
케이스로 보기 어렵고, 테스트 스위트에도 이 케이스(OHLC 정상 + Volume NaN)가
커버되어 있지 않아 그대로 병합되면 회귀 없이 통과합니다. Volume 파싱을 가격 필드용
`try/except`와 분리하거나, 기존 코드베이스에 이미 있는 `_is_nan` 헬퍼로
`row.get("Volume")`을 먼저 걸러 `0`으로 대체하는 방식으로 고쳐야 합니다. 병합 전
수정이 필요합니다.

### Resolution (B1 반영, 커밋 `014e9f3`)

Volume 파싱을 가격 필드 `try/except` 밖으로 분리하고, `row.get("Volume")`이 `None`이거나
`_is_nan`이면 `0`, 그 외에는 `int` 변환하도록 고쳤습니다. 이제 OHLC/adjusted_close가
정상이고 Volume만 NaN인 봉은 `volume=0`으로 유지되고, 가격 필드 결측 봉은 그대로
skip됩니다. 실측 재확인 결과 `OHLC 정상 + Volume NaN → 봉 1개(volume=0)`,
`High NaN → 봉 0개`로 기대대로 동작합니다. Volume NaN 회귀 테스트를
`tests/test_price_ingestion.py`에 추가했고, 재검증(`ruff`·`mypy` 401 files·`pytest`
869 passed) 모두 통과합니다.

## Questions

**Q1. `except ValueError`가 `Decimal` 파싱의 `decimal.InvalidOperation`은 잡지
못하는데, 의도된 범위인지 확인이 필요합니다.**

`_to_decimal`은 NaN/None에는 `ValueError`를 직접 던지지만, 값이 NaN도 None도 아닌
파싱 불가능한 문자열(예: 공급자가 `"N/A"` 같은 값을 섞어 보내는 경우)이면
`Decimal(str(value))`가 `decimal.InvalidOperation`(`ArithmeticError`의 하위 클래스,
`ValueError`가 아님)을 던져 이번 `except ValueError`로는 잡히지 않습니다. 이 경우
여전히 예외가 `_bars_from_frame` 밖으로 전파되어 전체 502로 돌아가는 기존 동작이
유지됩니다. 이슈 #324와 핸드오프가 명시한 범위는 NaN/None뿐이라 이 케이스는
스코프 밖이며 이번 PR이 만든 회귀도 아니지만, 그런 값이 실제 yfinance 응답에
등장할 가능성이 있는지, 있다면 후속 이슈로 다룰지 여쭙습니다. 차단 사유는
아닙니다.
