## Review Summary

이 PR은 `/api/v1/assets/{asset_id}/research-summary` 응답에 반대 관점을 구조화한 `counter_points` 필드를 additive로 추가합니다. 설계 문서 `docs/designs/298-counter-points.md`가 명시한 범위와 정확히 일치하며, 변경 파일도 스키마·서비스·테스트·설계 문서 다섯 개로 한정되어 있습니다.

`app/domains/research_summary/schema.py`에는 `CounterBasisType`(VALUATION/FUNDAMENTALS/COMPETITION/MACRO/SENTIMENT)과 `CounterPointStrength`(WEAK/MODERATE/STRONG) 두 `str` Enum과 `CounterPoint` 모델(`id`, `claim`, `basis`, `basis_type`, `strength`, `source_label: str | None = None`)이 새로 추가됩니다. `ResearchSummaryResponse.counter_points: list[CounterPoint]`는 기존 `counter_view` 필드 바로 아래에 삽입되어 있고, 기존 필드의 이름·순서·타입은 그대로 유지됩니다.

`app/domains/research_summary/service.py`는 `_CounterPointTemplate` TypedDict를 추가하고 두 mock 템플릿(BUY_CANDIDATE, WATCH)에 각 2건씩 `counter_points`를 채웁니다. `get_summary`의 응답 조립부에서 `CounterPoint.model_validate(point)`로 변환해 넣는 방식은 기존 `key_risks` 처리 패턴을 그대로 재사용한 것입니다.

mock 템플릿 데이터를 기존 `counter_view` 문구와 대조한 결과, 두 템플릿 모두 의미가 정확히 일치합니다. BUY_CANDIDATE는 밸류에이션 선반영(`VALUATION`/`MODERATE`)과 경쟁 심화(`COMPETITION`/`WEAK`) 순서로, WATCH는 펀더멘털 개선세(`FUNDAMENTALS`/`MODERATE`)와 우려 선반영(`SENTIMENT`/`WEAK`) 순서로 기존 문구의 취지를 그대로 계승하면서 근거 유형·강도만 새로 부여했습니다. 이는 설계 문서 3절이 명시한 매핑과도 일치합니다.

테스트는 계약 테스트(`test_api_contract.py`)에 `COUNTER_POINT_CONTRACT` 타입 계약을 추가하고, 도메인 테스트(`test_assets.py`)에는 필드 구성 전수 검사와 stance별 `(basis_type, strength)` 순서 단언까지 포함되어 있어 커버리지가 탄탄합니다.

## Suggestions

**S1. `MACRO` enum 값이 어느 mock 템플릿에서도 사용되지 않습니다.**

설계 문서 3절은 `CounterBasisType`에 `MACRO`를 포함시켰지만 두 템플릿(BUY_CANDIDATE, WATCH) 모두 `VALUATION`/`COMPETITION`/`FUNDAMENTALS`/`SENTIMENT`만 사용하고 `MACRO`는 어떤 응답에서도 노출되지 않습니다. FE 계약상 값 자체는 유효하므로 문제는 아니지만, 향후 매크로 계열 반대 관점을 추가할 때를 대비한 자리로 보입니다. 이번 범위에서 반드시 채울 필요는 없어 비차단입니다.

**S2. `source_label`의 null 케이스가 실제 응답으로 검증되지 않습니다.**

설계 문서는 `source_label: str | None = None`을 "mock 단계 null 허용"으로 명시했지만, 두 템플릿 모두 `"AI 분석"`으로 고정되어 있어 null이 실제로 직렬화되는 경로는 테스트되지 않습니다. 계약 테스트의 타입 튜플 `(str, type(None))`은 스키마 차원의 허용만 확인할 뿐, 런타임에서 null 값이 나오는 경로를 exercise하지는 않습니다. mock 단계에서는 두 템플릿 모두 출처가 있는 것이 자연스러워 당장 블로킹할 사안은 아니지만, LLM 실생성 연동 시점에는 null 케이스 테스트를 추가하는 것이 좋겠습니다.

**S3. `docs/api/frontend-api-spec.md`의 research-summary 예시 JSON이 갱신되지 않았습니다.**

364행 이하 예시 응답에는 `positive_factors`, `caution_factors`, `counter_view` 등 기존 필드도 이미 생략되어 있어, 이번 PR이 새로 만든 공백은 아닙니다. 다만 `counter_points`도 함께 누락되었으므로, 해당 문서를 다음에 손볼 때 전체 필드를 한 번에 정리하는 편이 좋겠습니다. 이번 PR 범위에서 요구하지는 않습니다.
