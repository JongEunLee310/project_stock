## Review Summary

이 PR은 두 이전 로컬 리뷰의 비차단 후속 소견(PR #249 S1, PR #258 S1)을 한 라운드로 정리합니다. 와이어 계약은 변경되지 않습니다.

**#251 — `_process_asset` 컴프리헨션 부수 효과 분리.** `app/domains/analysis/service.py`의 `new_results` 리스트 컴프리헨션이 `if` 조건 안에서 `save_with_symbol` DB 쓰기를 호출하던 구조를, 명시적 `for` 루프로 풀어 저장 호출과 신규 여부 필터링을 두 단계로 분리했습니다. 동작과 저장 순서·개수는 완전히 동일하며, `new_results` 변수에 타입 어노테이션(`list[NewsAdapterResult]`)이 추가되어 가독성도 개선되었습니다.

**#259 — `/signals/changes` 타임라인 전량 메모리 적재 제거.** `list_recent_changes`가 `list_all_ordered()`로 `asset_signal_snapshots` 전 행을 Python에 올려 인접쌍 파생·UNCHANGED 제외·정렬·limit을 수행하던 구조를, LAG 윈도우 기반 `list_change_rows(since, limit)` 하나의 쿼리로 대체했습니다. 핵심 구조는 두 단계입니다. 먼저 `history` 서브쿼리가 `PARTITION BY asset_id ORDER BY snapshot_date ASC, captured_at ASC, id ASC`로 LAG를 계산해 각 행에 이전 스냅샷의 `signal_type`, `score`, `captured_at`, `id`를 붙입니다. 이어 바깥 쿼리에서 `prev_id IS NULL AND signal_type IS NOT NULL` 또는 `prev_id IS NOT NULL AND signal_type IS DISTINCT FROM prev_signal_type` 조건으로 UNCHANGED 행을 제외하고, `since` 필터·`ORDER BY snapshot_date DESC, captured_at DESC, id DESC`·`LIMIT`을 적용합니다. 서비스 계층은 `SignalChangeRow` 평탄 구조를 받아 공용 헬퍼 `_build_change`로 방향을 분류하고 `SignalChangeTimelineItem`을 조립합니다.

공용 헬퍼 추출 후에도 공개 함수 `build_change`는 `changes_by_asset` 경로에서 그대로 사용됩니다. `_build_change`에 남아 있는 UNCHANGED 분기는 이 경로가 실제로 필요로 하는 코드로(인접쌍이 동일 타입일 때 UNCHANGED를 반환해야 함), 죽은 코드가 아님을 최종 검토에서 확인했습니다.

## Suggestions

**S1. UNCHANGED 제외 테스트가 세 케이스를 하나의 단언 묶음으로 암묵 검증합니다.**

설계 Test/Verification 절은 UNCHANGED 제외 시나리오를 세 가지로 명시합니다: 동일 `signal_type` 연속, `signal_type` 모두 NULL, 첫 스냅샷 NULL 타입. 이 세 경우가 `test_list_change_rows_partitions_assets_and_filters_unchanged` 하나에서 묵시적으로 함께 검증됩니다. 테스트가 틀린 것은 아니지만, 각 케이스가 독립적인 단언으로 분리되어 있지 않아 특정 케이스만 깨진 경우 실패 원인을 즉시 좁히기 어렵습니다. 이번 라운드 내 수정을 요구하지 않으며, 후속에서 케이스별 테스트를 분리하거나 단언에 의도 주석을 붙이는 것을 권장합니다. (비차단)

**S2. `type_coerce`를 `captured_at`에만 적용한 이유가 코드에서 드러나지 않습니다.**

`prev_captured_at`에만 `type_coerce(..., AssetSignalSnapshot.captured_at.type)`를 사용하고 `prev_signal_type`·`prev_score`에는 적용하지 않았습니다. LAG 결과가 `DateTime` 컬럼에 대해 방언에 따라 Python `datetime`으로 역직렬화되지 않는 문제를 방어한 것으로 판단되며 동작은 정확합니다. 다만 "왜 `captured_at`만인가"에 대한 짧은 주석이 없으면 후속 작업자가 누락으로 오해할 여지가 있습니다. 후속 라운드에서 한 줄 주석을 추가하면 충분합니다. (비차단)
