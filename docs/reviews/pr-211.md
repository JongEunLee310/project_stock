## Suggestions

**S1. 동일 키 동시 요청의 stampede 미방어 — 현 호출 규모에서 수용, 기록만 남깁니다.**
동시 요청 N개가 모두 miss로 판정되면 N번의 cloud 호출과 budget 소비가 발생합니다.
캐시 도입 동기가 비용 절감인 만큼, 브리핑 호출량이 늘어 실측에서 중복 호출이 관찰되면
락 또는 single-flight 도입을 검토하는 것을 권고합니다.

**S2. date 버킷·budget 키가 UTC 기준 — KST 09:00에 하루가 바뀝니다.**
기존 `DailyCallBudget`과 일관된 선택이고 stale이 아니라 추가 miss 방향이라 안전하지만,
국내 시장 기준의 "오늘" 경계와 어긋납니다. 운영에서 갱신 경계가 문제로 관찰되면
두 키의 기준 시간대를 함께 조정해야 합니다(캐시만 바꾸면 비일관).

**S3. Redis 연결에 소켓 타임아웃이 없어 hang형 장애 시 지연이 전파될 수 있습니다.**
예외형 장애는 miss로 흡수되지만, 응답 없이 매달리는 장애는 TCP 타임아웃까지 요청이
블로킹됩니다. `get_redis_connection()`을 쓰는 budget·scheduler와 공통 사안이므로
Redis 인프라 성숙 시점(PR #210 S1 원자화와 같은 묶음)에 함께 다루는 것을 권고합니다.
