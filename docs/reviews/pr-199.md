# PR #199 로컬 리뷰 — feat: LLM 분석 실행 route·워커 잡 배선 (BE #198)

## Review Summary

Epic #174의 첫 번째 후속 과제(BE #198)로, 7단계(PR #192)까지 완성돼 있던
`LLMAnalysisService.run_analysis`에 실행 진입점을 배선하는 PR입니다. 새 패턴 없이 기존 선례
세 가지를 그대로 잇습니다. 실행은 `analyze_watchlist_job`과 같은 구조의 RQ 워커 잡
`run_llm_analysis_job`(신규 `app/worker/jobs/llm_analysis.py`)이 맡아 `JobRunService`로
"llm_analysis" 잡 이력을 남기고, 트리거는 기존 `/worker/jobs/*` 형태의
`POST /api/v1/worker/jobs/llm-analysis`가 맡되 기존 두 enqueue route와 달리 `get_current_user`를
필수로 해서 `user_id`를 요청 본문이 아니라 인증 사용자에서 얻습니다(설계 075 Decision RR). 결과
확인은 신규 `GET /api/v1/llm-analysis/runs`(요약 projection)·`/runs/{run_id}`(상세)가 맡고,
repository에 추가된 `list_by_user`·`get_by_id_for_user`가 소유권 필터를 조회 단계에서 적용해 타
사용자 run은 존재 여부 구분 없이 404로 답합니다(Decision SS·TT).

핵심 경계 판단 두 가지가 설계대로 구현됐습니다. 첫째, 서비스가 자체 처리한 실패
(run.status=FAILED)를 잡 래퍼가 삼키지 않고 `JobRun` FAILED로 승격해 `error_message`를
전파합니다(Decision QQ). 둘째, 목록 응답은 `LLMAnalysisRunSummary`로 제한되어 번들 전문
(`input_context_json`)과 출력 원문이 상세 조회에서만 노출됩니다. Protected Files(`model.py`·
`service.py`·어댑터·factory)는 변경되지 않았고, `schema.py`·`repository.py`는 additive 수정만
있으며 마이그레이션도 없습니다. 구현은 Codex가 핸드오프
`.codex/tasks/task-138-llm-analysis-route.md` 기준으로 수행했습니다.

## Suggestions

- **S1. 잡 래퍼 테스트가 서비스 전체를 대체해 잡 경로의 통합 검증은 없습니다.**
  `test_run_llm_analysis_job_*`는 `LLMAnalysisService`를 monkeypatch로 대체해 상태 매핑
  (SUCCEEDED/FAILED/래퍼 예외)만 검증합니다. 실제 서비스-게이트웨이 경로는
  `tests/test_llm_analysis_service.py`(7단계)가 이미 커버하므로 현재 범위에서는 수용
  가능하지만, `LLM_PROVIDER=mock` 기준으로 잡 진입부터 run 영속까지 잇는 통합 테스트 한 건은
  실 워커 도입 시점에 추가할 가치가 있습니다. 후속 판단 사항이며 머지를 막지 않습니다.
- **S2. enqueue 응답과 분석 run 사이에 연결고리가 없습니다.** `JobQueuedResponse`는 RQ
  `job_id`만 반환하고 `LLMAnalysisRun.id`는 잡 실행 후에야 생기므로, 클라이언트는 결과를
  보려면 `/llm-analysis/runs` 목록에서 최신 run을 찾아야 합니다. 기존 enqueue route 선례와
  일관된 형태라 이번 범위에서는 적절하고, FE 연동 단계에서 필요해지면 `JobRun` payload나 응답
  확장으로 해결할 수 있는 후속 과제입니다.

## Questions

- **Q1. enqueue의 task_type 허용 범위를 좁힐 필요가 있는지 확인 부탁드립니다.** 요청 스키마가
  `LLMTaskType` 전체(AGENT 포함)를 받지만, 분석 프롬프트는 7단계 Decision NN에 따라 단일이라
  task_type별 동작 차이가 아직 없습니다. v0.1에서는 계약(enum) 재사용이 자연스러워 문제로 보지
  않지만, task_type별 프롬프트 분기가 후속으로 붙을 때 허용 목록을 함께 재검토하면 좋겠습니다.
