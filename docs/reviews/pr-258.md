# PR #258 로컬 리뷰 — feat: #257 자산별 dominant 시그널 일별 스냅샷·변화 추적

리뷰어: Claude Code (Opus — 교차 모델 독립 리뷰. 구현에 관여하지 않음)

Cross-model 리뷰: 설계·핸드오프는 Claude Code(Opus), 구현은 Codex(gpt-5.5)가 수행했습니다.
이번 라운드는 실험으로 Codex reasoning effort를 기존 medium 대신 **high**로 지정했습니다.

## Review Summary

로드맵 시그널 페이지 재설계 2단계 본체입니다. 자산별 dominant 시그널을 일별 스냅샷
테이블(`asset_signal_snapshots`)에 기록하고, 인접 스냅샷 diff로 변화를 파생합니다.
설계 문서(`docs/designs/257-signal-state-tracking.md`)의 계약을 충실히 따랐습니다.

- **테이블·마이그레이션** — 자산×일 1행, `(asset_id, snapshot_date)` unique,
  `signal_type`·`score` 비정규화, `signal_id`는 `ondelete="SET NULL"`로 시그널 삭제에도
  스냅샷 사실 기록이 보존됩니다. upgrade/downgrade 대칭이며 down_revision이 현재 head
  (`c3d4e5f60060`)에 올바르게 연결됩니다.
- **일별 job** — `snapshot_signal_states_job`이 `collect_prices_job` 패턴(SessionLocal·
  JobRunService start/succeed/fail·finally close)을 따르고, `capture_daily_snapshot`이
  `list_current_by_asset`을 재사용해 dominant 정의 중복 없이 스냅샷합니다. 활성 dominant가
  없는 자산도 null 스냅샷으로 기록해 CLEARED 전이를 포착할 수 있습니다. 같은 날 재실행은
  upsert로 멱등입니다. cron `30 11 * * 1-5`는 마지막 분석 스케줄(`0 9,11`) 이후로 배치됐습니다.
- **변화 파생** — `build_change` 순수 함수가 direction 6종을 설계 규칙표 그대로 구현하고,
  우선순위 rank는 신설 `signal_priority_rank`가 `WATCHLIST_STATUS_PRIORITY`에서 파생합니다
  (하드코딩 없음, 기존 정의 불변). 카테고리 매핑 `SIGNAL_TYPE_CATEGORY`도 FE
  `signalCategories.ts`와 리터럴이 일치합니다.
- **노출 계약 3종** — `view=current` 항목의 `change` 임베드는 `latest_pair_by_asset`
  (ROW_NUMBER ≤ 2) 배치 조회로 N+1 없이 처리합니다. `/changes`·`/summary` 라우트는
  `/{signal_id}`보다 앞에 선언되어 경로 충돌이 없습니다. `view=all` 응답은 불변입니다.
  부수 개선으로 `list_signals_expanded`의 자산 조회가 개별 `get_by_id` 반복에서
  `list_by_ids` 배치로 바뀌어 기존 N+1도 함께 해소됐습니다.

## Suggestions

**S1. `/changes`가 전체 스냅샷을 메모리에 적재합니다**

`list_recent_changes`가 `list_all_ordered()`로 스냅샷 전량을 읽어 Python에서 diff·정렬·limit을
수행합니다. 스냅샷은 자산 수 × 일수로 단조 증가하는 append-only 테이블이라, 운영 기간이
길어지면 이 경로가 무거워집니다. 현재 자산 규모에서는 문제가 없고 로직도 명확하므로 지금
바꿀 필요는 없지만, 후속에서 `since` 기본값을 두거나 window 함수로 인접쌍을 DB에서 계산하는
방식을 검토하면 좋겠습니다. 심각도: 비차단·후속 검토.

**S2. dominant가 없는 자산의 최초 스냅샷이 타임라인에 NEW로 잡힙니다**

`build_change`는 이전 스냅샷이 없으면 무조건 `NEW`를 반환하는데, 최초 스냅샷의
`signal_type`이 null(활성 시그널 없음)인 자산도 `NEW`가 되어 `/changes` 타임라인에
dominant 없는 항목으로 노출됩니다. job 첫 실행일에는 시그널이 없는 자산 전부가 타임라인에
등장하는 노이즈가 생깁니다. `previous is None and latest.signal_type is None`일 때
`UNCHANGED`(또는 null)로 처리하면 첫날 노이즈가 사라집니다. 심각도: 비차단·저비용 개선.

**S3. 동시 기록 시 `upsert_daily`의 IntegrityError 복구가 같은 배치의 선행 flush를 되돌립니다**

충돌 시 `db.rollback()`이 세션 전체를 되돌리므로, 같은 job 루프에서 앞서 flush만 된(커밋 전)
다른 자산의 스냅샷도 함께 사라진 뒤 해당 자산만 재시도됩니다. 이 경로는 같은 날짜에 외부
동시 기록자가 있을 때만 발동하고 현재 job은 단일 스케줄 실행이라 실질 위험은 낮지만, 동시
실행을 허용하게 되면 savepoint(`begin_nested`) 기반으로 바꾸는 편이 안전합니다. 심각도:
비차단·정보성.

## Review Summary

리뷰 소견 중 S2·S3를 반영한 후속 커밋(`cf2f1b2`, 핸드오프 `task-167`)에 대한 확인
리뷰입니다. S1(타임라인 전량 메모리 적재)은 후속 이슈 #259로 분리했습니다.

- **S2 반영** — `build_change`가 "이전 스냅샷 부재 + 현재 dominant 없음"일 때 `NEW` 대신
  `UNCHANGED`를 반환합니다. 타임라인은 UNCHANGED를 제외하므로 job 첫 실행일에 시그널 없는
  자산이 `/signals/changes`에 노출되던 노이즈가 사라집니다. "이전 부재 + 현재 dominant
  있음"은 여전히 `NEW`로, 바뀐 것은 해당 단일 케이스뿐입니다.
- **S3 반영** — `upsert_daily`의 신규 insert가 `begin_nested()` savepoint로 격리됐고 세션
  전체 `rollback()` 호출이 제거됐습니다. unique 충돌 복구가 같은 배치에서 앞서 flush된
  다른 자산의 스냅샷을 되돌리지 않습니다. 복구 불가 시 예외 전파는 기존과 동일합니다.

savepoint 테스트는 `get_by_asset_date`의 stale read를 monkeypatch로 1회 유도해 사전 커밋된
행과의 실제 `IntegrityError`를 발생시키고, 복구 후 선행 자산의 flush 보존과 충돌 자산의
갱신 값을 모두 검증합니다. 유도 방식은 인위적이지만 검증 대상(실 충돌·선행 보존)은
실제 경로입니다.
