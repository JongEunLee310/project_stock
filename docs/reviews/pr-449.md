# PR #449 로컬 리뷰 — feat: RAG 1차 pgvector 인프라·document_chunks 모델 (#439)

## Review Summary

RAG 리서치 에이전트(에픽 #438) 1차의 저장 기반을 추가하는 PR입니다. 커밋은 두 묶음입니다.
하나는 orchestrator가 작성한 결정·설계 문서(ADR-018, 설계 438, 핸드오프)이고, 다른 하나는
Codex가 구현한 인프라·모델·마이그레이션·테스트·CI입니다.

**Part A — 결정과 설계(ADR-018, 설계 438).** ADR-018은 RAG agent를 BE 내부 모듈로 두고
pgvector를 쓰기로 결정합니다. 아울러 이 결정을 다시 열어야 하는 조건을 프로젝트 분리
트리거(T1~T5)와 전용 vector DB 전환 트리거(V1~V4)로 명시합니다. 분리 비용을 낮게 유지하기
위한 경계 규칙(R1~R5)도 둡니다. 설계 438은 1차 범위 전체(모델, 임베딩 job, 어댑터, Q&A API,
Obsidian, 테스트)를 스켈레톤으로 확정합니다. 설계 과정에서 두 가지 코드 사실을 확인해 반영했습니다.
`run_pipeline`이 호출되지 않아 코퍼스 원본을 `raw_news_events`로 잡았고, 테스트 DB가 SQLite라
`postgres` 마커로 분리했습니다.

**Part B — 저장 기반 구현(#439, 설계 438 §1·§2·§7).** `docker-compose.yml`의 postgres 이미지를
`pgvector/pgvector:pg16`으로 바꾸고 의존성 `pgvector`를 추가했습니다. `app/domains/rag/`에
`DocumentChunk`와 enum 두 종(`ChunkSourceType`, `ChunkContentQuality`)이 새로 생겼습니다.
`embedding`(`Vector(1536)`)과 `asset_ids`(`ARRAY(Integer)`)는 `with_variant(JSON, "sqlite")`로
SQLite 테스트를 통과하게 했습니다. HNSW·GIN 인덱스는 `Index(...).ddl_if(dialect="postgresql")`로
Postgres에서만 생성됩니다. 마이그레이션 `c3d4e5f6006f`는 `CREATE EXTENSION IF NOT EXISTS vector`와
테이블, 제약, 인덱스 4개를 만들고, downgrade에서는 테이블만 지웁니다. CI에는 pgvector 서비스
컨테이너를 쓰는 `Verify pgvector` 잡이 추가되어 마이그레이션 왕복과 `pytest -m postgres`를
실행합니다. 기존 `verify` 잡은 바뀌지 않았습니다.

이번 리뷰는 설계 §2.2와의 일치, SQLite·Postgres 양쪽 동작, 기존 데이터 볼륨에 대한 영향,
protected 파일 변경 범위를 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. postgres 마커 skip 로직이 두 곳에 있습니다 — 경미, 후속 정리 권장.**
`tests/conftest.py`의 autouse fixture `skip_postgres_without_url`과 `tests/rag/conftest.py`의
`postgres_db` fixture가 모두 `TEST_POSTGRES_URL`이 없을 때 skip합니다. 동작에는 문제가 없지만
조건이 바뀔 때 한쪽만 고칠 위험이 있습니다. #440에서 `PgVectorStore` 통합 테스트가 `postgres_db`를
재사용할 때, fixture를 `tests/conftest.py` 한 곳으로 옮기고 중복 skip을 없애면 됩니다.

**S2. 모델과 마이그레이션의 `asset_ids` 기본값 표현이 다릅니다 — 경미, 허용.** 마이그레이션은
`server_default='{}'::integer[]`를 두고, 모델은 `default=list`(Python 측)만 둡니다. ORM 경로로만
쓰는 지금은 결과가 같습니다. 다만 나중에 Alembic autogenerate로 비교하면 차이로 잡힐 수 있으니,
다음 rag 마이그레이션을 만들 때 모델에 `server_default`를 맞추는 정도로 충분합니다.

**S3. 배포 환경에도 같은 REINDEX 절차가 필요합니다 — 머지와 별개로 운영 확인 필요.** 배포
compose는 이 repo에 없습니다. 배포 쪽에서 이미지를 바꿀 때 설계 438 §12의 절차를 따르지 않으면,
로컬 복제본에서 확인한 것과 같은 인덱스 손상이 생길 수 있습니다. 배포 설정을 관리하는 쪽에 이
절차를 전달해야 합니다.

## Questions

**Q1. 기존 볼륨 전환 시 인덱스 손상 여부 — 리뷰 중 확인해 해소했습니다.** 원본 볼륨
`project_stock_postgres_data`를 읽기 전용으로 복제한 볼륨에 새 이미지를 붙여 확인했습니다. 기동과
조회는 정상이었지만, `amcheck`의 `bt_index_check` 결과 텍스트 btree 인덱스 32개 중 2개
(`uq_raw_news_events_url`, `ix_fund_flow_outlooks_analysis_version_sector`)가 손상돼 있었습니다.
alpine(musl)에서 만든 `en_US.utf8` 인덱스를 debian(glibc 2.36)에서 읽기 때문입니다.
`REINDEX DATABASE stock_db` 후 손상은 0개가 됐고, 이어서 `alembic upgrade head`가 실데이터에 정상
적용됐습니다(`raw_news_events` 2,703건). 절차는 설계 438 §12에 기록했습니다. 원본 볼륨은 바꾸지
않았습니다.

**Q2. 로컬 원본 볼륨 전환을 언제 할지 — 개발자 판단이 필요합니다.** 머지 후 로컬 compose를
다시 띄우면 새 이미지가 원본 볼륨에 붙습니다. §12 절차(앱 정지, REINDEX, upgrade, 앱 기동)를
개발자가 직접 진행할지, orchestrator가 진행할지 정해 주세요.

## Final Recommendation

머지 가능합니다. 모델의 필드, 타입, nullable, unique 제약, 인덱스 4개가 설계 §2.2와 일치하는지
항목별로 확인했습니다. 범위는 #439에 한정돼 있고 #440~#443의 어댑터·job·API는 들어오지
않았습니다. protected 파일 가운데 `.github/workflows/ci.yml`은 핸드오프가 허용한 새 잡 추가만
있고 기존 잡은 그대로입니다. `docs/decisions/`의 변경은 ADR-018 추가와 색인 한 줄입니다. 추가된
테스트는 SQLite 라운드트립(벡터, 배열, 빈 배열, enum 값), unique 제약, SQLite에서 Postgres 전용
인덱스 생략, Postgres 벡터 라운드트립과 인덱스 정의, 코사인 거리 정렬, `asset_ids` 포함 조건을
덮습니다. Blocking은 없습니다. S1·S2는 후속 정리로 충분하고, S3는 배포 쪽 운영 확인 사항입니다.
Q1은 리뷰 중 해소했고, Q2는 머지 후 로컬 전환 방식에 대한 개발자 판단을 요청합니다.

최종 머지 권한은 개발자에게 있습니다.
