# PR #395 로컬 리뷰 — 자금 흐름 전망을 수치 구간으로 개방 (#393)

## Review Summary

자금 흐름 전망의 금액을 라벨 문자열에서 하한·상한·통화를 갖는 수치 구간으로 바꾼 PR입니다.
커밋은 두 건입니다. 리뷰어가 먼저 작성한 결정 기록
(`docs: ADR-017 자금 흐름 전망을 수치 구간으로 표현`)과 Codex 구현입니다.

**Part A — 결정 기록(ADR-017).** 3차 설계는 확정 예측을 막기 위해 금액을 라벨 문자열로
저장하기로 했고, `fund_flow_outlooks.estimated_range`는 `"+0.8~+1.8조원 가능 범위"` 같은
`str`이 됐습니다. 세부 수정 단계에서 설계 이미지와 대조하며 두 가지가 드러났습니다. 설계의
`예상 자금 흐름`과 `시나리오`는 모두 부호 있는 수치를 전제하는 막대 그래프인데 계약에 그릴
수치가 없었고, 그 결과 화면이 남은 정성 필드를 전부 펼치는 긴 텍스트 카드가 됐습니다.
ADR-017은 **금지 대상이 점 예측이지 구간이 아니라는 구분**을 세워 이 충돌을 해소합니다.
대안 셋(화면만 압축·단일 수치 도입·문자열 병존)을 검토하고 각각을 기각한 근거를 남겼습니다.
설계 문서 §2.1·§2.2·§3.1·§3.2와 서두 와이어 컨벤션 절을 이 결정에 맞춰 갱신했습니다.

**Part B — 계약·모델·마이그레이션 구현(#393).** `FundFlowRange` projection(`low`·`high`·
`currency`)을 새로 정의하고 두 응답에서 공유합니다. 금액은 `Decimal`을 문자열로 직렬화하며,
2차 `InvestorFlowItem.net_value`의 `field_serializer` 방식을 그대로 따릅니다.
`FundFlowOutlookItem.estimated_range: str | None`이 `estimated_flow: FundFlowRange | None`로
교체됐고, `FundFlowScenarioItem`에 `expected_net_flow`가 추가됐습니다. 모델에는 컬럼 세
쌍(`estimated_flow_low`·`_high`·`_currency`, `expected_net_flow_low`·`_high`·`_currency`)이
`Numeric(20, 4)`·`String(10)`으로 들어갔고, 마이그레이션 `c3d4e5f6006e`가 3차 head 위에
스택됐습니다.

이번 리뷰는 ADR 결정과 구현의 일치, 값 없음과 0의 구분, 백필하지 않기로 한 판단의 타당성,
경계 검증의 위치, 배포 순서 위험을 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. 경계 검증이 응답 스키마에 있다 — 현 단계에서는 유일한 지점, 쓰기 경로가 생기면 이동
검토.** `FundFlowRange.validate_bounds`가 `low > high`를 `model_validator`로 막습니다. 응답
모델이므로 DB에 뒤집힌 값이 들어가 있으면 조회가 500으로 실패합니다. 조용히 잘못된 구간을
그리는 것보다는 낫고, 지금은 쓰기 경로가 시드뿐이라 검증을 걸 다른 자리도 없습니다. 실제
공급원이 붙는 #391에서 쓰기 시점 검증(모델 제약 또는 저장 서비스)을 추가하고, 그때 응답 측
검증을 유지할지 함께 판단하면 됩니다. 병합을 막지 않습니다.

**S2. 통화 코드가 자유 문자열이다 — 골격 단계에서 허용.** `currency`는 `String(10)`이고
스키마에서도 `str`입니다. `KRW` 외의 값이나 오타를 막지 않습니다. 현재 공급원이 시드뿐이고
통화가 하나뿐이라 enum으로 좁히는 이득이 작습니다. 다중 통화가 실제로 들어오는 시점에
enum이나 패턴 제약을 넣는 편이 낫습니다.

**S3. 마이그레이션 downgrade가 데이터를 복원하지 않는다 — 의도된 선택, 문서화 필요.**
`downgrade`는 `estimated_range` 컬럼을 다시 만들지만 값은 비어 있습니다. upgrade에서 백필하지
않기로 한 결정(서술 문자열 파싱 금지)의 대칭이므로 일관됩니다. 현재 실데이터가 시드뿐이라
실질 손실도 없습니다. 다만 되돌릴 때 값이 사라진다는 점은 배포 절차에 남겨 두는 편이
안전합니다.

## Questions

**Q1. 값이 없는 구간과 값이 0인 구간이 실제로 구분되는가.** 확인해 해소했습니다. 서비스의
`_fund_flow_range`가 `low`·`high`·`currency` 중 하나라도 `None`이면 `None`을 반환하고, 셋 다
있으면 값이 0이어도 객체를 만듭니다. 추가된 테스트가 이 구분을 정면으로 덮습니다. 한 항목은
`low=0`·`high=0`·`currency="KRW"`로 두어 객체가 나오는지, 다른 항목은 `low=0`·`high=None`으로
두어 `null`로 접히는지 확인합니다.

**Q2. 백필하지 않은 판단이 맞는가.** 확인해 해소했습니다. 기존 값은
`"+0.8~+1.8조원 가능 범위"` 같은 서술 문자열입니다. 이것을 파싱해 수치로 옮기는 것은 이
변경이 금지하려는 행위와 같습니다. 현재 이 테이블의 실데이터는 시드뿐이므로 보존해야 할
운영 데이터도 없습니다. 시드는 같은 의미를 통화 기본 단위 수치로 직접 옮겼습니다(반도체
`800000000000`~`1800000000000`, 2차전지 `-300000000000`~`300000000000`).

**Q3. 배포 순서에 위험이 없는가.** 확인했고 위험이 있어 밝힙니다. 이 마이그레이션은
`estimated_range` 컬럼을 **제거**합니다. 이전 버전 백엔드는 이 컬럼을 모델에서 읽으므로,
마이그레이션만 먼저 적용하면 기존 이미지가 `/fund-flow-outlook`에서 실패합니다. 마이그레이션과
이미지 교체를 함께 진행해야 합니다. 로컬 compose 기준으로는
`docker compose up -d --build backend` 이후 `alembic upgrade head` 순서입니다. PR 본문에도
같은 내용을 적었습니다.

**Q4. 시드의 시나리오 구간이 방향과 어긋나지 않는가.** 확인해 해소했습니다. 낙관은
`1800000000000`~`3000000000000`, 기준은 `800000000000`~`1800000000000`으로 양의 유입이고,
보수는 구간을 `null`로 두었습니다. 낙관의 하한이 기준의 상한과 맞물려 세 시나리오의 관계가
단조롭습니다. 보수를 비운 것은 값이 없는 경우가 계약에서 어떻게 표현되는지 시드로 드러내려는
의도이며, 핸드오프가 요구한 사항입니다.

이번 PR에서 두 문서가 반영됐습니다. `docs/decisions/ADR-017-fund-flow-quantitative-range.md`가
새로 추가됐고, `docs/designs/307-news-intelligence-phase3.md`의 모델 절(§2.1·§2.2), API 절

함께 남겨, 문자열 표기를 기억하는 사람이 배경 없이 되돌리지 않게 했습니다.

ADR은 필요했고 작성했습니다. 기록된 설계 원칙을 바꾸는 변경이며, 대안 셋 중 하나를 고른
결정이기 때문입니다. `docs/decisions/README.md`가 정한 "approach is chosen over alternatives"
기준에 해당합니다.

Failure Record는 불요합니다. 실패한 접근을 사후에 대체한 것이 아니라, 설계 이미지와 계약의
어긋남을 확인하고 결정을 갱신한 계획된 변경입니다. 판단 근거는 ADR-017에 남았습니다.

## Final Recommendation

머지 가능합니다. ADR-017의 결정을 항목별로 확인했습니다. 금액이 하한·상한·통화를 갖는 구간으로
제공되고, 하한은 상한보다 클 수 없으며, 값이 없으면 구간 전체가 `null`이고 반열린 구간이
없습니다. 구간을 대표하는 단일 수치 필드는 만들어지지 않았습니다. 통화 코드가 응답에 함께
실려 화면이 단위를 추측하지 않아도 됩니다.

범위는 지켜졌습니다. 구간을 산출하는 정량 로직은 추가되지 않았고, `weight`·`likelihood`·
`confidence`의 의미도 그대로입니다. 다른 도메인의 금액 표현은 건드리지 않았습니다.
Protected Files는 없으며 diff는 모델·스키마·서비스·시드·마이그레이션·테스트와 두 문서에
한정됩니다.

추가된 테스트가 덮는 것은 세 가지입니다. `/fund-flow-outlook`과 `/topics/{id}/scenarios`
응답에 구간이 실리고 금액이 문자열이며 통화가 함께 오는지, `0~0` 구간과 `null` 구간이
구분되는지, 그리고 모델 수준에서 컬럼 정밀도(`Numeric(20, 4)`)와 nullable 여부, 시드 환산값이
맞는지입니다. `estimated_range` 컬럼이 사라졌다는 사실도 단언에 포함됐습니다. 기존 단언 중
삭제된 것은 없고, `estimated_range`를 확인하던 자리는 새 형식으로 다시 쓰였습니다.

Blocking은 없습니다. S1·S2는 실제 공급원이 붙는 #391 단계에서 판단할 후속 사항이고, S3은
백필하지 않기로 한 결정과 대칭인 의도된 동작입니다. Q1·Q2·Q4는 확인해 해소했고, Q3은 배포
순서 주의사항이라 PR 본문과 이 기록에 함께 남깁니다.

최종 머지 권한은 개발자에게 있습니다.
