# PR #377 로컬 리뷰 — 뉴스 인텔리전스 토픽 상세·추이·근거 계약 (#304)

## Review Summary

뉴스·공시 인텔리전스(에픽 #307) 1차 계약의 마지막 단위로, 토픽 상세 3종 엔드포인트를 추가합니다. #303 브랜치 위에 스택된 PR이며 커밋은 1건입니다. 이 PR이 머지되면 1차 BE 계약(모델 + overview·events·briefing·topic-map·topic-detail)이 완성됩니다.

세 라우트는 `app/api/v1/endpoints/news_insights.py`에 추가됐습니다. `GET /topics/{id}`는 `service.get_topic_detail`로 토픽 헤더·`scores`·`affected_symbols`와 `TopicInsight` 최신 버전 insight(`version`·`counter_arguments` 포함)를 반환하고, `GET /topics/{id}/trend`는 `window`·`interval`(둘 다 `^[1-9]\d*[hd]$`) 기준 구간 집계 points·사건 markers·출처 분포를 반환하며, `GET /topics/{id}/evidence`는 `types`(DocumentType)·`direction`(SentimentDirection) 필터와 cursor pagination으로 근거를 반환합니다. 재사용한 것은 #301에서 추가한 `cursor_paginated`/`encode_datetime_cursor`와 `get_current_user`·`success` 엔벨로프이고, 새로 추가된 것은 상세·추이·근거 projection과 repository/service 로직입니다. 공용 파일 변경은 `app/core/error_codes.py`에 404용 `NEWS_INSIGHT_TOPIC_NOT_FOUND` enum 1건 추가뿐입니다.

이번 리뷰는 설계 §4.5·§4.6·§4.7 계약 일치, 버전 누적·반대 근거 반영, 토픽↔이벤트 연결 가정의 타당성을 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. `app/core/error_codes.py`에 도메인 에러 코드 1건 추가 — 기존 패턴 준수한 additive.** 미존재 토픽 404를 위해 `NEWS_INSIGHT_TOPIC_NOT_FOUND`를 추가했습니다. `REPORT_NOT_FOUND`·`SIGNAL_NOT_FOUND` 등 기존 도메인 not-found 코드와 동일한 패턴이며 기존 코드에 영향이 없습니다. 후속 조치는 불필요합니다.

**S2. 라우트 등록 순서 — `/topics/map`이 `/topics/{topic_id}`보다 먼저 등록돼 충돌 없음.** `/topics/map`(#303)이 리터럴 경로로 먼저 등록돼 있어 `GET /topics/map` 요청이 `{topic_id}` 라우트로 잘못 매칭되지 않습니다(설령 순서가 바뀌어도 `topic_id: int` 파싱 실패로 방어되지만, 현재 순서가 정상). 확인만 남기며 조치는 불필요합니다.

## Questions

**Q1. 토픽↔이벤트 연결 정본 — `TopicInsight.key_evidence` 사용 가정.** #305 모델에 topic-event join 테이블이 없어, `/evidence`·추이 marker의 토픽 관련 이벤트를 `TopicInsight.key_evidence`의 event_id로 해석했습니다. 1차 seed 계약에서는 타당하나, 2차 실클러스터링 도입 시 topic-event 연결을 명시 테이블 또는 `extracted_events`의 토픽 참조로 구체화할지 결정이 필요합니다. 리뷰 중 확인한 결과 seed·테스트는 이 가정 위에서 일관되게 동작하며, 설계 계약(§4.5~§4.7)과도 배치되지 않습니다. 2차 설계 시점의 판단 사항으로 남깁니다.

**Q2. Stacked PR 머지 순서.** base는 `feat/303-news-insights-topic-map`(#376)이고 그 아래로 #375·#374까지 4단계 스택입니다. 머지는 #374 → #375 → #376 → #377 순서로 하고, 하위 PR이 dev에 머지될 때마다 상위 PR base를 retarget해야 합니다. 코드 판단이 아니라 머지 순서 확인 사항입니다.

## Final Recommendation

머지 가능합니다(단, Q2의 머지 순서·base retarget 조건). 설계 §4.5의 상세(scores·affected_symbols·최신 버전 insight·counter_arguments), §4.6의 추이(points·markers·source_distribution), §4.7의 근거(evidence_role·cursor pagination·types/direction 필터)가 구현과 일치함을 항목별로 확인했습니다. 미존재 토픽 404가 표준 에러 코드로 처리됩니다. 범위는 토픽 상세 3종으로 지켜졌고 `/graph`·`/symbols`·`/scenarios`·`/explanation`은 2·3차로 남겼습니다. Protected Files 변경은 없으며 core 변경은 error 코드 1건뿐입니다. 추가된 테스트는 상세 응답·추이 구조·근거 cursor·404를 덮습니다. Blocking은 없고, Suggestions(S1·S2)는 기존 패턴 준수 additive와 라우트 순서 확인이며, Questions(Q1은 2차 설계 판단, Q2는 머지 순서)는 확인으로 정리됩니다.
