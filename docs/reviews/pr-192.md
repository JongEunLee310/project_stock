## Review Summary

Epic 7단계로, ContextBuilder가 만든 `LLMContextBundle`을 `LLMGateway`에 태워 분석을 실행하고
입력·출력을 재현 가능하게 영속하는 오케스트레이션을 신설한 PR입니다. LLM 어댑터 스택(밀스톤 #4)과
`llm_analysis` 데이터 계약·마이그레이션(1단계 #175)은 재사용했고, 신규 실체는
`repository.py`·`service.py`·번들→CloudSafe projection·분석 프롬프트로 한정됩니다(설계 Decision KK).

`LLMAnalysisService.run_analysis`는 번들을 조립해 `input_context_json`을 담은 PENDING run으로 먼저
영속한 뒤, projection을 게이트웨이에 태우고 응답을 `LLMAnalysisResult`로 파싱해 `output_json`·
status=SUCCEEDED로 갱신합니다. 게이트웨이 호출·파싱 실패는 삼키지 않고 status=FAILED·
`error_message`로 기록하며, 이때 입력은 이미 영속돼 있어 실패도 추적 가능합니다(Decision MM·OO).

경계 처리가 이 PR의 핵심입니다. `LLMContextBundle`은 개인 원가(`avg_buy_price`) 등 SEMI 정보를
포함해 cloud에 직접 태울 수 없습니다. `to_context_bundle_snapshot`이 `avg_buy_price`를 제거하고
`holding`·`weight`·`unrealized_return`만 남긴 `AGGREGATED` projection(`ContextBundleSnapshot`)으로
변환해 기존 `PrivacyGate`(cloud는 `AGGREGATED`·`PUBLIC`만 허용)를 그대로 통과시킵니다. `PrivacyGate`
와 기존 CloudSafe snapshot은 손대지 않은 additive 변경이라 경계·아키텍처가 바뀌지 않습니다
(Decision LL). 전체 번들은 `input_context_json`으로 로컬 DB에만 남아 재현성을 확보합니다.

## Suggestions

- **S1 · 응답 provider·model_name 미기록**: 현재 `mark_succeeded`에 `model_name=None`·`provider=None`
  을 넘깁니다. 게이트웨이 `complete_json`이 JSON 본문만 반환하고 응답 메타(`LLMResponse`의 provider·
  model)를 돌려주지 않는 구조라 불가피한 선택입니다. §3.5는 `model_name`을 추적 대상으로 명시하므로,
  cloud 실호출을 붙이는 후속 단계에서 게이트웨이가 provider·model을 함께 반환하도록 확장하고 이
  필드들을 채우는 것을 권합니다. 최소한 라우터가 해석한 provider(`"cloud"`)는 지금도 기록 가능한
  값이라, 관측성 측면에서 우선 채워두는 것도 방법입니다.
- **S2 · 광범위 예외 포착**: `run_analysis`가 `except Exception`으로 게이트웨이·파싱 실패를 한데
  잡아 status=FAILED로 기록합니다. 시스템 경계에서 실패를 추적 가능한 상태로 남기는 의도에는
  부합하나, 프로그래밍 오류(예: `AttributeError`)까지 삼켜 FAILED로 기록될 수 있습니다. 후속에서
  게이트웨이 계열 예외(`LLMCallError`·`LLMTimeoutError`·`CloudBoundaryViolationError`)와 검증
  오류(`ValidationError`)로 포착 범위를 좁히는 것을 고려할 만합니다. 현재 범위에서는 문제가 아닙니다.
- **S3 · projection 모델 다수 신설**: 번들 구조를 CloudSafe로 옮기며 projection 하위 모델
  (`ContextBundle*Projection`)이 여러 개 추가됐습니다. 계약(`llm_context/schema.py`)과 필드가
  대부분 겹쳐 표면이 다소 큽니다. 다만 CloudSafe 경계는 계약과 독립적으로 진화해야 하고(원가 제거가
  그 예), `from_attributes` 기반 변환이라 결합을 낮춘 선택이라 수용 가능합니다. 향후 필드가 늘면
  projection과 계약의 동기화 지점을 문서로 명시해 두는 것을 권합니다.
