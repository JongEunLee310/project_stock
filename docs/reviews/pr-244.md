## Review Summary

관심종목 분석 파이프라인(`analyze_watchlist_job`)에 실행 트리거 3종을 연결해 관심종목
추가부터 시그널·리포트 생성까지의 체인을 완성하는 PR입니다.

**추가 시 자동 큐잉** — `app/api/v1/endpoints/watchlists.py`의 `add_watchlist_item` 핸들러가
`WatchlistService.add_item` 성공 후 `enqueue_watchlist_analysis_safe(watchlist_id)`를
호출합니다. 이 함수는 `app/worker/jobs/analysis.py`에 신규 추가된 것으로, `Queue.enqueue`
중 `Exception`이 발생하면 `logger.warning`으로 기록하고 예외를 억제합니다. 결과적으로
Redis 장애가 발생해도 종목 추가 응답(HTTP 201)은 영향을 받지 않습니다.

**세션 밴드 스케줄** — `analyze_all_watchlists_job`이 신규 추가되었습니다. DB에서 모든
watchlist id를 조회한 뒤 각 id에 대해 `WatchlistAnalysisService.run`을 순차 실행하며,
잡 전체를 단일 JobRun(`"all_watchlists_analysis"`)으로 추적합니다. watchlist 단위 예외는
`db.rollback()` 후 `failures` 목록에 기록하고 다음 watchlist로 진행하는 방식으로, 기존
`analyze_watchlist_job`의 종목 단위 격리 패턴과 구조가 일치합니다. 이 잡은
`app/scheduler/registry.py`에 4개의 `ScheduleDefinition`으로 등록됩니다. 모두
`enabled=settings.ANALYSIS_SCHEDULE_ENABLED`를 참조하므로 플래그 하나로 4개가 함께
제어됩니다.

**수동 트리거 정비** — `app/api/v1/endpoints/worker.py`의 `enqueue_analysis_job`에
`current_user: User = Depends(get_current_user)` 의존성이 추가되어 미인증 요청은 401을
반환합니다. 인증된 요청에는 `connection.set(rate_limit_key, "1", nx=True, ex=60)` SET
NX+EX 원자 연산으로 rate limit을 적용합니다. 키가 이미 존재하면 `AppException`으로
HTTP 429 + `Retry-After: 60` + `RATE_LIMIT_EXCEEDED` 에러 코드를 반환합니다.
`AppException`은 `headers: dict[str, str] | None` 파라미터를 지원하고
`app_exception_handler`에서 `_response_headers`를 거쳐 응답 헤더에 포함됩니다.

핸드오프 Expected Output에 없던 `.env.example` 항목(`ANALYSIS_SCHEDULE_ENABLED=false`)이
추가되었습니다. 새로운 env 변수를 문서화하는 자연스러운 처리로, 타당한 판단입니다.

## Suggestions

**S1. rate limit 키 스킴 픽스처에 출처 주석 없음**

`tests/test_worker_jobs.py`의 `test_enqueue_analysis_job_api`에서 FakeRedis가
`"rate_limit:analysis_manual:42"`를 `assert`로 검증하고 있습니다. 이 문자열은
설계 문서(`docs/designs/243-analysis-triggers.md` rate_limit Redis 키 스킴 절)에서
"가정"으로 표기된 계약 값인데, 구현 후 확정된 이 시점에서도 픽스처에 출처 주석이 없습니다.
`quality-process-policy.md`의 Real-Contract Fixtures 규율에 따르면 계약 값에는
출처를 주석으로 남겨야 합니다. 다른 테스트(cron 리터럴)와 일관성도 맞지 않습니다.

`# Source: app/api/v1/endpoints/worker.py rate_limit_key` 형태의 주석을 해당 assert
근처에 추가하면 됩니다. 심각도: 비차단·권장.

**S2. `ANALYSIS_SCHEDULE_ENABLED` env 변경 후 재시작 필요 여부를 문서에 명시**

`app/scheduler/registry.py`의 `default_scheduler_registry`는 모듈 레벨에서 생성되고,
`enabled=settings.ANALYSIS_SCHEDULE_ENABLED`는 임포트 시점에 단 한 번 평가됩니다.
따라서 프로세스 재시작 없이 env를 바꿔도 분석 스케줄 활성화 상태는 변하지 않습니다.
`cron_config.py` 역시 모듈 임포트 시 `_register_cron_jobs()`를 실행하므로 같은
제약이 적용됩니다.

이 동작은 핸드오프 Background에서 암묵적으로 언급되었고 `cron_config.py`의 기존 동작과
동일합니다. 다만 `docs/knowledge/product-workflow.md` 스케줄러 섹션에 "활성화 상태를
바꾸려면 프로세스 재시작이 필요하다"는 한 줄을 추가하면 운영 실수를 예방할 수 있습니다.
심각도: 비차단·권장.

## Questions

**Q1. watchlist ID 조회 실패 시 JobRun 미기록 — 의도된 동작인지 확인 요청**

`analyze_all_watchlists_job`에서 `watchlist_ids = list(db.scalars(...))` 조회가 예외를
던지면, `job_run_id`가 `None` 상태이므로 외부 `except Exception` 블록에서
`job_run_service.fail`을 건너뜁니다. 즉, DB 조회 자체가 실패하면 JobRun이 전혀 생성되지
않고 해당 잡 실패가 추적되지 않습니다.

이 동작은 기존 `analyze_watchlist_job`에서도 동일하게 나타납니다. `job_run_service.start`
전에 실패하면 JobRun이 없는 채로 예외가 상위로 전파됩니다. 기존 패턴과 일치하므로
의도된 설계일 가능성이 높지만, `analyze_all_watchlists_job`은 DB 조회가 선행 단계이기
때문에 `analyze_watchlist_job`보다 이 경로에 해당하는 빈도가 상대적으로 높습니다.
기존 패턴 유지로 확정된 것인지 확인 요청드립니다.
