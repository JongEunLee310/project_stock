FE 빠른 감시 설정 패널(`project_stock_frontend#120`)의 BE 계약 Phase 1을 구현하는 PR입니다.
신규 테이블 `watchlist_alert_rules`, 레포지토리·서비스·스키마 클래스, 그리고 엔드포인트 2개

핵심 구조는 기존 watchlist child endpoint 패턴(`/evaluations`, `/observations` 선례)을 그대로
따릅니다. `WatchlistAlertRuleService`는 `(db: Session)` 주입 방식으로 `WatchlistRepository`와
`WatchlistAlertRuleRepository`를 보유하며, 처리 순서는 소유권 검증 → 레포지토리 조작 → 4종
전체 상태 반환입니다. 소유권 검증은 `evaluations_service.py:144` 패턴과 동일하게 404 선행·403
후행 순서를 유지합니다. `GET`은 DB 행이 없는 템플릿도 포함해 항상 4종을 반환하고,
`PUT`은 요청에 포함된 템플릿만 upsert하되 미포함 템플릿의 현재 상태를 보존합니다.

`apply_templates` 안에서 리스트 컴프리헨션으로 모든 템플릿의 유효성을 선검증한 뒤 upsert 루프를
돌기 때문에, 무효 `template_type`이 하나라도 있으면 어떤 upsert도 실행되지 않습니다. 이 원자적
검증 패턴은 `test_apply_templates_validates_all_templates_before_upsert`가 정확히 검증합니다.

`WatchlistAlertRuleRepository.upsert_template`은 SELECT-INSERT-catch 패턴을 사용합니다. 행이
없으면 INSERT를 시도하고, 동시 삽입으로 `IntegrityError`가 발생하면 rollback 후 행을 재조회해
`is_active`만 갱신합니다. 이 흐름은 `test_apply_templates_updates_duplicate_template_without_unique_violation`
에서 동일 템플릿 연속 호출 시나리오로 검증됩니다.

Phase 2 범위(스냅샷 저장·Signal 생성·스케줄러)는 일절 침범하지 않습니다. `'DTO'` 용어도 없으며,
신규 Pydantic 타입은 모두 `Projection` 또는 `BulkRequest` 접미사를 사용합니다.

## Suggestions

**S1. 단일 PUT 요청 내 동일 `template_type` 중복 입력 동작이 명시적으로 테스트되지 않았습니다.**

`apply_templates` 루프는 `data.templates`를 순서대로 순회해 `upsert_template`을 호출하므로,
동일 `template_type`이 두 번 등장하면 첫 번째 값으로 INSERT 또는 UPDATE가 완료된 뒤 두 번째
값으로 다시 UPDATE됩니다. 결과적으로 마지막 값이 적용되는 동작입니다. 이 동작 자체에는 정합성
문제가 없으나, 설계 문서와 핸드오프 어디에도 중복 입력 처리 방식이 명시되어 있지 않습니다.
현재 머지를 막지 않으며, 후속 PR이나 코드 주석에서 이 동작을 명확히 하면 계약이 더 견고해집니다.

**S2. `upsert_template`의 SELECT-INSERT-catch 패턴은 고빈도 동시 쓰기에 제한이 있습니다.**

현재 구현은 핸드오프가 제안한 `IntegrityError` catch-update 방식을 정확히 따르고 있으며, 테스트
환경(SQLite 직렬 쓰기)과 현재 규모에서는 충분합니다. 운영 DB가 PostgreSQL이고 동시 PUT 요청이
많아지는 경우, `INSERT ... ON CONFLICT DO UPDATE` (SQLAlchemy `dialect_kwargs`)로 교체하면
DB 수준에서 원자성이 보장됩니다. 지금 단계에서 머지를 막지 않으며, 부하 증가 시 후속 PR에서
검토할 것을 권장합니다.

## Final Recommendation

**머지해도 좋다고 판단합니다.** Blocking 항목이 없습니다.

정확성 핵심 항목을 모두 충족합니다. `GET`은 DB 행이 없는 템플릿도 `is_active=False`로 포함해
4종을 반환하고, `PUT`은 요청 외 템플릿 상태를 보존합니다. 소유권 검증은 404 선행·403 후행 순서로
구현되어 있으며, 무효 `template_type`은 서비스 레이어에서 AppException 422로 처리됩니다. 유효성
검사가 upsert 전에 일괄 실행되어 부분 적용 없이 요청 전체를 거부합니다.

마이그레이션 체인은 `down_revision = "c3d4e5f60059"`로 정확히 연결되어 있으며, 단일 head가
확인됩니다. UniqueConstraint `uq_watchlist_alert_rules_template`과 `ix_watchlist_alert_rules_watchlist_id`
인덱스가 모델과 일치하고, downgrade는 인덱스 삭제 후 테이블 삭제 순서를 올바르게 따릅니다.

Phase 2 범위(watchlist_evaluation_snapshots·Signal 생성)는 코드 어디에도 침범하지 않습니다.
기존 `/evaluations`, `/observations`, `/recommendations`, `/sparklines`, `/summary` 계약에는

S1·S2는 후속 PR 또는 운영 관찰 수준의 사항으로, 현재 머지를 막지 않습니다.
