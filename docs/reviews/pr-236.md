# PR #236 로컬 리뷰 — feat: 관심종목 항목별 평가 배지 API — LLM 평가 4종과 집계

리뷰어: value-for-fable (Sonnet — VFF 위임)

Cross-model 리뷰: 구현자는 Codex (GPT-5, medium), 리뷰어는 Sonnet(VFF). 구현에 관여하지 않은 독립 모델 시점이 확보되어 있습니다.

## Review Summary

FE 관심종목 페이지(`project_stock_frontend#117`) Phase 3을 위해 `GET /api/v1/watchlists/{watchlist_id}/evaluations` 엔드포인트를 신설하는 PR입니다.

구조는 observations·recommendations 선례를 그대로 따릅니다. `WatchlistEvaluationsService`는 `(db: Session, gateway: LLMGateway)` 주입 패턴을 사용하며, 소유 확인 → snapshot 구성 → `LLMGateway.complete_json` 단일 배치 호출 → projection 생성 순서로 처리합니다. observations_service와 달리 `WatchlistService(db)` 전체를 인스턴스화하지 않고 `_get_owned_watchlist`를 자체 구현했는데, 이는 PR #235 S2에서 지적한 과도한 의존성 문제를 이번 서비스에서 자연스럽게 피한 설계입니다.

평가 enum 4종(`NewsRisk`, `ValuationBurden`, `ThemeHeat`, `AiJudgment`)은 `app/domains/watchlists/types.py`에 독립 파일로 정의되고, LLM 응답에서 오는 자유 문자열은 내부 클래스 `_ValidatedEvaluation`을 통해 enum으로 변환됩니다. symbol hallucination 필터(`_project_items`)는 snapshot에 없는 symbol과 중복 symbol을 모두 제거합니다. 집계 2종은 `projected_items` 기준으로 코드에서 직접 산출되며 LLM 판단에 위임하지 않습니다.

`WATCHLIST_EVALUATION` 태스크는 `WATCHLIST_NOTE`와 동일하게 `launch="cloud", future_primary="local"`로 라우팅됩니다. `WatchlistEvaluationSnapshot.sensitivity`는 `SensitivityLevel.AGGREGATED`이며, 필드는 symbol·status·per·peg·daily_change_percent로 포지션 크기·비용 등 개인 식별 민감 정보를 포함하지 않습니다.

응답 클래스는 `WatchlistItemEvaluationProjection`, `WatchlistEvaluationsResponse`로 명명되어 'DTO' 금지 규칙을 준수합니다.

PR #235 S1 후속으로 스파크라인 404 제외 분기 테스트 2개가 `tests/test_watchlist_sparklines.py`에 추가되었습니다. `PRICE_SERIES_NOT_FOUND` AppException 제외 케이스와 다른 error_code 404 재발생 케이스를 각각 관통하며, `ErrorCode` 출처 주석도 명시되어 있습니다.

## Blocking

None.

## Suggestions

**S1. enum 외 값 반환 시 `ValidationError`가 전체 요청을 실패시킵니다.**

`_project_items`에서 `_ValidatedEvaluation.model_validate(item.model_dump())`를 호출할 때, LLM이 enum에 정의되지 않은 값(예: `"high"` 소문자, `"UNKNOWN"`)을 반환하면 Pydantic `ValidationError`가 잡히지 않고 전파되어 전체 `generate` 호출이 500 오류로 실패합니다. `ItemEvaluationResult`의 필드가 `str` 타입이어서 `WatchlistEvaluationsResult.model_validate`는 항상 통과하지만, `_ValidatedEvaluation` 변환 단계에서 실패합니다. 현재 프롬프트가 허용 값을 명시하고 있으며 관련 선례(observations)도 별도 enum 검증 없이 자유 문자열을 그대로 사용합니다. 따라서 지금 당장 머지를 막지는 않으나, 허용하지 않는 enum 값이 들어올 때 해당 항목만 스킵하는 방어 처리를 후속 PR에서 검토할 것을 권장합니다. 설계 문서는 "enum 검증"의 실패 처리 방식을 명시하지 않아 현재 구현을 규격 위반으로 볼 수 없으므로 Suggestion으로 분류합니다.

**S2. `app/adapters/llm/mock.py`의 `WatchlistEvaluationsResult` 픽스처에 enum 출처 주석이 없습니다.**

테스트 파일 `tests/test_watchlist_evaluations.py`에는 `# Enum values are sourced from app/domains/watchlists/types.py.` 주석이 있어 quality-process-policy.md Real-Contract Fixtures 요건을 충족합니다. 반면 `mock.py`의 LLM mock 응답 딕셔너리(`"news_risk": "LOW"` 등)에는 동일한 출처 주석이 없습니다. `mock.py`는 테스트 픽스처가 아닌 LLM mock provider이므로 엄밀히 요건의 적용 대상인지 해석 여지가 있으나, 동일한 리터럴 값을 담고 있는 만큼 한 줄 주석을 추가하는 것이 일관성을 높입니다. 현재 범위에서 머지를 막지 않습니다.

## Questions

**Q1. `cash_relevance_avg`와 `needs_research_count` 집계 분모가 `projected_items` 수 기준입니다.**

LLM 출력에서 snapshot에 있는 symbol만 포함한 `projected_items`를 분모로 사용하므로, LLM이 snapshot 항목 일부를 누락했을 때 해당 종목이 집계에서도 제외됩니다. 핸드오프에서 분모를 "전체 결과 항목 수"로 정의했으므로 현재 구현은 그 표현에 부합하지만, snapshot 기준(원래 관심종목 수)과 LLM 결과 기준 중 어느 것이 제품 의도에 더 가까운지 확인이 필요합니다. 정의 변경이 필요하다면 서비스 레이어 집계 로직만 교체하면 됩니다.

GitHub Actions 결과는 PR에서 별도 확인이 필요합니다.

## Documentation Impact

`docs/designs/234-watchlist-evaluations.md`가 PR에 포함되어 Status가 `Implemented`로 갱신되었습니다. 별도의 ADR은 필요하지 않습니다. 온디맨드 LLM + 게이트웨이 캐시 방식은 observations·recommendations 선례와 동일하고, child endpoint 패턴도 `/sparklines` 선례가 있습니다. Failure Record도 필요하지 않습니다.

## Final Recommendation

**머지해도 좋다고 판단합니다.** Blocking 항목이 없습니다.

정확성 핵심 항목을 모두 충족했습니다. `_ValidatedEvaluation`을 통한 서비스 레이어 enum 검증이 이루어지고, snapshot에 없는 symbol은 `_project_items`에서 필터링됩니다. `needs_research_count` 기준(`news_risk is NewsRisk.HIGH or ai_judgment is AiJudgment.RISK_INCREASING`)과 `cash_relevance_avg` 기준(`ai_judgment is AiJudgment.WATCH` 비율)이 설계 문서와 일치하며 enum singleton `is` 비교로 안전하게 처리됩니다. 빈 관심종목은 LLM 호출 없이 즉시 0값으로 반환됩니다. `WatchlistEvaluationSnapshot`은 `SensitivityLevel.AGGREGATED` privacy 경계를 올바르게 유지합니다. `WATCHLIST_EVALUATION` 라우팅은 `WATCHLIST_NOTE`와 동일한 패턴을 따릅니다. 기존 `/observations`, `/recommendations`, `/sparklines`, `/summary` 계약에는 변경이 없습니다.

S1은 LLM hallucination 발생 시 가용성 영향을 주는 방어 처리 부재이며 후속 PR에서 보완을 권장합니다. S2와 Q1은 현 범위에서 머지를 막지 않는 수준의 관찰 사항입니다.

최종 머지 권한은 개발자에게 있습니다.

### Confirmed (개정분 검증 항목)

**portfolio_id 소유권 검증**: `_build_buy_readiness`는 `PortfolioService(self.db).get_summary(resolved_portfolio_id, user_id)`를 호출합니다. `PortfolioService.get_summary` 첫 줄이 `self._get_owned_portfolio(portfolio_id, user_id)`로 소유권을 검증하므로, 타 사용자의 portfolio_id가 전달되면 403이 발생합니다. 별도 소유 검증이 필요하지 않다는 설계(R1-3)가 코드에서 정확히 구현되어 있습니다.

**null 경로**: `portfolio_id` 미제공 시 `self.portfolio_repo.list_by_user(user_id, limit=1)`이 빈 목록을 반환하면 즉시 `None`을 반환합니다. 테스트(`test_get_watchlist_summary_counts_total_and_active_risk_assets`, `test_get_watchlist_summary_returns_empty_values_for_empty_watchlist`)가 이 경로를 관통하며 `buy_readiness: None`을 단언합니다.

**레벨 경계값 판정**: `_buy_readiness_level`이 `>= CASH_FLOOR_MEDIUM → SUFFICIENT`, `>= CASH_FLOOR_HIGH → LIMITED`, 나머지 → `RESTRICTED` 순서로 평가합니다. `CASH_FLOOR_HIGH`·`CASH_FLOOR_MEDIUM` 상수를 `app/domains/portfolios/service.py`에서 직접 import하여 매직 넘버가 없습니다. 경계값 파라미터 테스트 5종(0.20/0.15/0.14/0.05/0.04)이 모두 `Decimal` 타입과 상수 import로 작성되어 설계(R1-1 레벨 판정 표) 기준과 정확히 일치합니다.

**BUY_CANDIDATE 집계 범위**: `_build_buy_readiness`에 전달되는 `asset_ids`는 `item_repo.list_by_watchlist(watchlist.id)`에서 추출한 관심종목 항목 기준입니다(`service.py:192`). 포트폴리오 포지션이 아니라 관심종목 asset_ids로 한정되어 있습니다.

**기존 테스트 약화 없음**: `cash_relevance_avg` 검증 지점 4개(`test_watchlist_evaluations_service_maps_gateway_result_and_snapshot`, `test_watchlist_evaluations_service_aggregates_research_count`, `test_watchlist_evaluations_service_returns_zero_aggregates_for_empty_watchlist`, `test_watchlist_evaluations_endpoint_returns_enveloped_mock_response`)가 모두 `"cash_relevance_avg" not in result.model_dump()` 또는 `"cash_relevance_avg" not in data` 형태로 갱신되었으며, 다른 단언은 그대로 유지됩니다.

### Suggestions

**S-R1-1. `seen_symbols` 업데이트 위치와 누락 심볼 집계의 미묘한 분리 (논블로커)**

`_project_items`에서 `seen_symbols.add(item.symbol)`이 `try` 블록 **앞**에서 실행됩니다. enum 검증 실패로 스킵된 항목도 `seen_symbols`에 추가되므로, 루프 이후의 `missing_symbols = snapshot_symbols - seen_symbols` 계산에서 enum 실패 항목은 "LLM이 완전히 누락한 심볼"로 집계되지 않습니다. 두 로그("Skipping invalid...": enum 실패, "LLM watchlist evaluation omitted...": LLM 미반환)가 서로 다른 실패 모드를 커버한다는 점에서 의미상 분리는 합리적입니다. 다만 설계 문서 R1-4는 "LLM이 snapshot 항목을 누락했을 때"만 서술하며 enum 실패 항목의 분류 기준을 명시하지 않습니다. 현재 동작이 올바른 이유를 코드 주석 한 줄로 남기면 후속 유지보수자가 혼동하지 않을 것입니다.

**S-R1-2. `test_get_watchlist_summary_uses_first_portfolio_when_id_omitted`의 `assert first["id"] == 1` (논블로커)**

첫 번째 포트폴리오가 id=1임을 단언하고 있는데, 이는 DB auto-increment가 테스트 간에 리셋된다는 가정에 의존합니다. 현재 CI는 통과하지만, 다른 픽스처가 포트폴리오를 먼저 생성하는 경우 이 단언이 깨질 수 있습니다. 실제로 검증하려는 동작은 "portfolio_id를 지정하지 않으면 id 오름차순 첫 번째 포트폴리오가 선택된다"이므로, `first["id"] < second["id"]`와 같이 두 포트폴리오 간의 상대적 관계를 단언하는 것이 더 견고합니다.

**S-R1-3. `/summary` 응답 성능 변화 모니터링 권장 (논블로커)**

`PortfolioService.get_summary`는 시장 데이터를 조회합니다. 포트폴리오가 등록된 사용자가 `/summary`를 호출할 때마다 시장 데이터 호출이 발생하게 되어 이전 대비 응답 시간이 늘어납니다. 핸드오프 Risk 절에 인지되어 있으며 블로커가 아닙니다. 다만 기존 FE 대시보드 등 `/summary`의 기존 소비자가 이 지연 증가를 감지할 수 있으므로, 첫 릴리스 후 p99 응답 시간을 모니터링하는 것을 권장합니다.
