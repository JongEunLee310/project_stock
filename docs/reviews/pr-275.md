## Suggestions

**S1. `_collected_axis` 내 `item_count == 0` 분기의 가드 의존**

`service.py`의 `_collected_axis` 메서드는 `item_count == 0`이면 `_not_collected_axis`를 호출하는 방어 분기를 포함합니다. 집계 SELECT에서 COUNT가 0을 반환하면 MAX도 None을 반환하므로 실제로 이 분기가 발동될 수 있는 상황은 없습니다(COUNT=0이면 최상위 호출자인 `get_coverage`가 해당 행을 만들지 않는다고 오해할 수 있음). 그러나 현재 코드에서는 `_news_coverage`와 `_price_coverage`가 `item_count`를 직접 반환하고, `get_coverage`가 이를 무조건 `_collected_axis`에 넘기므로 COUNT=0인 자산에서도 이 분기가 정상 경로가 됩니다. 방어 코드 자체는 올바르게 동작하므로 차단 사항은 아니지만, 의도가 이 경로가 실제 발동 경로임을 명시하는 주석을 달거나 `get_coverage` 측에서 `item_count > 0` 여부로 분기를 올리는 것이 호출 흐름을 더 명확하게 합니다. 심각도: 비차단·가독성 개선.

**S2. 단일 템플릿 커버리지 테스트 자산 수**

`test_get_research_summary_returns_structured_fields_for_all_templates`는 자산 2개로 2개 템플릿을 모두 순회합니다. 현재는 2개 템플릿이므로 충분하지만, 이후 템플릿을 추가하면 테스트가 새 템플릿을 무음으로 건너뜁니다. 후속 템플릿 추가 시 자산 수를 `len(_SUMMARY_TEMPLATES)`에 연동하는 방식으로 갱신할 것을 권장합니다. 심각도: 비차단·후속 고려.

## Questions

**Q1. `last_collected_at` 시맨틱 — `created_at` vs 실수집 시각**

`last_collected_at`은 `news_items.created_at`의 MAX를 사용합니다. `TimestampMixin.created_at`은 `server_default=func.now()`로 DB 삽입 시각을 기록하므로, 실수집 파이프라인에서 외부 API 응답의 원 게시 시각과 삽입 시각이 일치한다는 전제가 있어야 합니다. 테스트 픽스처는 `created_at`을 명시적으로 지정해 이 점을 우회하고 있는데, 실제 파이프라인에서도 `created_at`이 수집 완료 시각을 의미하는지 확인이 필요합니다. 설계 문서("해당 축 데이터의 마지막 수집 시각")와는 일치하지만, 후속 실수집 구현 시 `published_at`이 아닌 `created_at`을 사용함을 명시하는 주석을 서비스 레이어에 추가하면 혼동을 방지할 수 있습니다. 심각도: 비차단·설계 확인 요청.
