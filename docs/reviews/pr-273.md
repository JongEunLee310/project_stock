## Review Summary

`GET /api/v1/assets/{asset_id}/news-disclosure` 엔드포인트를 신설해 뉴스(`news_items`)와 공시(mock `DisclosureProvider`)를 `news`·`disclosures` 두 배열로 분리해 반환합니다. 이슈 #268의 설계 문서 범위를 14파일 402줄로 구현했습니다 — 앱 파일 9개, 테스트 4개, 마이그레이션 1개.

변경의 핵심 흐름은 다음과 같습니다. `assets.py` 라우터가 `AssetRepository.get_by_id()`로 자산 존재를 확인하고 symbol을 확보한 뒤 `NewsDisclosureService.get_news_and_disclosures()`에 위임합니다. 서비스는 `NewsItemRepository.list_by_asset_with_limit()`(DB)과 `DisclosureProvider.fetch()`(mock)를 각각 호출해 두 배열을 조립합니다. 공시 배열은 서비스 내에서 `published_at DESC`로 정렬한 뒤 `limit`으로 잘리는데, 설계 확정 사항 3항의 "뉴스와 동일한 limit 파라미터를 공시 배열에도 적용"을 정확히 따른 것입니다.

`news_items` 테이블에는 `category VARCHAR(30) NULL` 컬럼이 nullable로 추가되고 단일 Alembic 마이그레이션(`c3d4e5f60064`)이 생성됩니다. `NewsAnalysisService.summarize()`는 LLM 응답에서 category를 파싱하되, 비정상 값(enum 외 문자열, 비문자열 타입 등)이면 `None`으로 폴백하는 방어 로직을 `_NEWS_CATEGORIES frozenset` 멤버십 검사로 구현했습니다.

Projection 타입(`NewsItemProjection`, `DisclosureItemProjection`, `NewsDisclosureResponse`)은 ADR-009의 'Projection' 접미사 규칙을 준수하며 'DTO' 용어는 쓰이지 않습니다. `app/domains/reports/`와 `app/adapters/disclosure/base.py`의 `DisclosureResult`는 변경 불가 규칙대로 수정되지 않았습니다.

## Blocking

**B1. `test_get_news_disclosure_separates_news_and_disclosures`에서 뉴스 id를 리터럴 `2`로 단언합니다**

테스트 88번 줄 `"id": 2` 단언이 DB autoincrement 순서에 의존합니다. conftest의 `client` 픽스처는 테스트마다 `Base.metadata.drop_all` → `create_all`로 스키마를 재생성하지만 SQLite의 autoincrement 카운터는 in-memory DB가 폐기될 때만 리셋됩니다. 현재 `StaticPool`로 단일 in-memory DB를 공유하기 때문에, 이 테스트보다 먼저 실행되는 다른 테스트가 `NewsItem` 행을 삽입했다면 id가 `2`가 아닌 다른 값이 됩니다. 실행 순서에 따라 CI에서 간헐 실패할 수 있습니다.

수정 방향: `data["news"][0]["id"]`가 존재하고 정수임만 단언하거나, `asset_id`와 `title`을 기준으로 대조합니다. 다른 계약 테스트(`test_get_research_summary_returns_structured_fields_for_all_templates` 등)는 id를 직접 단언하지 않으므로 이 테스트만 수정이 필요합니다. 심각도: 차단 — 실행 순서 변경 시 간헐적 CI 실패 위험.

## Suggestions

**S1. 공시 정렬 전에 전체 fetch 결과를 메모리에 로딩합니다**

`NewsDisclosureService`는 `disclosure_provider.fetch([symbol])`의 반환값 전체를 받은 뒤 Python에서 정렬·슬라이스합니다. mock 단계에서는 문제없지만, 실 어댑터 도입 시 provider가 다수 종목의 대량 결과를 반환할 경우 불필요한 메모리 적재가 발생합니다. 이번 설계 확정 사항에서도 "실 어댑터 도입 시 재검토"를 명시했으므로 현 단계에서 범위 내 허용 사항입니다. 실 어댑터 핸드오프 시 limit을 provider 인터페이스로 내려보내는 방향을 검토하면 됩니다. 심각도: 비차단·후속 이슈 사항.

**S2. `DisclosureItemProjection`에 `model_config = {"from_attributes": True}`가 없습니다**

`NewsItemProjection`은 `model_config = {"from_attributes": True}`를 선언해 SQLAlchemy 모델을 직접 `model_validate`로 변환합니다. `DisclosureItemProjection`은 `DisclosureResult`(frozen dataclass)를 필드 단위로 직접 할당해 생성하므로 현재 동작에 문제가 없습니다. 다만 두 Projection의 선언 패턴이 다른 점은 이후 유지보수 시 혼란 소지가 있습니다. 구현자 판단에 맡깁니다. 심각도: 비차단·의견.
