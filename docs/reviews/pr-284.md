## Suggestions

**S1. `collect_valuation_job`의 symbols 직접 전달 시 market이 NASDAQ으로 하드코딩됨**

심각도: 비차단 · 범위 한정적. `app/worker/jobs/valuation.py` 17행에서 `symbols`가 직접 전달될 때 `[(symbol.upper(), "NASDAQ") for symbol in symbols]`로 market을 NASDAQ으로 고정합니다. `/jobs/valuation` API 라우트를 통해 KOSPI 종목을 지정 수집하려는 수동 트리거 시나리오에서 market이 무조건 NASDAQ으로 설정됩니다. 현 단계는 `symbols=None`(유니버스 자동 해소) 경로가 주 경로이고 라우트도 내부 운영 도구 수준이므로 즉각 차단은 아닙니다만, 향후 멀티 마켓 수동 트리거를 고려한다면 `ValuationJobRequest`에 `market` 필드를 추가하거나 `(symbol, market)` 쌍 전달 방식을 검토하는 것이 적절합니다.

**S2. `ValuationIngestionService.collect_and_save`에서 성공 시 `saved_count`와 `success_count`가 항상 같은 값이 됨**

심각도: 비차단 · 명확성 개선 여지. `app/domains/valuation/ingestion_service.py` 50–51행에서 성공 시 `success_count += 1; saved_count += 1`이 동시에 증가하여 두 필드가 항상 일치합니다. 현재 코드에서 provider 호출 성공 후 repository upsert가 실패하면 `except` 블록으로 빠져 `failure_count`로 집계되는데, 이 경우 `success_count`는 증가하지 않으므로 실제로는 두 필드가 항상 같습니다. `ValuationIngestionResult`에서 둘 중 하나를 제거하거나, 명확히 다른 의미(예: provider 성공 vs. DB 저장 성공)를 가지도록 분리하는 것이 가독성에 더 좋습니다. 기능 정확성에는 영향이 없습니다.

**S3. `_profile` 로직에서 스냅샷 부재(snapshot is None) 시 DEFICIT 판정 가능성이 없어 GENERAL로 수렴하지만, 테스트에 스냅샷 없는 DEFICIT 케이스가 없음**

심각도: 비차단 · 커버리지 여지. 설계 문서 5절에서 "스냅샷 부재 포함 → GENERAL"을 명시하고, `service.py` 73행 `_profile` 로직도 `snapshot is not None`을 DEFICIT 진입 조건으로 둬 일치합니다. 다만 `tests/test_valuation.py`의 profile 규칙 파라미터화 케이스(1118–1159행)에는 스냅샷이 없는 GENERAL 케이스가 없고, `test_get_valuation_metrics_without_snapshot_returns_null_values`는 profile이 GENERAL임을 단언하지만 sector는 None입니다. sector=None + 스냅샷 없는 GENERAL 경로는 암묵적으로 커버되지만, sector="Technology" + 스냅샷 없는 케이스를 파라미터화 테이블에 추가하면 명시성이 높아집니다. 현 단계 기능에는 영향이 없습니다.

## Questions

**Q1. `updated_at`의 `onupdate=func.now()` 동작 여부**

`TimestampMixin`의 `updated_at`은 SQLAlchemy ORM `onupdate=func.now()`로 선언되어 있어 ORM을 통한 UPDATE에서는 갱신됩니다(`app/db/base.py` 16–17행). `ValuationRepository.upsert`는 기존 스냅샷 발견 시 `setattr` 후 `db.commit()`을 사용하므로 ORM 경로를 통하며, 이 경우 `updated_at`이 갱신됩니다. 단, `onupdate` SQLAlchemy 이벤트는 raw SQL `UPDATE`에는 적용되지 않으므로 현재 구현(ORM setattr + commit)이 정합합니다. `test_research_coverage.py`에서 `valuation_updated_at`을 생성자에 직접 전달해 고정하는 방식(62행 `updated_at=valuation_updated_at`)은 `TimestampMixin` 필드를 생성자 인자로 넘겨 `server_default`를 우회하는데, SQLAlchemy 모델에서 이 패턴이 실제로 저장값을 대체하는지 확인을 권장합니다. 대부분의 경우 SQLAlchemy ORM 생성자에서 `server_default` 컬럼에 명시적 값을 넘기면 그 값이 INSERT됩니다. 테스트의 `last_updated_at` 단언이 실제 DB 저장값과 일치하는지는 CI 통과로 검증됩니다.

**Q2. `MockValuationProvider`에서 `fcf_yield`의 범위가 `-50 ~ 100%`인 근거**

`app/adapters/market/mock.py` 173행에서 `fcf_yield=_ratio(seed, -50, 150, 10)`으로 -5.0 ~ 10.0 범위의 값을 생성합니다(span=150, 분모=10, 최솟값=-50→-5.0). 음수 FCF yield(현금 소진 기업) 케이스를 포함하려는 의도로 보이며 설계 문서는 "일부 null 케이스 포함"을 언급하지만 음수 범위에 대한 명시는 없습니다. 기능적으로 null 케이스와 음수 케이스가 모두 테스트에 흘러들어오므로 결함은 아니지만, mock 수치 범위의 의도를 주석으로 남겨두면 후속 유지보수 시 의미 파악이 쉬워집니다.
