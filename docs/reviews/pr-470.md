## Review Summary

일일 리서치 에이전트를 실제 실행 경로(스케줄, 관심종목 추가, 워커 API)에 연결하고 기존 관심종목 분석
흐름을 제거하는 PR입니다. 커밋은 핸드오프와 Codex 구현으로 구성됩니다. `.env.example`에 남은 주석 한 줄은
orchestrator가 정리했습니다.

**Part A — 실행 경로 연결(설계 459 §6).** `run_daily_research_job`은 실행 기록을 시작한 뒤
`prepare_embeddings`로 임베딩 backlog를 한 번 처리하고 에이전트를 실행합니다. 종목 실패와 노트 실패는
metadata `partial_failures`에 남기고, 예외가 나면 job 실패로 기록한 뒤 다시 던집니다. 스케줄은
`daily_research_agent`(`30 22 * * 0-4`)이고, 관심종목을 추가하면 추가한 종목만 enqueue합니다. 워커 API는 FE
`triggerAnalysis`가 쓰는 경로·요청·응답·rate limit을 유지하며, 소유한 관심목록의 종목 id로 job을 넣습니다.
종목 루프에 있던 인덱서 호출은 빠졌습니다(PR #468 S1).

**Part B — 제거(ADR-020 §4).** `app/domains/analysis/`, 분석 job, 스케줄 4개, `ANALYSIS_SCHEDULE_ENABLED`와 관련
테스트를 지웠습니다. 제거 대상 식별자를 grep하면 `app`·`scripts`·`tests`·`.env.example`에서 0건입니다.
`summarize`·`analyze_conflict`는 운영 호출처 없이 남깁니다.

이번 리뷰는 FE 계약 유지, 제거 누락, 실행 경로의 실패 처리를 축으로 봤습니다.

## Suggestions

**S1. 빈 관심목록이면 `status="skipped"`, `job_id=""`를 반환합니다 — 경미, 허용.** 응답 스키마(`status: str`)는
그대로지만 FE 타입은 `status: 'queued'`로 선언돼 있습니다. FE는 이 값으로 분기하지 않아 화면 동작은 바뀌지
않습니다. 다음 FE 작업 때 타입에 `'skipped'`를 더하면 됩니다.

**S2. 스케줄이 항상 켜져 있습니다 — 설계 의도와 일치.** 기존 분석 스케줄은 opt-in(`ANALYSIS_SCHEDULE_ENABLED`)
이었지만, 새 스케줄은 `enabled=True`입니다. ADR-020이 평일 1회 실행을 정했고 비용은 종목 수에 비례하므로
허용합니다. `LLM_PROVIDER=mock` 환경에서는 실제 비용이 없습니다.

## Questions

**Q1. 미소유 관심목록에 404를 쓰는 것이 맞는가 — 개발자 확인 요청.** 핸드오프는 "기존 관심목록 API와 같은
처리"를 요구했지만 기존 API는 미소유에 403을 씁니다. Codex는 존재 여부를 드러내지 않는 404를 택하고 설계
459 §6에 차이를 기록했습니다. 리뷰어는 404를 권장하지만, 일관성을 우선하면 403으로 바꿀 수 있습니다.

**Q2. 실제 job 경로가 동작하는가 — 리뷰 중 확인해 해소했습니다.** 복제 DB, 실제 Ollama와 LLM, 임시 vault로
`run_daily_research_job()`을 실행했습니다. `job_runs`에 `daily_research_agent`가 `success`로 기록됐고, 종목 노트
4개와 인덱스 1개가 생성됐습니다. 복제 DB에는 새 뉴스가 없어 네 종목 모두 "새 소식 없음" 경로를 탔습니다.
새 소식 경로는 PR #468·#469에서 확인했습니다.
