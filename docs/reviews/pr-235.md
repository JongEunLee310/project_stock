## Review Summary

FE 관심종목 페이지(`project_stock_frontend#117`) Phase 2를 위해 BE 응답 계약 세 가지를 확장하는 PR입니다.

첫 번째로, `WatchlistItemExpandedResponse`에 `status: str` 필드를 추가했습니다. 기존 `WatchlistService`에 이미 주입되어 있던 `SignalRepository`를 그대로 활용해 `active_signal_types_by_asset` 배치 조회를 `list_items_expanded` 안에 추가하고, `resolve_watchlist_status`로 항목별 우선순위 최상위 활성 시그널 타입을 결정합니다. 두 번째로, `AssetBriefResponse`에 `reference_at: UtcDatetime | None = None` 필드를 추가해 기존 `QuoteResult.as_of` 값을 전달합니다. 필드명은 `IndexQuoteResult.reference_at` 시장 도메인 표기 규칙과 통일했습니다. 세 번째로, `GET /watchlists/{id}/sparklines` 엔드포인트를 신설해 관심종목 전체 종목의 최근 일봉 종가 시리즈를 배치로 반환합니다.

구조상 핵심 결정은 스파크라인을 별도 배치 엔드포인트로 분리한 것입니다. pagination과 수명 주기가 달라 inline expand 방식보다 FE 캐싱과 관심사 분리 면에서 유리하며, 기존 `/summary/trends` child endpoint 선례와 동일한 패턴입니다. `WatchlistSparklineService`에서 소유 확인은 `WatchlistService._get_owned_watchlist`를 호출하는 방식이며, `trend_service.py:32`에 동일한 선례가 있습니다.

`status` 픽스처는 `SignalType` enum을 실제 import해 사용하고, 주석으로 출처(`app/domains/signals/types.py`)를 명시했습니다. `reference_at` 단언값 `"2026-06-19T00:00:00Z"`는 `app/adapters/market/mock.py:18`의 `_AS_OF = datetime(2026, 6, 19, 0, 0, tzinfo=timezone.utc)` 상수에서 직접 파생되므로 실제 생산자 코드에 근거한 실계약 픽스처입니다.

두 응답 모델 변경 모두 필드 추가만이므로 FE 하위 호환이 유지됩니다.

## Suggestions

**S1. `PriceSeriesService.get_series` 404 제외 동작에 대한 테스트가 없습니다.**

`sparkline_service.py`는 `AppException`을 잡아 `exc.status_code == 404` AND `exc.error_code == ErrorCode.PRICE_SERIES_NOT_FOUND` 두 조건을 모두 확인한 뒤 해당 종목을 결과에서 제외합니다. 핸드오프 Requirements 절에 "가격 시계열이 없는 종목은 결과에서 제외"가 명시된 기능 요구이지만, 이 분기를 검증하는 테스트가 신규 파일(`tests/test_watchlist_sparklines.py`)과 기존 파일 어디에도 없습니다. 조건 분기가 미래 리팩터링에서 일부 깨지더라도 테스트 스위트가 이를 감지하지 못합니다. 현재 범위에서 머지를 막지는 않지만, 후속 PR 또는 기존 단위 테스트에 케이스를 추가하는 것을 권장합니다.

**S2. `WatchlistSparklineService`가 단일 메서드 호출을 위해 `WatchlistService(db)` 전체를 인스턴스화합니다.**

`_get_owned_watchlist` 호출 하나를 위해 `WatchlistService.__init__`에서 `SignalRepository`, `AssetRepository`, `WatchlistRepository`, `WatchlistItemRepository`, `RecommendationRepository` 다섯 개 의존성이 생성됩니다. `trend_service.py:32` 선례를 따른 것이므로 기존 패턴에서 벗어나지 않으며 동작에 문제는 없습니다. 장기적으로 `_get_owned_watchlist`를 공통 유틸로 분리하는 방안을 검토할 수 있지만, 지금 범위에서는 논의 사항으로만 남겨 둡니다.
