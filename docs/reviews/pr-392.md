# PR #392 로컬 리뷰 — 투자자 동향 window를 기간 필터로 정합 (#390)

## Review Summary

개요 화면의 `투자자 동향` 패널이 항상 비어 있던 결함을 고친 PR입니다. 단일 커밋
(`916d0a0 fix: 투자자 동향 조회 기간 불일치 수정`)입니다.

원인은 개념의 혼동입니다. `investor_flow_records`가 조회 파라미터 `window`를 기간이 아니라
저장된 문자열 라벨(`InvestorFlow.window`)에 대한 완전 일치 조건으로 썼습니다. 데이터를 넣는
유일한 경로인 `seed_mock_news_insights`는 `window="5d"`로 쓰고, 화면은 두 페이지 모두
`window="7d"`로 조회합니다. `'7d' != '5d'`이므로 행이 0건이 되고, 서비스가 이를
`availability.available = false`로 바꿔 정상적인 빈 응답으로 돌려줬습니다. HTTP 200이라
오류로도 드러나지 않았습니다. 이 도메인에서 `window`를 완전 일치로 쓰는 곳은 이 한 곳뿐이며,
나머지 조회는 모두 `service.py`의 `_parse_window`로 `timedelta`를 만들어 기간으로 거릅니다.
설계된 선택이 아니라 어긋난 지점이었다는 뜻입니다.

수정은 세 갈래입니다. 첫째, 조회 조건을 `InvestorFlow.as_of >= 기준 시각 - window`로 바꿨고
기준 시각은 서비스가 `as_of or utcnow()`로 정해 리포지토리에 키워드 인자로 넘깁니다.
리포지토리가 스스로 현재 시각을 만들지 않으므로 PR #386이 도입한 시계 고정이 그대로 통합니다.
둘째, `InvestorFlowsResponse`에 `aggregation_windows: list[str] | None`을 더해 반환된 행의
실제 집계 기준을 밝힙니다. 데이터가 없으면 `null`이고, 요청값을 집계 기준인 양 채우지
않습니다. 셋째, 로컬 개발용 시드 스크립트 `scripts/seed_news_insights.py`를 추가했습니다.

이번 리뷰는 조회 결과 집합 변화의 타당성, 새 필드가 실제 데이터를 반영하는지, 시계 주입이
유지되는지, 회귀 테스트가 결함의 핵심을 덮는지, 시드 스크립트의 파괴 범위를 축으로 봤습니다.

## Blocking

None.

## Suggestions

**S1. `aggregation_windows`가 반환값에 쓰이지 않은 행의 라벨까지 포함할 수 있다 — 낮은 위험,
현 데이터에서는 무해.** 집계 결과는 투자자 유형별로 가장 최근 두 행만 쓰지만(`values[0]`과
`values[1]`), `aggregation_windows`는 조회 기간 안의 모든 행에서 `DISTINCT`로 뽑습니다. 같은
기간에 세 번째 이상의 오래된 행이 다른 라벨로 존재하면, 실제로 값에 반영되지 않은 기준이
목록에 섞입니다. 현재는 공급원이 시드뿐이라 이런 상황이 생기지 않고, 필드의 목적이 "이 응답이
어떤 집계 기준의 데이터 위에 서 있는가"를 밝히는 것이므로 과잉 포함이 오해를 만들 여지도
작습니다. 실제 공급원이 붙는 #391에서 여러 라벨이 실제로 섞이기 시작하면, 반환에 쓰인 행만
집계하도록 좁히는 편이 정확합니다.

**S2. 계약에 필드가 추가돼 프론트엔드가 아직 이 값을 쓰지 않는다 — 의도된 순서.** 화면의
투자자 동향 패널은 배지에 요청값(`{market} · {window}`)을 그대로 표시합니다. 데이터의 집계
기준이 `5d`인데 배지가 `7d`로 읽히는 상태라 정확하지 않습니다. 이번 PR은 백엔드 계약까지만
다루고, 배지를 `aggregation_windows` 기반으로 바꾸는 작업은 후속 프론트엔드 PR로 남겼습니다.
새 필드는 추가이므로 기존 프론트엔드 어댑터가 깨지지 않습니다.

**S3. 시드가 투자자 유형을 한 종류만 넣는다 — 이번 범위 밖, 데모 품질 사항.**
`seed_mock_news_insights`는 `InvestorFlow`를 `FOREIGN` 한 건만 만듭니다. 설계 이미지의 투자자
동향은 외국인·기관·개인 세 주체를 비교하는 패널이므로, 시드로 채운 화면에서는 한 줄만
보입니다. 이번 수정의 대상이 아니고 핸드오프에서도 시드 값 변경을 범위 밖으로 뒀으므로 그대로
뒀습니다. 데모 데이터의 폭을 넓히는 일은 별도로 판단하면 됩니다.

## Questions

**Q1. 수정이 실제 데이터에서 동작하는가.** 확인해 해소했습니다. 실행 중인 개발 DB
(`stock_db`)에 시드를 넣고 서비스 계층을 직접 호출해 비교했습니다. 수정 전에는 `window=7d`가
0건이었고, 수정 후에는 `available=True`, `items=1`, `aggregation_windows=['5d']`로 시드 행이
반환됩니다. `window=5d`·`window=1h`도 같은 행을 돌려주며, 이는 시드의 `as_of`가 방금 시각이기
때문에 맞는 동작입니다.

**Q2. 시계 고정이 깨지지 않는가.** 확인해 해소했습니다. 리포지토리는 현재 시각을 만들지 않고
`as_of` 키워드 인자로 받습니다. 서비스가 `as_of or utcnow()`로 정하므로 PR #386의
`freeze_news_insights_clock` fixture가 그대로 적용되고, 새 테스트도 `SEEDED_AT` 기준으로
경계를 단언합니다.

**Q3. 시드 스크립트가 다른 도메인 데이터를 지우지 않는가.** 확인해 해소했습니다. 삭제 대상은
`NEWS_INSIGHT_TABLES`에 나열된 뉴스 인사이트 17개 테이블뿐이며, `news_items`(2,481건)·
`raw_news_events`(2,622건)·`earnings_events`(100건)는 대상이 아닙니다. 삭제 순서는 자식 →
부모 순으로 외래키 제약을 만족합니다(`explanation_factors` → `topic_explanations`,
`agent_run_stages` → `agent_runs`, `event_evidence` → `extracted_events`·`source_documents`,
`topic_clusters` 참조 테이블 전부 → `topic_clusters`). 기본 실행은 데이터가 있으면 건너뛰고
`--reset`을 줄 때만 삭제하며, 삭제 전에 대상 테이블과 건수를 출력합니다. 전체가 하나의
트랜잭션(`SessionLocal.begin()`) 안에서 돌아 실패 시 되돌아갑니다. 실제로 두 모드를 모두
실행해 확인했습니다.

## Documentation Impact

이번 PR에서 두 문서가 갱신됐습니다. `docs/designs/307-news-intelligence-phase2.md` §3.2가
`window`의 의미(저장 라벨 일치가 아니라 조회 기간)와 `aggregation_windows` 필드를 반영했고,
`docs/failures/FAILURE-005-investor-flow-window-contract-drift.md`가 새로 추가됐습니다.
FAILURE-005는 `FAILURE-000-template.md` 형식을 따르며 기존 001~004와 문체가 일치합니다.

ADR은 불요합니다. 새 도메인·테이블·외부 의존성이 없고, 이 도메인의 다른 조회가 이미 쓰고 있는
기간 필터 방식으로 맞추는 정합 작업입니다.

Failure Record는 필요했고 반영됐습니다. 시드가 쓰는 값과 테스트가 묻는 값이 같아서 계약이
화면과 어긋난 채로 계약·모델·화면 세 단계를 통과한 사례이며, 재발 방지는 "계약 테스트는 화면이
실제로 보내는 파라미터로 조회한다"입니다.

## Final Recommendation

머지 가능합니다. 핸드오프의 요구를 항목별로 확인했습니다. 완전 일치 조건이 기간 조건으로
바뀌었고, 리포지토리는 현재 시각을 스스로 만들지 않으며, `InvestorFlowsQuery`의 `window`
패턴(`^[1-9]\d*[hd]$`)은 그대로입니다. 데이터가 없을 때의 `availability.available = false`와
fallback 문구 동작도 유지됩니다. 이제 빈 응답은 파라미터가 어긋났다는 뜻이 아니라 실제로
데이터가 없다는 뜻입니다.

범위는 지켜졌습니다. 다른 조회(`overview`·`topic map`·`calendar`·`trend`)의 window 처리는
건드리지 않았고, `seed_mock_news_insights`가 넣는 값도 `window="5d"` 그대로입니다. 조회 측이
저장 라벨을 알아맞히지 않아도 되게 만드는 것이 이번 수정의 요점이므로 맞는 선택입니다.
Protected Files는 없으며 diff는 리포지토리·서비스·스키마·테스트·시드 스크립트와 두 문서에
한정됩니다.

추가된 테스트는 이번 결함의 핵심을 정면으로 덮습니다.
`test_investor_flows_uses_requested_window_as_time_range`가 화면이 실제로 보내는
`market=KR`·`window=7d`로 조회해 `window="5d"`로 저장된 행이 나오는지 확인하고,
`test_investor_flows_excludes_rows_outside_requested_window`가 기간 밖 행의 제외를 확인합니다.
기존 두 테스트는 유지됐고 단언이 약해진 곳은 없습니다. 오히려 세 곳에
`aggregation_windows` 단언이 더해졌습니다.

Blocking은 없습니다. S1은 실제 공급원이 붙는 #391에서 좁히면 되는 후속 사항이고, S2는 의도된
작업 순서이며, S3은 이번 범위 밖입니다. Q1·Q2·Q3은 모두 직접 확인해 해소했습니다.

최종 머지 권한은 개발자에게 있습니다.
