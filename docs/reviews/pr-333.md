`error_codes.py`·`alerts.py`는 추가만 했습니다.

delivery_policy가 일치하고, `TOPIC_IMPACT_SURGE`는 `is_active=False`로 노출됩니다. 조건 검증기
`validate_condition`은 설계 §4대로 단일 조건과 `all`(AND) 배열만 허용하고(중첩 `all` 거부),
지원 metric·operator·값 도메인을 세밀하게 검사합니다: 전이 지표(`SIGNAL_CHANGED`·
`AI_JUDGMENT_CHANGED`)는 `CHANGED`+`value=None`만, 나머지는 EQ/GTE/LTE에 한해 `NewsRisk`·
`ThemeHeat` enum 값·수치 범위(`POSITION_WEIGHT`∈[0,1] 등)를 검증하며, 비활성
`TOPIC_IMPACT_SCORE`로는 활성 규칙을 만들 수 없게 막습니다. 소유권은 `_get_owned_rule`에서
`ALERT_RULE_NOT_FOUND`(404)·`ALERT_RULE_FORBIDDEN`(403)으로 처리하고, SYSTEM 규칙 삭제는
403으로 거부합니다. overview의 `triggered_today_count`는 UTC 자정 기준으로, 기존
`research_queue`의 `updated_today_count`(UTC day 경계)와 프로젝트 관례가 일치합니다.

`AlertRuleUpdate`는 `model_validator`로 non-nullable 필드에 null 주입을 막고, projection
명명 규칙(`*Projection`)을 지킵니다.

## Non-blocking

**S1. overview `high_severity_count`가 전체 기간의 HIGH·CRITICAL 이벤트를 집계합니다(읽음
포함).** `count_high_severity_events`가 read_at·날짜 필터 없이 소유자의 모든 HIGH/CRITICAL
이벤트를 셉니다. 설계 §4의 "즉시 확인이 필요한 항목"은 미읽음 또는 당일 기준일 여지가 있어,
시간이 지나면 이 수치가 계속 커집니다. FE F1(#224)에서 이 숫자의 의미(전체 vs 미읽음 vs 당일)를
확정해 맞추길 권합니다. 계약을 바꾸려면 지금이 비용이 가장 적습니다. 본 PR에서 반드시 고칠
필요는 없습니다.

**S2. `create_rule`의 사용자 지정 condition이 템플릿의 target_type 의미와 교차 검증되지
않습니다.** 예컨대 SYMBOL 템플릿에 `POSITION_WEIGHT` 조건을 실어도 통과합니다. MVP에서는
템플릿이 올바른 사용을 유도하고 파워유저 케이스라 위험이 낮지만, 후속에서 metric↔target_type
정합 검증을 고려할 수 있습니다.

**참고(B3 대비). `/alerts/overview`는 정적 경로라 `alerts.py` 상단에 선언됐습니다.** B3에서
`/alerts/{alert_id}` 동적 경로를 추가할 때 `/overview`(및 `/read`)가 그보다 먼저 선언되도록
유지해야 shadowing이 없습니다.
