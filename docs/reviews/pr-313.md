## Review Summary

이 PR은 계약에는 정의되어 있지만 실제 수집 데이터에서 채워지지 않던 `news_items.category`를 규칙 기반 키워드 분류로 채웁니다. 설계 문서 `docs/designs/296-news-category-classification.md`와 핸드오프 `.codex/tasks/task-191-news-category.md`가 요구한 범위(순수 분류 함수, 정규화·공시 경로 적용, idempotent backfill)를 그대로 따르고 있습니다.

핵심은 `app/domains/news/categorizer.py`에 신규 추가된 `categorize(title, summary) -> NewsCategory`입니다. 카테고리별 한국어·영어 키워드 튜플을 EARNINGS부터 MARKET까지 우선순위 순서로 순회하며 첫 매칭을 반환하고, 무매칭 시 `OTHER`로 폴백합니다. DB·외부 호출이 전혀 없는 순수 함수이고, 문자열은 `casefold()`로 비교해 대소문자를 가립니다.

적용 지점은 세 곳입니다. `normalizer.py`의 `to_news_item_create()`는 원시 뉴스를 정규화하며 항상 `categorize()` 결과를 채워 넣고, `news_disclosure_service.py`는 공시 응답을 조립하는 시점에 기존 하드코딩된 `"OTHER"`를 `categorize(item.title, None)` 호출로 대체했습니다(공시는 애초에 DB에 영속화되지 않고 외부 제공자에서 매 요청 조회하는 기존 구조이므로, 매 요청 재계산은 새로운 문제가 아니라 기존 구조를 그대로 따른 것입니다). 그리고 `repository.py`의 `create()`는 `data.category`가 `None`일 때만 분류기를 적용하는 공통 fallback으로, 설계 3절이 명시한 대로 다른 저장 경로가 category를 채우지 않은 경우를 보완합니다.

기존 category·LLM 분류값 보존과 관련해서는 `update_summary()`가 `if data.category is not None: item.category = data.category`로 바뀌었습니다. 변경 전에는 `item.category = data.category`로 무조건 덮어써서 LLM 응답에 category가 없으면 기존 규칙 기반 분류값이 `None`으로 지워질 수 있었는데, 이번 변경으로 그 회귀를 막았습니다. `backfill.py`의 `backfill_news_categories()`는 `NewsItem.category.is_(None)` 행만 대상으로 하고, `tests/test_news_category_backfill.py`가 이미 category가 있는 행은 건드리지 않는지와 두 번째 호출에서 갱신 건수가 0인지를 직접 검증합니다.

## Suggestions

**S1. `update_summary()`의 category 보존 분기를 직접 겨냥한 테스트가 없습니다.**

이번 리뷰의 핵심 관점인 "기존 category·LLM 분류값 보존(덮어쓰기 금지)" 로직은 코드 검토 결과 정확하게 구현되어 있습니다. 다만 `tests/test_news_analysis.py`의 `test_news_analysis_service_falls_back_to_none_for_invalid_category`는 `create_news_item()`이 `NewsItemRepository.create()`가 아니라 `NewsItem` 모델을 직접 생성하는 방식이라 애초에 category가 `None`인 상태에서 시작합니다. 그래서 이 테스트는 "무효한 category가 오면 None으로 폴백"만 검증할 뿐, "이미 규칙 기반으로 분류된 category가 있는 상태에서 LLM 응답에 category가 없을 때 기존 값이 보존되는지"는 어떤 테스트도 직접 확인하지 않습니다. 저장소 전체에서 `update_summary`를 호출하는 테스트를 찾아봐도 이 경로는 없습니다. 로직 자체는 옳고 회귀도 발견되지 않았으므로 비차단이지만, 이 PR이 도입한 회귀 방지 로직인 만큼 후속으로 보존 케이스를 직접 검증하는 테스트를 추가하는 편이 좋겠습니다.

**S2. 키워드 사전 일부 항목이 지나치게 일반적이어서 오분류 위험이 있습니다.**

PARTNERSHIP의 `"agreement"`는 제휴 계약뿐 아니라 합의·화해·대출 약정 등 REGULATION이나 CAPITAL에 더 가까운 문맥에서도 흔히 쓰이는 단어입니다. PARTNERSHIP이 REGULATION보다 먼저 검사되기 때문에, 예를 들어 "규제 당국과 합의(agreement)"류 제목은 REGULATION이 아니라 PARTNERSHIP으로 분류될 수 있습니다. PRODUCT의 `"service"`·`"제품"`도 고객 서비스·금융 서비스 등 제품 출시와 무관한 문맥에서 자주 등장합니다. 1차 규칙 기반 분류는 설계 문서가 이미 완전한 정밀도를 요구하지 않고 LLM 기반 2차 분류로 개선을 미루고 있어(설계 §1) 이번 범위에서 반드시 고쳐야 할 사안은 아니지만, 향후 키워드를 다듬을 때 참고할 오탐 사례로 기록해 둡니다.
