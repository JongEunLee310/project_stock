## Review Summary

리서치 상세의 AI briefing을 하드코딩 템플릿 mock에서 `LLMGateway` 실생성·저장
구조로 전환하는 PR입니다. 기존 `ValuationRepository.upsert` 패턴(select 후
insert-or-update, `TimestampMixin`의 `updated_at`을 생성 시각으로 재사용)과
`STOCK_RECOMMENDATION` 태스크 등록 패턴을 그대로 재사용해, `research_summaries`
테이블 신설과 `LLMTaskType.RESEARCH_SUMMARY` 등록이라는 두 축을 연결하는
구조입니다.

- `ResearchSummaryRow`(`app/domains/research_summary/model.py`)는 설계 §3.1
  테이블과 컬럼·제약(`UniqueConstraint("asset_id")`, JSON 기본값 `[]`,
  `key_risks` not null)이 정확히 일치하며, 마이그레이션
  `alembic/versions/c3d4e5f60068_create_research_summaries.py`도 동일합니다.
  `ResearchSummaryRepository.upsert`는 `get_by_asset_id` 결과가 있으면 필드만
  덮어쓰고 없으면 새로 추가하는 단일 upsert이며,
  `test_repository_upsert_keeps_one_row_per_asset`이 동일 `asset_id`에서 행 수가
  1로 유지되고 `updated_at`이 갱신되는지 직접 검증합니다.
- `ResearchSummaryService.generate`는 `context_builder.build_symbol_context`로
  얻은 `SymbolCard`를 `to_research_summary_snapshot`으로 변환해
  `gateway.complete_json`에 넘긴 뒤 저장소에 upsert합니다.
  `ResearchSummarySnapshot`(`app/adapters/llm/privacy.py:195-209`)에는
  `portfolio_context` 필드 자체가 없어 CloudSafe 경계에서 배제되며,
  `test_generate_uses_cloud_safe_snapshot_without_portfolio_context`가
  `"portfolio_context" not in snapshot.as_payload()`로 직접 확인합니다.
  `sensitivity = SensitivityLevel.AGGREGATED`는 `StockRecommendationSnapshot` 등
  기존 스냅샷들과 동일한 등급입니다.
- `GET`은 저장본 조회로 전환되어 저장본이 없으면
  `404 RESEARCH_SUMMARY_NOT_FOUND`를 반환하고(`test_research_summary_returns_not_found_without_stored_summary`),
  응답의 `created_at`은 설계대로 저장 행의 `updated_at`을 그대로 노출하며
  이름-의미 불일치를 서비스 코드 주석으로 남겼습니다
  (`app/domains/research_summary/service.py`의 `_to_response`).
- `research_queue/service.py`는 `get_summary` 호출을 `get_summary_or_none`으로
  교체해 저장본 없는 자산에서도 큐 조회가 예외 없이 `stance=None`/`headline=None`으로
  응답합니다. 이 교체와 함께 `ResearchSummaryService.prefetch(asset_ids)`를
  큐 조회 루프 앞에 추가해 자산별 개별 조회 대신 배치 조회 1건으로 처리합니다.
  `test_query_count_does_not_grow_with_asset_count`가 쿼리 수를 10에서 11로
  갱신해 "배치 조회 1건 추가, N+1 없음"을 직접 고정합니다.
- 라우팅·프롬프트·mock 응답은 기존 관례를 그대로 재사용합니다.

## Suggestions

**S1. batch prefetch 추가가 PR 본문의 "가정 검증 결과"에 이탈로 기록되지 않았습니다.**

`research_queue/service.py`의 `prefetch`(`ResearchSummaryService.prefetch`)는
설계 §4·핸드오프 Implementation Scope에는 명시되지 않은 추가입니다. 다만 GET이
mock 계산에서 실제 DB 조회로 바뀌면서 루프 안에서 자산별로 조회하면 N+1이
발생해 기존 회귀 테스트(`test_query_count_does_not_grow_with_asset_count`)가
깨졌을 것이므로, 이 추가는 "기존 계약·수집 경로 회귀 없음"이라는 완료 조건을
지키기 위해 사실상 불가피했습니다. 쿼리 수 10→11 갱신으로 배치 조회 1건만
추가됐음이 테스트로 고정되어 있고, `ResearchQueueService`가 요청마다 새로
생성되므로(`app/api/v1/endpoints/research_queue.py:32`) `_prefetched_rows`
상태가 요청 간에 누수될 위험도 없습니다. 동작 자체는 정확하고 잘
검증되었으나, `quality-process-policy.md`의 Deviations Log 규율상 설계
스켈레톤을 벗어난 추가는 구현 노트에 남기는 것이 원칙이므로, PR 본문의
"가정 검증 결과" 절에 이 추가와 그 이유를 한 줄 덧붙이는 편을 권장합니다.
비차단입니다.

## Questions

**Q1. `stance`/`stance_confidence` 값 어휘가 시스템 프롬프트에 명시되지 않습니다.**

`ResearchSummaryResult.stance`는 enum이 아닌 `str`이고, 신설 시스템 프롬프트
(`app/adapters/llm/prompts/research_summary.py`)는 JSON 스키마 준수만 지시할 뿐
`BUY_CANDIDATE`/`WATCH` 같은 기존 어휘(design-266 §"stance"에 문서화된 값)를
직접 나열하지 않습니다. DB 컬럼도 `String(50)`으로 고정 길이입니다. 이는 이번
PR이 새로 만든 문제가 아니라 상위 설계(#322)에도 명시되지 않은 기존 공백이며,
FE 소비 측(project_stock_frontend#219)은 이번 범위 밖이라 지금 당장 계약을
깨뜨리지는 않습니다. 다만 실제 cloud LLM이 문서화된 어휘를 벗어난 값을
반환하면 FE 라벨 매핑이나(추후) DB 길이 제약과 충돌할 수 있어, 실 연동 검증
단계에서 확인이 필요한지 여쭙습니다. 차단 사유는 아닙니다.
