## Review Summary

PR #338(이슈 #336) 로컬 리뷰에서 S2로 제기한 사항의 후속입니다. 커밋은 두 건이며 핸드오프
문서(`.codex/tasks/task-205-alert-metric-unavailable.md`) 추가와 구현으로 나뉩니다.

파생 지표(`NEWS_RISK`·`THEME_HEAT`·`AI_JUDGMENT_CHANGED`)는 시그널 스냅샷에서 값을
끌어오는데, `_derive_signal_metrics`가 `signal_type=None`에도 `LOW`·`NEUTRAL`·`STABLE`을
돌려주기 때문에 스냅샷이 아예 없는 자산과 실제로 조용한 자산이 같아졌습니다. 운영 중 규칙이
발동하지 않을 때 데이터가 없어서인지 조건을 만족하지 않아서인지 가릴 방법이 없었습니다.

구현은 새 표현 수단을 만들지 않고 기존 경로에 연결했습니다.
`app/domains/alert_engine/snapshot_provider.py`의 `_aggregate_derived_metric`이 `latest`가
`None`인 자산을 집계 대상에서 걸러내고, 남는 자산이 없으면 `None`을 돌려줍니다. 반환 타입은
`_MetricReading | None`으로 바뀌었습니다. `MetricSnapshotProvider.get_snapshot`은
`_read_metric`이 `None`이면 해당 지표를 `values`에 넣지 않고, `AlertEvaluator`의
`_evaluate_condition`은 `metric not in snapshot.values`를 이미 `unavailable_metric`으로
분류합니다. 그래서 호출부와 `MetricSnapshot` 구조는 손대지 않았고, 프로덕션 코드 변경은 5행에
그칩니다.

리뷰는 세 축으로 봤습니다. 값 미제공 판정이 의도한 경우에만 발생하는지, 기존 집계 규칙
(전이 선택과 tie-break, 최고 심각도 선택)이 필터링 이후에도 보존되는지, 그리고 이번 변경이
후속 이슈 #340의 범위를 침범하지 않는지입니다.

## Follow-up Review — Q1 반영 (커밋 e2758c2)

리뷰 Q1에 대해 개발자가 "값 미제공과 부재를 처음부터 구분하지 않은 잘못이며, 사용자나 LLM이
둘의 차이를 파악하지 못하는 문제가 있으므로 enum으로 구분하겠다"고 결정했습니다. 같은
브랜치에 반영했고(`local-review-policy.md`의 Handling Review Feedback), 아래는 그 변경에 대한

### 변경 내용

`MetricUnavailableReason(str, Enum)`을 `app/domains/alert_engine/types.py`에 두고 멤버를
`NO_TARGET`과 `NO_DATA` 두 개로 정했습니다. 대상 자체를 확정하지 못한 경우와 대상은
확정했으나 계산할 데이터가 없는 경우를 가릅니다.

리더 5종(`_derived_signal_metric`·`_price_change`·`_signal_change`·`_position_weight`·
`_earnings_date`)의 반환 타입을 `_MetricResult`(`_MetricReading | MetricUnavailableReason`)로
바꾸고, 기존에 `None`을 돌려주던 지점마다 사유를 배정했습니다. 대상 유형 불일치·`target_id`
없음·정수 파싱 실패·레코드 없음·소유자 불일치는 `NO_TARGET`, 봉 수 부족·스냅샷 전무·포지션
없음·다가오는 실적 없음은 `NO_DATA`입니다.

`MetricSnapshot.unavailable_reasons`와 `AlertEvaluationResult.unavailable_reasons`는 기본값을
가진 추가 필드입니다. `unavailable_metrics`는 형태와 값이 그대로여서 기존 소비처가 영향을
받지 않습니다. evaluator는 스냅샷에 사유가 없으면 `NO_DATA`로 폴백합니다.

### 추가 발견 사항

**S2. `_read_metric`의 fallthrough가 `NO_DATA`로 분류됩니다 — 현재 도달 불가이며 허용
가능합니다.** 리더가 없는 지표는 데이터 부재라기보다 미지원에 가깝지만, `UNSUPPORTED_METRICS`
필터가 앞에서 걸러내므로 실제로는 도달하지 않는 경로입니다. 새 지표를 추가하면서 리더를
빠뜨리면 `NO_DATA`로 조용히 묻힐 여지가 있으니, 지표를 늘릴 때 이 분기를 함께 확인하면
됩니다. 병합을 막지 않습니다.

**Q1(해소). 사유를 API로 노출할지 판단이 필요합니다.** 이번 변경은 엔진 내부 표현까지이며
`AlertEvent` 스키마와 API 응답은 그대로입니다. 리뷰 중 확인한 결과 현재 사유는 평가 결과와
사이클 로그에만 남고 사용자 화면에는 도달하지 않습니다. 알림이 왜 오지 않는지를 사용자나
LLM이 직접 확인해야 한다면 응답 노출이 별도로 필요하며, 그 시점에 스키마 변경을 별도
이슈로 다루면 됩니다. 이번 PR의 병합 판단에는 영향이 없습니다.

**S1(해소).** 최초 리뷰에서 제안한 설계 문서 보완이 이번 커밋에 포함됐습니다.
`docs/designs/alert-rule-event-unified.md` §5에 사유 구분과 다자산 지표의 집계 제외 기준이
함께 기록됐습니다.
