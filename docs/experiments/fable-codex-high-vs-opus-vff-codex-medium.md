# 실험 기록: Fable 5 + Codex(high) vs Opus + VFF(Sonnet) + Codex(medium)

측정일: 2026-07-04 · 대상: BE #138 (LLM Cache) · 기준 커밋: main `b1a4083` ·
출처: 본 세션 실측(타임스탬프·서브에이전트 usage·codex exec 토큰 보고·블라인드 리뷰 산출물)

## 1. 목적

기존 표준 작업 모델(Opus 오케스트레이터 + 설계·리뷰 초안 VFF(Sonnet) 위임 + Codex
medium 구현)과 신규 조합(Fable 5가 설계·검증을 직접 수행 + Codex high 구현)을 동일
이슈로 비교한다. 라운드2(`orchestrator-comparison-round2-vff-sonnet.md`)가 남긴 통제
권고(동일 작업·클린 컨텍스트·사전 정의 지표·블라인드 채점)를 부분 적용한 첫 라운드다.

### 3.2 토큰

| 항목 | 조합 A | 조합 B |
|---|---|---|
| 오케스트레이터 | Opus 약 115.7k (usage 보고) | 측정 불가(메인 세션에 실험 운영 토큰과 혼재) |

이번 라운드는 단가 환산을 생략한다. Fable 5 단가 체계가 기존 라운드의 기준표와 달라

방향성만 기록한다: A는 Anthropic 측 토큰(Opus+Sonnet 합계 212k)이 크고 codex가 싸며,
B는 그 반대다.

## 4. 블라인드 리뷰 결과

| | 조합 A (candidate-1) | 조합 B (candidate-2) |
|---|---|---|
| 점수 | **60 / 100** | **70 / 100** |
| Blocking | 3 | 1 |
| Major | 3 | 3 (그중 2건은 인공 지적 — §6 한계 4) |
| Minor / Nit | 3 / 3 | 5 / 4 |

주요 적발 내용이 우열을 갈랐다.

- **조합 A Blocking**: (1) 모델 무효화를 수동 상수(`LLM_MODEL_POLICY_VERSION`)에
  의존해 `OPENAI_MODEL` 설정 변경 시 이전 모델의 캐시가 조용히 반환됨 — 이슈의
  "model version 변경 시 무효화" 요구와 ADR-011의 "조용히 stale 반환 금지" 제약
  직접 위반. (2) 캐시 조회·저장에 예외 처리가 없어 Redis 장애가 브리핑 API 실패로
  전파됨(fail-closed). (3) 호출부(도메인 서비스 2곳)가 `cache_policy`를 넘기는 opt-in
  구조가 ADR-011의 "호출부가 캐시 존재를 알 필요가 없다" 제약과 충돌.
- **조합 B Blocking**: 빈 응답 `{}`가 정상 결과로 캐싱되어 TTL 동안 고착될 수 있음
  (provider가 빈 content를 `{}`로 반환하는 경계 조건). Major 중 실질 1건은 키 재료
  밖 코드(프롬프트 조립 등) 변경 시 일괄 무효화 수단(캐시 스키마 버전 네임스페이스)
  부재.
- 결함의 성격이 다르다: A의 결함은 **조용한 오답(stale)과 가용성 저하**로 사용자에게
  직접 노출되는 유형이고, B의 결함은 발생 조건이 좁고 실패 방향이 안전한(fail-open,
  추가 miss) 유형이다.

## 5. 정성 비교

| 축 | 조합 A | 조합 B |
|---|---|---|
| 이슈 원문 충실도 | 높음 — user_id·model_policy_version 등 키 요소를 문자 그대로 구현 | 선택적 — user_id 제외·버전 상수를 본문 해시로 대체하고 설계 문서에 이탈 사유 기록 |
| ADR-011 제약 정합 | 호출부 비인지 제약과 충돌(스펙의 `CachePolicy` enum 실사용이 명분) | 게이트웨이 내부 투명 캐시로 제약 준수 |
| 무효화 강건성 | 수동 bump 2곳 의존(누락 시 stale) | 프롬프트·스키마·모델명 본문 해시로 자동 무효화 |
| 장애 격리 | 없음(예외 전파) | Redis 장애·손상 값을 miss로 흡수 |
| 설계 문서 | 280줄, 구성 요소 표 상세 | 172줄, 결정·기각 대안 중심 |
| VFF 초안 품질 | 보정 16건 필요(환각 3건 포함, 예: 존재하지 않는 `.env.example` 항목 서술) | 해당 없음 |

두 조합 모두 절차 규율(브랜치·커밋 규약·보호 파일·검증 4종·ADR-011 Accepted 승격)은
지켰다. 차이는 절차가 아니라 **설계 판단의 질** — 요구사항을 문자 그대로 옮길지,
제약과 충돌하는 요소를 식별해 더 강한 등가물로 대체할지 — 에서 났다.

## 6. 한계

1. **n=1 단일 이슈.** 캐시 계층 구현이라는 특정 유형에서의 결과이며 일반화할 수 없다.
2. **조합 B의 토큰 미격리·웜 컨텍스트.** B의 오케스트레이터는 메인 세션이라 실험 운영
   토큰과 분리되지 않았고, 이 저장소의 축적된 컨텍스트(직전 PR·정책 문서)를 이미
   보유한 상태였다. A는 콜드 스타트로 컨텍스트 수집부터 시작했다 — 시간·품질 모두
   B에 유리한 교란이다.
3. **조합 A의 벽시계 오염.** 서브에이전트 세션 한도로 약 4시간 중단이 끼어 실작업
   시간은 파일 mtime 기반 추정치다.
4. **블라인드의 불완전성.** 익명화를 위해 diff에서 docs를 제외한 탓에 "ADR-011
   미갱신"·"이탈 사유 미기록" 같은 인공 지적이 발생했다(양쪽 대칭 적용, 실제 두
   브랜치 모두 ADR-011을 갱신함). 또 1차 리뷰 라운드는 조합 A의 worktree 잔존물이
   저장소 안에 남아 리뷰어가 A의 갱신된 ADR을 기준 문서로 오독하는 오염이 발견되어
   폐기하고 재실행했다.
5. **판정자 중립성.** 실험 설계자·조합 B 수행자·최종 판정자가 동일 주체(Fable 5)다.
   블라인드 채점으로 완화했으나 리뷰어 역시 같은 모델이라 모델 친화 편향 가능성이
   남는다.
6. **축 미분리.** 오케스트레이터 모델과 codex reasoning effort가 동시에 변해 어느
   축이 품질 차이를 만들었는지 분리할 수 없다(2×2 설계 아님). codex 토큰 +35%가
   high 때문인지 핸드오프 상세도 차이 때문인지도 미상.

## 7. 결론·권고

이 측정 조건에서는 **조합 B(Fable 5 + codex high) 우세**다. 블라인드 점수 70 vs 60,
Blocking 1 vs 3이며, 남은 결함의 실패 방향도 B가 안전하다. 시간도 실작업 기준 절반
이하였으나 §6-2·3의 교란으로 단정할 수 없다.

권고: 조합 B 산출물을 리뷰 적발 사항(빈 응답 미저장·캐시 버전 네임스페이스·TTL 검증·
장애 로그) 반영 후 #138의 머지 후보로 올린다. 조합 전환의 확정은 이질적 작업 유형
(도메인 API 신설·FE 작업)에서 라운드를 반복하고, 가능하면 codex effort 축을 고정한
2×2 부분 설계로 오케스트레이터 축을 분리한 뒤에 판단한다.
