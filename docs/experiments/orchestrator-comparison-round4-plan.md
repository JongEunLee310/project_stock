# 라운드4 실험 계획 — 오케스트레이터 축 단독 비교 (BE #139)

## Status

Executed (2026-07-05) — 결과는 `orchestrator-comparison-round4.md` 참조. 실행 중 발견된
계획 이탈(전역 codex 설정에 의한 effort 통제 실패와 시정)은 결과 문서 §4에 기록했다.

## 목적

라운드3(`fable-codex-high-vs-opus-vff-codex-medium.md`)은 Fable 5+codex(high)가 70 vs 60으로
우세했지만, 결과 해석을 흐리는 교란이 네 가지 있었다.

1. codex effort가 조합과 함께 변해(medium vs high) 품질 차이가 오케스트레이터 덕인지
   codex effort 덕인지 분리되지 않았다.
2. Fable 5 오케스트레이터가 공용 세션에서 돌아 토큰이 격리 측정되지 않았다.
3. 세션 한도 대기(약 4시간)가 벽시계 시간을 오염시켰다.
4. 판정자가 단일이었고 승자와 같은 모델(Fable 5)이었다.

라운드4는 위 네 가지를 각각 통제해 **오케스트레이터(설계 주체) 축만** 분리 비교한다.

품질 차이는 오케스트레이터 축에 귀속된다.

## 통제 변인

- 동일 base: 실행 시점의 최신 `main` 동일 커밋에서 양 브랜치 분기. 분기 커밋 해시를 기록.
- 양 팔 모두 **콜드 전용 컨텍스트**(모델 고정 서브에이전트)로 기동 — 라운드3에서 B가
  가졌던 웜 컨텍스트 이점 제거. 프로젝트 지침 로드 조건은 양 팔 동일.
- **순차 실행**, 팔 전환 시 `git status` clean과 `git worktree list` 잔존물 없음을 확인
  (라운드3 블라인드 리뷰 오염의 재발 방지).
- 시작 프롬프트는 본 문서 §시작 프롬프트의 정본을 그대로 사용한다. 팔 세션에는 본 계획
  문서를 참조시키지 않는다(루브릭 노출로 인한 최적화 편향 방지 — 프롬프트는 자기완결).
- 검증 4종 동일: `uv run ruff check .` / `uv run mypy .` / `uv run pytest` /
  `uv run alembic heads`.

## 측정

### 토큰 (교란 2 해소)

- 오케스트레이터: 팔 전용 서브에이전트의 usage 리포트로 집계한다. 서브에이전트가 해당 팔
  작업만 수행하므로 통제 세션 토큰과 격리된다. (대화형 전용 세션으로 돌릴 경우 세션
  transcript jsonl의 assistant usage 합산으로 대체 — 측정 대상은 동일.)
  input / output / cache 구분이 가능한 범위에서 기록하고 단가 환산은 결과 문서에서 한다.
- VFF(Arm A): 서브에이전트 완료 리포트의 토큰 집계(라운드3과 동일 방식).
- codex: `codex exec` 출력의 token usage(라운드3과 동일 방식).

### 시간 (교란 3 해소)

- 각 팔은 단계 시작·완료마다 단계명과 `date -Iseconds` 스탬프를
  `~/.claude/experiments/round4/checkpoints-{a|b}.log`에 append한다
  (저장소 밖 경로 — diff·커밋 오염 없음). 단계: 세션 시작, 설계 완료, 핸드오프 완료,
  codex 시작, codex 종료, 검증 통과.
- 세션 한도 대기가 발생하면 대기 시작·해제 시각도 스탬프하고 실작업 시간에서 제외한다.
- 한도 리셋 직후 시간대에 시작해 대기 자체를 회피하는 것을 권장한다. 산출물 mtime으로 교차 검증.

### 품질 — 이중 블라인드 판정 (교란 1·4 해소)

- 판정자 2인: **J1** = Claude Code(Fable 5) code-reviewer 서브에이전트(서브에이전트는
  자동 메모리를 로드하지 않아 라운드3 결과 인지가 차단됨), **J2** = `codex exec`
  `model_reasoning_effort=xhigh`.
- 각 판정자가 각 후보를 **독립 컨텍스트에서 절대 채점**(2 판정자 × 2 후보 = 4회) —
  쌍대 제시의 순서 편향을 제거한다.
- 루브릭은 라운드3과 동일: 정확성 40 · 설계 제약 준수 25 · 테스트 25 · 명료성 10.
- diff 익명화: code·tests·config에 **설계 문서를 포함**하되 정체 문자열(브랜치명·조합명·
  모델명·팔 명칭·세션 언급·**위임/서브에이전트 언급**)을 제거하고 후보 라벨(candidate-1/2)을
  무작위 배정한다. 커밋 메시지는 diff에 포함하지 않는다(Co-Authored-By가 모델 정체를 노출).
  라운드3에서 docs 제외로 생긴 인공 지적("ADR 미갱신" 류)을 해소한다.
- 판정자 지시에 "관련 ADR의 미결 질문은 설계 판단으로 취급"을 유지한다.

### 판정 규칙

- 후보별 합산 점수(J1+J2)의 우세 + Blocking 결함의 심각도·실패 방향 서술 비교.
- 판정자 간 승자가 불일치하면 자동 판정하지 않고 네 편의 리뷰 전문을 개발자에게 제시한다.
- 승자 브랜치를 PR + 로컬 리뷰로 제출하고 패자 브랜치는 미머지 보존한다.
  최종 머지 권한은 개발자에게 있다.

## 절차

0. 준비(통제 세션): main 갱신 → 분기 커밋 기록 → `~/.claude/experiments/round4/` 생성 →
   worktree 잔존물·git status 확인.
1. Arm A: 통제 세션이 **모델 고정 서브에이전트**(model=opus, 콜드 컨텍스트)로 §시작
   프롬프트 A를 투입해 기동. 완주 후 서브에이전트 usage 리포트로 토큰을, 체크포인트
   로그로 시간을, 브랜치 커밋 해시를 기록. headless `claude -p` 기동은 통제 세션의
   권한 정책이 거부해 서브에이전트 방식을 채택했다 — 서브에이전트는 자동 메모리를
   로드하지 않아 라운드3 결과 인지가 차단되는 이점이 있고, 라운드3 팔 기동 방식과 같아
   라운드 간 비교에도 유리하다. 대화형 전용 세션과의 차이는 한계에 기록.
2. 전환 점검: git status clean 확인, main 복귀.
3. Arm B: 모델 고정 서브에이전트(model=fable)로 §시작 프롬프트 B를 투입해 동일 기록.
4. 검증(통제 세션): 각 브랜치에서 검증 4종을 독립 재실행(팔의 자기 보고에 의존하지 않음).
5. 판정: 익명화 diff 생성 → J1 2회 + J2 2회 → 집계.
6. 기록: 라운드4 결과 문서 작성(측정치·채점·한계), 승자 PR에 동봉.

## 시작 프롬프트 (정본)

두 프롬프트는 설계 주체 지시(2번 항목)만 다르고 나머지는 동일하다.

### Arm A (Opus 세션)

> BE 이슈 #139(위험도 Escalation 엔진)를 구현해줘. 절차:
> (1) 최신 main에서 `experiment/139-escalation-opus` 브랜치를 생성한다.
> (2) 설계 문서 스켈레톤을 docs/designs에 작성한다 — 설계 초안은 value-for-fable:itsvff
> 서브에이전트에 위임하고, 검토·확정은 직접 한다.
> (3) .codex/tasks에 핸드오프 문서를 작성한다.
> (4) codex exec로 구현을 위임한다. reasoning effort는 기본값(medium)을 유지하고 올리지
> 않는다. 실행 전 `export PATH="$HOME/.nvm/versions/node/v22.23.1/bin:$PATH"`,
> `--sandbox workspace-write` 사용. 신규 의존성이 필요하면 codex 밖에서 `uv add` 후 재실행.
> (5) 검증 4종(`uv run ruff check .` / `uv run mypy .` / `uv run pytest` /
> `uv run alembic heads`)을 통과할 때까지 수정한다.
> (6) 브랜치에 커밋한다. push와 PR 생성은 하지 않는다.
> 각 단계의 시작·완료 시 단계명과 `date -Iseconds` 스탬프를
> `~/.claude/experiments/round4/checkpoints-a.log`에 append한다. 세션 한도 대기가 발생하면
> 그 시각도 기록한다. 이 작업 외 다른 작업은 하지 않는다.

### Arm B (Fable 5 세션)

> 위와 동일하되 (2)를 "설계 문서 스켈레톤을 docs/designs에 직접 작성한다(서브에이전트
> 위임 없이)"로, 브랜치를 `experiment/139-escalation-fable`로, 로그 파일을

## 예고된 한계

- n은 여전히 1 — 이번 라운드로도 전환 확정이 아니라 근거 축적이다.
- J1이 Arm B와 같은 모델이다. 현재 가용한 최상위 모델이 Fable 5인 이상 제거 불가하며,
  J2(codex xhigh) 교차 판정으로 완화한다.
- 순차 실행이라 두 팔의 실행 시간대·한도 상태가 완전히 같지는 않다.
- 오케스트레이터 축 안에 "모델(Opus vs Fable 5)"과 "위임 구조(VFF 위임 vs 직접)"가 함께
  묶여 있다. 이 두 축의 분리(예: Fable 5+VFF, Opus 직접 팔)는 후속 라운드 과제다.
- 루브릭 비노출은 완전하지 않다. 라운드3 기록(루브릭 포함)이 저장소에 커밋되어 있고 자동
  메모리 색인에도 실험 이력이 있어 팔 세션이 원리상 접근 가능하다. 프롬프트로 유도하지
  않으며 노출은 양 팔에 대칭이다.
- 익명화는 문자열 수준이다. 설계 문서의 문체·구성 습관이 모델 정체를 시사할 수 있고,
  J1이 같은 모델의 문체를 선호하는 편향은 제거하지 못한다(J2 교차로 완화).
- 팔이 서브에이전트로 돌아 대화형 전용 세션(자동 메모리·스킬 로드)과 실사용 조건이
  완전히 같지는 않다. 양 팔 대칭이며, 자동 메모리 미로드는 블라인드 측면에서는 이점이다.
