# BE 설계: 에이전트 파이프라인 집계 지표 확장 — 이슈 #394

상태: **설계 확정** — 2026-07-23. 에픽 #307 후속(세부 수정). 선행 계약은
`docs/designs/307-news-intelligence-phase2.md` §2.4·§3.6.

이 문서는 `GET /api/v1/news-insights/agent-runs` 응답에 추가할 집계 지표의 범위와 산출 근거를
스켈레톤 수준으로 확정한다. 필드와 산출 정의만 담고 구현 코드는 담지 않는다.

## 배경

설계 이미지(`news-instight.png`)의 `에이전트 파이프라인` 패널 하단에는 집계 5종이 있다.

```text
수집 소스 1,248 | 오늘 처리 건수 48,672 | 이벤트 추출 312 | 평균 처리 지연 3분 21초 | 정확도 92.3%
```

현재 `AgentRunsResponse`는 `processed_documents`·`extracted_events`·`active_topics` 3종만
제공한다. 프론트엔드는 없는 수치를 지어내지 않으므로 나머지 세 칸을 `—`로 비워 두고 있다.

세 칸의 성격이 서로 다르다. **두 개는 이미 있는 데이터에서 산출되고, 하나는 정의 자체가 없다.**
이 문서는 그 구분을 확정하는 것이 목적이다.

## 1. 산출 가능성 판정

| 설계 라벨 | 판정 | 근거 |
|---|---|---|
| 수집 소스 | 산출 가능 | `source_documents.source_name` 보유 |
| 오늘 처리 건수 | 기존 필드 | `processed_documents` |
| 이벤트 추출 | 기존 필드 | `extracted_events` |
| 평균 처리 지연 | **부분** 산출 가능 | `agent_runs.started_at`·`finished_at` 보유. 아래 §3 참조 |
| 정확도 | **산출 불가** | 정의 없음. 아래 §4 참조 |

스키마 변경은 필요 없다. 두 지표 모두 기존 컬럼에서 파생한다. 마이그레이션도 없다.

## 2. `collected_sources` — 수집 소스

- 타입: `int`(`ge=0`).
- 정의: `source_documents`의 **고유 `source_name` 개수**. 시간 구간으로 자르지 않는다.
- 의미: 시스템이 실제로 문서를 받아 온 출처의 수. run 단위 지표가 아니라 수집 범위 지표다.

### run 구간으로 자르지 않는 이유

초안은 최근 run의 `started_at` ~ `finished_at` 사이에 `collected_at`이 들어오는 문서로 한정했다.
**이 정의는 틀렸다.** run은 자기가 도는 동안 들어온 문서가 아니라 **그 전에 쌓인 문서를 처리**한다.
run 구간으로 자르면 처리 대상과 무관한 집합을 세게 된다.

시드 데이터가 이 오류를 그대로 드러냈다. 문서는 기준 시각 1시간 55분·1시간 25분 전에 수집되고
run은 15분 전에 시작해 2분 전에 끝난다. 겹치는 구간이 없어 값이 `0`이 된다. 화면에는
`수집 소스 0`이 뜨는데, 이는 출처가 없다는 **거짓 진술**이다. 값을 모른다는 `—`보다 나쁘다.

`source_documents`에는 `agent_run_id`가 없어 run과 문서를 직접 이을 방법이 없다. 없는 연결을
시간으로 흉내 내는 대신, 연결이 필요 없는 정의를 쓴다. 설계 이미지의 `수집 소스 1,248`도 run
하나가 처리한 수가 아니라 수집 대상 출처의 규모로 읽힌다.

run 단위 출처 수가 필요해지면 `source_documents`에 `agent_run_id`를 두는 것이 선행이다(#391).

## 3. `average_run_duration_seconds` — 평균 처리 시간

- 타입: `int | None`. 완료된 run이 하나도 없으면 `null`.
- 정의: 최근 **완료된** run 최대 20건의 `finished_at - started_at` 평균(초, 반올림).
- 대상: `finished_at`이 `null`이 아닌 `agent_runs`. `started_at` 내림차순 20건.

**이름을 `delay`로 두지 않는다.** 지연은 기준 시간과의 차이인데 목표 처리 시간이 정의된 적이
없다. 목표 없이 소요 시간을 `지연`이라 부르면 없는 기준이 있는 것처럼 읽힌다. 계약은 실제로
측정한 값의 이름을 쓰고, 화면 라벨과의 차이는 아래 후속으로 남긴다.

건수 상한 20건은 시계에 의존하지 않고 결과를 결정적으로 만들기 위한 값이다. 24시간 같은 시간
창을 쓰면 조회 시각에 따라 표본이 흔들려 테스트가 시각에 묶인다.

## 4. 정확도 — 이번 범위에서 제외

무엇에 대한 정확도인지 정의가 없다. 후보는 최소 세 가지다.

- 추출 이벤트의 검수 통과 비율
- 토픽 분류가 사후 판정과 일치한 비율
- 인사이트 예측이 이후 가격·수급으로 확인된 비율

어느 쪽이든 **정답 레이블을 기록하는 테이블이 먼저 있어야 한다.** 현재 도메인에 검수 결과나
사후 판정을 담는 자리는 없다. 정의 없이 숫자를 만들면 화면에 근거 없는 신뢰를 만들어 내므로
이번 범위에서 제외한다. 화면은 계속 `—`로 둔다.

정의가 서면 별도 이슈로 다룬다. 선행은 실제 파이프라인 실행 기록(#391)이다.

## 5. API 계약 변경

`GET /agent-runs` 응답에 두 필드를 **추가**한다. 기존 필드는 그대로 둔다.

```text
last_processed_at, processed_documents, extracted_events, active_topics,
collected_sources(신규), average_run_duration_seconds(신규, nullable),
stages[], analysis_version, has_delay
```

`active_topics`는 화면에서 빠졌지만 계약에서 제거하지 않는다. 다른 소비자가 생길 수 있고,
제거는 되돌리기 어려운 변경이다.

## 6. 후속

- 화면 라벨 `평균 처리 지연`은 실제로 처리 **소요 시간**이다. 라벨 정정은 프론트엔드 표현
  변경이므로 이번 범위 밖이며, 프론트엔드 세부 수정 라운드에서 함께 다룬다.
- run–문서 연결(`agent_run_id`)과 정확도 정의는 실제 수집·추출 파이프라인(#391) 이후가 적기다.
  연결이 생기면 `collected_sources`를 run 단위로 좁힐지 다시 판단한다.

## 7. ADR·실패 기록 판단

- ADR: 기존 테이블에서 파생하는 응답 필드 추가이고 와이어 컨벤션도 그대로이므로 **불요**.
  다만 `정확도`를 정의 없이 만들지 않는다는 판단은 ADR-009(사실·추론 분리)의 연장이다.
- 실패 기록: 해당 없음. 실패한 접근을 대체한 것이 아니라 계약 부족을 메우는 작업이다.
