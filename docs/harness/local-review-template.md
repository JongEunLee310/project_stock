# Local Review Template

`docs/reviews/pr-<number>.md`를 작성할 때 쓰는 정본 템플릿입니다. `local-review-policy.md`가
정한 고정 7섹션을 실제 문서 형태로 구체화한 것이며, 리뷰 기록은 예외 없이 이 형식을 따릅니다.

기준 예시는 `docs/reviews/pr-210.md`입니다. 형식 판단이 애매할 때는 그 기록을 참조합니다.

## Skeleton

아래 골격을 그대로 복사해 채웁니다. 섹션 헤더와 순서는 변경하지 않습니다.

```markdown
# PR #<number> 로컬 리뷰 — <PR 제목> (#<이슈번호>·#<이슈번호>)

## Review Summary

<이 PR이 무엇을 하는지 한두 문장으로 요약합니다. 커밋이 여러 건이면 구성을 밝힙니다.>

**Part A — <부제>(<이슈번호>, <설계 Decision 또는 근거>).** <재사용한 기존 코드, 새로 추가된
것, 핵심 메커니즘, 계약 변경 사항을 산문으로 설명합니다.>

**Part B — <부제>(<이슈번호>, <근거>).** <위와 같은 방식으로 설명합니다.>

<이번 리뷰를 어떤 축으로 봤는지 한 문장으로 밝힙니다.>

## Blocking

None.

## Suggestions

**S1. <한 줄 제목> — <심각도와 처리 판단>.** <근거를 설명하고, 왜 병합을 막지 않는지 또는
현재 범위에서 왜 허용 가능한지를 명시합니다. 후속 조치가 필요하면 무엇을 언제 하면 되는지
적습니다.>

## Questions

**Q1. <한 줄 제목>.** <무엇이 불확실한지, 누구의 판단이 필요한지 적습니다. 리뷰 중에 직접
확인해 해소했다면 확인 방법과 결과를 적고 해소됐음을 밝힙니다.>

## CI Result

<검증을 누가 언제 실행했는지 밝히고, 명령별 실제 출력과 수치를 적습니다.>

- `<명령>` — <결과와 수치>

GitHub Actions(<workflow 이름>) — <결과와 소요 시간, run/job 링크 또는 번호>.

## Documentation Impact

<문서 갱신이 필요한지 판단하고 근거를 답니다. 이번 PR에서 이미 갱신된 문서가 있으면
나열합니다. ADR 필요 여부와 Failure Record 필요 여부를 각각 명시하고, 불필요하다면 왜
불필요한지 근거를 답니다.>

## Final Recommendation

<머지 가능 여부를 먼저 밝힙니다. 그다음 무엇을 항목별로 확인했는지, 범위가 지켜졌는지,
Protected Files가 보존됐는지, 추가된 테스트가 무엇을 덮는지를 근거로 답니다. 마지막에
Blocking·Suggestions·Questions의 처리 상태를 다시 진술해 머지 판단이 모호하지 않게 합니다.>

최종 머지 권한은 개발자에게 있습니다.
```

## Section Conventions

### 제목 줄

`# PR #<number> 로컬 리뷰 — <PR 제목> (#<이슈번호>)` 형식으로 씁니다. PR 제목과 관련
이슈 번호를 제목 줄에 담고, 별도의 메타데이터 목록 블록은 두지 않습니다. 이슈가 여러
건이면 가운뎃점으로 잇습니다.

### Review Summary

리뷰어가 아니라 나중에 이 기록을 읽는 사람을 위한 섹션입니다. diff를 열지 않고도 변경을
파악할 수 있어야 합니다. 다음을 산문으로 담습니다.

- 이 PR이 무엇을 하는지, 커밋이 여러 건이면 어떤 구성인지.
- 재사용한 기존 코드와 새로 추가된 것의 구분.
- 핵심 메커니즘. 파일 경로·함수·설정 키 같은 식별자를 그대로 적어 밀도를 유지합니다.
- 계약 변경이 있으면 변경 전후를 명시합니다.

변경이 뚜렷하게 둘 이상의 덩어리로 나뉘면 **Part A**·**Part B**로 나눠 각 덩어리의 부제와
해당 이슈 번호, 설계 Decision 근거를 볼드 도입부에 담습니다. 단일 관심사 PR이면 나누지
않고 이어서 씁니다.

마지막에 이번 리뷰를 어떤 축으로 봤는지 한 문장으로 밝힙니다.

### Blocking · Suggestions · Questions

세 섹션 모두 발견 사항을 번호로 구분합니다. Blocking은 `B1`, Suggestions는 `S1`,
Questions는 `Q1`부터 매깁니다. 비어 있으면 `None.` 한 줄만 둡니다.

각 항목은 **볼드 한 줄 제목**으로 시작하고, 제목 자체가 처리 판단을 담습니다. 관찰만
적고 끝내지 않습니다.

```
**S1. INCR→EXPIRE 비원자성 — 낮은 위험, 후속 판단 사항.**
**S2. 클라이언트 실패 시에도 카운트 소비 — 설계상 허용된 보수적 카운팅, 운영 시 인지 필요.**
```

제목 뒤 본문에는 근거와 판단을 함께 답니다. 판단은 설계 문서, 핸드오프, 이슈, 스펙 조항
같은 근거에 묶어 감사 가능하게 만듭니다. 의견이 아니라 확인된 사실로 읽혀야 합니다.

Blocking과 Suggestions의 구분은 정직하게 유지합니다. Blocking은 머지 전에 반드시 고쳐야
하는 항목이고, Suggestions는 선택적이거나 후속 사항입니다. 후속 사항을 Blocking으로
부풀리지 않고, 실제 Blocking을 Suggestions에 묻지 않습니다.

Questions는 작성자나 사람의 판단이 필요한 항목입니다. 리뷰 중에 직접 확인해 해소할 수
있으면 확인하고, 확인 방법과 결과를 적은 뒤 해소됐음을 밝힙니다.

### CI Result

"통과"만 적지 않습니다. 검증을 누가 실행했는지 밝히고, 명령별 실제 출력과 수치를 답니다.
구체적인 숫자가 있어야 검증이 실제로 이뤄졌음을 나중에 확인할 수 있습니다.

- 테스트는 통과 건수를 적고, 직전 PR 대비 증감을 알면 함께 적습니다.
- 타입 검사는 검사한 파일 수를 적습니다.
- 마이그레이션이 있는 변경은 단일 head 여부와 revision을 적습니다.
- GitHub Actions 결과는 workflow 이름·소요 시간·run 식별자와 함께 적습니다.

검증 명령은 저장소마다 다릅니다. 백엔드는 `uv run ruff check .`·`uv run mypy .`·
`uv run pytest`를 쓰고, 스키마 변경이 있으면 `uv run alembic heads`를 더합니다.

### Documentation Impact

문서 갱신 필요 여부를 판단하고 근거를 답니다. 이번 PR에서 이미 갱신된 문서가 있으면
나열해 무엇이 정본 상태인지 분명히 합니다. 설계 문서의 Status 전환이 필요하면 그것도
적습니다.

ADR 필요 여부와 Failure Record 필요 여부를 각각 명시합니다. 불필요하다는 판단도 근거를
답니다. 기존 ADR의 구체화인지 새로운 방향 선택인지, 계획된 구현인지 사후 대응인지가
판단 기준입니다.

### Final Recommendation

머지 가능 여부를 먼저 밝히고 그 근거를 답니다. 다음을 포함합니다.

- 설계 Decision이나 핸드오프 요구사항과 구현의 일치를 항목별로 확인한 결과.
- 범위가 지켜졌는지, 회귀 위험이 낮다고 보는 근거.
- Protected Files가 변경되지 않았음을 diff에서 확인한 사실.
- 추가된 테스트가 무엇을 덮는지.

마지막에 Blocking·Suggestions·Questions의 처리 상태를 다시 진술해 머지 판단이 모호하지
않게 합니다. 닫는 문장은 정확히 다음과 같이 씁니다.

> 최종 머지 권한은 개발자에게 있습니다.

## Language and Tone

본문 산문은 한국어로 쓰고, 섹션 헤더·Status 라벨·`None.`·코드 기호는 영어로 유지합니다.
`~합니다` 체를 쓰되 과하게 격식적이거나 구어적인 표현은 피합니다. 직역투, 서술어가 빠진
명사형 종결, 화살표로 절을 잇는 표기, 한 명사에 수식어를 겹겹이 쌓는 문장은 쓰지 않습니다.
상세 원칙은 `design-record-policy.md`를 따릅니다.
