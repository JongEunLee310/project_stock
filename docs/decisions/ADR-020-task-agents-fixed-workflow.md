# ADR-020: Task Agents as Fixed Workflows — 관심종목 분석 흐름을 일일 리서치 에이전트로 대체

## Status

Accepted — 개발자가 2026-10-12 PR #467 리뷰 Q1에서 머지를 승인으로 보기로 했다.

## Context

ADR-018로 RAG 기반(pgvector, 로컬 임베딩, 근거 검색, 인용 검증)을 만들고 첫 기능으로 종목 리서치 Q&A를
붙였다(에픽 #438). 그런데 사용자가 원한 "에이전트"는 질문에 답하는 대화형이 아니라, **특정 작업을
스스로 수행하는 작업형 에이전트**였다(2026-10-12). 사용자는 네 가지 작업을 맡기기로 했다(에픽 #459).

1. 관심종목 일일 리서치
2. 공시·실적 분석
3. 투자 가설 감시
4. 뉴스 인텔리전스 파이프라인

이 ADR은 네 에이전트에 공통으로 적용할 실행 방식과 경계를 정하고, 첫 에이전트가 기존 관심종목 분석
흐름(`WatchlistAnalysisService`, 설계 019)을 대체한다는 결정을 기록한다.

기존 흐름의 상태는 다음과 같다.

- 기사마다 LLM 요약과 가설 충돌 판단을 하고, 기사마다 리서치 리포트를 만들고, 규칙 엔진으로 신호와
  알림을 만든다.
- 정기 스케줄 4개가 등록돼 있지만 `ANALYSIS_SCHEDULE_ENABLED=False`가 기본값이라 돌지 않는다. 실제
  산출물은 리포트 44건(마지막 2026-07-13), 신호 6건(마지막 2026-07-09)이다.
- 규칙 엔진의 두 규칙은 기사별 LLM 결과(`news_items.impact_level`·`sentiment`)와 가설 충돌 결과에
  의존한다.

## Decision

### 1. 작업형 에이전트는 고정 워크플로로 만든다

작업 단계(수집 → 근거 검색 → 분석 → 기록)는 코드로 고정하고, 단계 안의 요약·판단·비교만 LLM이
맡는다. LLM이 도구를 골라 반복 호출하는 자율 도구 호출형은 쓰지 않는다. 실행 경로가 매번 같아 결과를
검증하기 쉽고, 비용을 대상 수로 예측할 수 있으며, 지금의 동기 구조와 스케줄러(ADR-003, ADR-007)
위에서 돈다. 고정 워크플로로 해결되지 않는 작업이 생기면 그 작업에 한해 자율형을 검토하며, 그때는
ADR-018 T1(실행 모델 충돌)에 따라 분리를 함께 검토한다.

### 2. 에이전트의 위치

코드는 `app/domains/agents/{agent}/`에 둔다. 공통 부품(실행 기록, 대상별 실패 격리 등)은 두 번째
에이전트를 만들 때 실제로 겹치는 부분만 `app/domains/agents/`로 올린다. 미리 프레임워크를 만들지 않는다.
에이전트는 다른 도메인의 service·repository 공개 함수와 RAG 부품(ADR-018)을 조합하며, 다른 도메인
테이블을 직접 쿼리하지 않는다.

### 3. 공통 경계

- **산출물만 쓴다.** 에이전트는 자기 산출물(리포트, 신호, 알림, Obsidian 노트)과 분석 결과 필드만
  쓴다. 사용자가 작성한 데이터(투자 가설, 판단 기록 본문)는 바꾸지 않는다. 판단 기록 상태 전이처럼
  사용자 데이터에 영향을 주는 동작은 해당 에이전트를 설계할 때 사용자와 따로 정한다.
- **수치는 DB 값 그대로 쓴다.** 가격, 일정 같은 수치는 LLM이 만들지 않는다. LLM은 해석과 종합만 맡고,
  모든 주장에 근거를 인용하며, 인용은 검증한다.
- **매수·매도를 권유하지 않는다.**
- **실패를 격리한다.** 한 대상(종목 등)의 실패가 다른 대상의 처리를 막지 않는다.
- **클라우드 경계를 지킨다.** LLM 입력은 CloudSafe projection(ADR-009)으로만 보내고, 사용자 작성
  텍스트가 들어가면 마스킹(ADR-019)을 거친다.

### 4. 관심종목 분석 흐름을 일일 리서치 에이전트로 대체한다

| 기존 산출물 | 대체 후 |
|---|---|
| 기사별 LLM 요약(`news_items.summary` 등) | 없앤다. 종목당 하루 1회 종합으로 대체한다 |
| 기사별 영향도·감성(`impact_level`·`sentiment`) | 종합 호출의 출력에 새 기사별 영향도·감성을 함께 담아 기록한다(LLM 호출 수는 늘지 않음) |
| 가설 충돌 판단 | 에이전트 3(투자 가설 감시)으로 넘긴다. 그때까지 공백이다 |
| 기사별 리서치 리포트 | 종목·날짜당 하나의 일일 브리프 리포트(`report_type=DAILY_BRIEF`)로 바꾼다 |
| 규칙 엔진 신호·알림 | 유지한다. `HighImpactNewsRule`은 위 영향도로 계속 동작하고, `ThesisConflictRule`은 에이전트 3 전까지 발동하지 않는다 |
| 트리거(관심종목 추가, 스케줄 4개, 워커 API) | 관심종목 추가 시 해당 종목 즉시 실행, 평일 07:30 KST 1회, 워커 API 수동 실행 |

기존 `WatchlistAnalysisService`, 분석 스케줄 4개, `ANALYSIS_SCHEDULE_ENABLED`는 제거한다. 설계 019는
대체됨(superseded)으로 표시한다.

## Alternatives

- **자율 도구 호출형 에이전트.** 보류. 유연하지만 실행마다 경로가 달라 검증이 어렵고 비용이
  들쭉날쭉하다. 다회 루프와 장시간 실행은 ADR-018 T1 분리 트리거에 해당한다.
- **기존 분석 흐름을 켜고 그 위에 종합 단계를 얹기.** 기각. 사용자가 대체를 선택했다. 기사마다 LLM을
  호출하는 비용이 기사 수에 비례하고, 같은 일을 하는 경로가 둘로 갈라진다.
- **신호를 에이전트 1에서 빼기.** 기각. 종합 호출에 영향도 판정을 더하면 추가 호출 없이 신호와
  알림을 유지할 수 있다.
- **에이전트 공통 프레임워크를 먼저 만들기.** 보류. 에이전트 하나만 있는 지금 만든 추상화는 추측이다.
  두 번째 에이전트에서 실제로 겹치는 부분만 올린다.

## Consequences

- 쉬워지는 것: 네 에이전트가 같은 원칙(고정 워크플로, 산출물만 쓰기, 수치는 DB 값, 인용 검증) 위에서
  만들어진다. 일일 LLM 비용이 종목 수에 비례해 예측 가능하다.
- 어려워지는 것과 위험
  - 기사별 요약이 사라져 `news_items.summary`가 새로 채워지지 않는다. 이 필드를 쓰는 화면은 제목으로
    대체 표시해야 한다.
  - 가설 충돌 신호가 에이전트 3 전까지 생성되지 않는다(지금도 기존 흐름이 꺼져 있어 실제로 잃는 것은
    적다).
  - 영향도 판정을 종목 단위 종합 호출 안에서 하므로, 기사 수가 많은 날에는 판정 품질이 떨어질 수 있다.
    종합에 넘기는 새 기사 수에 상한을 둔다.
- `research_reports` 스키마가 바뀐다(컬럼 추가). 기존 리서치 큐와 리포트 API는 그대로 동작해야 한다.
