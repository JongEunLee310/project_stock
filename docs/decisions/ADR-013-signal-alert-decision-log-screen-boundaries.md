# ADR-013: Signals / Alerts / Decision-Log 3-화면 책임 분리

## Status

Proposed

## Context

시그널 재설계 라운드에서 사용자가 "알림함과 시그널 목록의 내용이 동일하다"는 혼선을
제기했다(#253). 원인은 현재 `Alert`가 자체 콘텐츠 없이 `signal_id` + `dedup_key` + 읽음
상태만 가진 시그널의 1:1 래퍼이고(`app/domains/alerts/model.py`), 분석 파이프라인이 시그널마다
알림을 1:1로 생성하기 때문이다(`AlertService.create_alert`). 그 결과 Signals 화면과 Alerts
화면이 같은 내용을 보여주며, 사용자가 "분석 화면"인지 "설정 화면"인지 구분하지 못한다.

세 화면의 성격은 근본적으로 다르다.

- **시그널** = 시스템이 발견한 투자 판단 후보(분석 결과). "무엇을 봐야 하는가."
- **알림** = 사용자가 놓치지 않도록 전달하는 통지 장치(전달 조건과 채널). "언제 알려줄 것인가."
- **판단 기록** = 사용자가 남긴 투자 판단 로그. "나는 왜 그렇게 판단했는가."

비유하면 시그널은 레이더에 잡힌 물체, 알림은 관제사에게 울리는 경고음, 판단 기록은 관제사가
남긴 대응 로그다. 레이더에 잡혔다고 항상 사이렌을 울리지 않고, 사이렌은 여러 조건을 종합해
울릴 수 있다. 이 경계가 흐려지면 Signals 화면에 알림 규칙·채널·발송 내역이 섞여 들어가
분석 화면이 설정 화면처럼 변한다.

## Decision

세 화면의 책임을 분리하고, 각 화면의 정본 데이터와 사용자 행동을 다음과 같이 고정한다.

### 1. Signals 화면 = 분석 결과 탐색(읽기 중심)

- 중심 데이터: 시그널 유형, 신뢰도(score), 발생 이유·근거, 관련 지표, 우선순위, 최근 변경,
  마지막 업데이트.
- 사용자 행동: 근거 보기, 판단 기록 작성, 종목 리서치 이동, 관심종목 추가.
- **금지**: 알림 채널 선택, 이메일/디스코드/슬랙 설정, 알림 규칙 테이블, Rule Builder,
  최근 알림 발송 내역. 이들은 Alerts로 보낸다.
- 알림 관련 요소는 **보조 버튼 하나**("이 시그널 변화 알림 받기")만 허용한다.

### 2. Alerts 화면 = 알림 조건/채널 관리

- 중심 데이터: 알림 규칙 목록, 조건, 대상 종목/범위, 채널, 활성 여부, 최근 발생 이력.
- 사용자 행동: 규칙 생성·수정·일시정지, 채널 설정, 최근 알림 보기.

### 3. Decision Log 화면 = 판단 기록(ADR-006 도메인)

- 기존 `decision_logs` 도메인이 담당한다. 본 ADR은 경계만 확인한다.

### 4. 도메인 모델 방향

현재 `Alert`(시그널 1:1 래퍼)는 목표 모델에서 두 개념으로 분리한다.

- **`AlertRule`** — 조건(`SIGNAL_CHANGED`·`NEWS_RISK`·`PRICE_CHANGE` 등)·대상 범위
  (`WATCHLIST`·`PORTFOLIO`·`SYMBOL`)·채널(`APP`·`EMAIL`·`DISCORD`·`SLACK`)·활성 여부.
- **`AlertEvent`** — 규칙 충족으로 실제 발생한 통지 기록(대상 종목·제목·메시지·심각도·
  전달 채널·발생/읽음 시각).

현재의 `Alert`는 사실상 규칙 없이 발생만 있는 축약된 `AlertEvent`에 가깝다. 상세 필드·enum·
마이그레이션·기존 데이터 처리는 후속 설계 문서에서 확정한다(본 ADR은 방향만 고정).

### 5. 두 화면의 연결 지점

완전 단절이 아니라 단방향 연결을 둔다. Signals 카드의 보조 버튼
"이 시그널 변화 알림 받기"를 누르면 Alerts의 Rule Builder로 이동하며 조건이 미리 채워진다
(예: `WHEN symbol=TSLA AND signal_type=RISK_ALERT THEN APP`). 관계는 유지하되 화면 책임은
섞이지 않는다.

## Alternatives

- **현행 유지 + 화면에서 읽음관리 용도로만 차별화.** 기각: 콘텐츠가 동일한 근본 원인을
  해소하지 못한다. 알림이 여전히 시그널의 그림자다.
- **알림 = 고심각도 시그널만 선별 생성(RISK_ALERT·THESIS_BROKEN 또는 score 임계 이상).**
  부분 개선이지만 여전히 "알림 = 시그널 부분집합"이라 규칙/채널이라는 알림 고유 의미를
  주지 못한다. 선별 로직은 향후 `AlertRule` 기본 규칙으로 흡수 가능하다.
- **AlertRule/AlertEvent 즉시 전면 구현.** 범위가 커 이번 라운드에서 기각. 경계를 ADR로
  먼저 고정하고 구현은 후속 이슈로 단계화한다.

## Consequences

- 쉬워지는 것: Signals 화면이 분석에 집중해 사용자가 할 일(근거 확인 → 판단 기록)이
  명확해진다. Alerts가 규칙/채널이라는 고유 책임을 갖는다. FE 타입도 `Signal`·`AlertRule`·
  `AlertEvent`로 분리돼 화면 책임이 코드에 드러난다.
- 어려워지는 것: Alerts 도메인을 래퍼에서 규칙/이벤트 체계로 재편해야 한다(BE 신규 계약·
  마이그레이션·기존 `Alert` 데이터 처리). FE Alerts 화면 재설계가 필요하다.
- 위험: 기존 `Alert` 소비처(알림함·읽음 상태)와의 하위호환. 전환 중 계약 병존 구간 관리.

## Follow-up

- 상세 설계는 `docs/designs/alert-rule-event-unified.md`에서 확정한다(필드·enum·API 계약·엔진·
  마이그레이션·기존 인프라 흡수). 본 ADR이 위임한 후속 설계 문서다.
- 후속 구현 이슈로 단계화한다.
  1. **BE #255**(재개): `AlertRule` + `AlertEvent` + `AlertDelivery` + `NotificationChannel`
     통합 모델·마이그레이션. #255는 미이행 상태로 닫혔으므로 통합 모델 도입 이슈로 재개하며,
     규칙/이벤트/채널/엔진은 BE 에픽 하위 서브이슈로 분해한다.
  2. **FE #133**: Alerts 화면을 규칙/채널/이벤트 관리로 재설계(BE 계약 선행). 알림 아이콘
     교체(♧→FiBell)와 감시망 설정실 위젯을 서브이슈로 분해한다.
  3. **FE #134**: Signals 카드의 "알림 설정"을 보조 버튼 "이 시그널 변화 알림 받기"로 교체하고
     Alerts Rule Builder로 조건 prefill deep-link.
- 관련 지표(`relatedMetrics`) 노출은 시그널 재설계 로드맵 3단계(근거 불릿·구조화)에 포함한다.
