# ADR-019: Free-Text Masking at the Cloud Boundary — ADR-009 보완

## Status

Proposed — complements ADR-009.

## Context

ADR-009는 클라우드 경계에서 원본 entity를 금지하고, 허용된 필드만 담는 화이트리스트 CloudSafe
projection을 요구한다. 이 방식은 **어떤 필드가 나가는지**를 통제한다. 하지만 **필드 안에 무엇이
들어 있는지**는 통제하지 못한다.

사용자가 직접 쓰는 자유 텍스트 필드가 이 틈에 해당한다.

- 리서치 Q&A 질문(`ResearchQASnapshot.question`, #442)
- 판단 기록 작성 보조의 가설·이유·메모(`DecisionAssistSnapshot.thesis`·`rationale`·`memo`, #356)

이 필드들은 기능상 클라우드로 보내야 하지만, 사용자가 "삼성전자 300주를 평단 7만 원에 샀는데"처럼
보유 수량·금액이나 연락처·계좌번호를 적으면 ADR-009가 막으려던 정보가 그대로 나간다. PR #453
리뷰 Q2에서 이 문제를 제기했고, 사용자가 2026-10-12 "민감한 정보가 있으면 마스킹 후 전송"하기로
결정했다(#456).

## Decision

### 1. 마스킹은 화이트리스트의 보완이다

ADR-009의 화이트리스트 원칙은 그대로 둔다. 구조화된 데이터는 여전히 projection으로만 내보낸다.
마스킹은 화이트리스트로 허용된 필드 가운데 **사용자가 쓴 자유 텍스트**의 내용에만 추가로 적용한다.
ADR-009가 기각한 "entity 필드를 벗기는 denylist"와는 대상이 다르다. 여기서 가리는 것은 필드가 아니라
필드 안의 문자열 조각이다.

### 2. 자유 텍스트 필드는 projection에 선언한다

`CloudSafePayload` 하위 타입은 사용자 작성 자유 텍스트 필드를 `free_text_fields` 클래스 변수로
선언한다. 공개 데이터(뉴스 제목, 발췌 등)는 선언하지 않는다. 공개 사실 속 금액("300억 달러 계약")을
가리면 답변 품질만 떨어지기 때문이다.

### 3. 게이트웨이 안에서 강제한다

마스킹은 각 호출부가 아니라 `LLMGateway`가 클라우드로 라우팅할 때 `PrivacyGate` 단계에서 적용한다.
ADR-009 §4의 단일 choke point와 같은 이유다. 호출부가 마스킹을 잊어도 우회할 수 없다. 로컬로
라우팅되는 작업, 로컬 임베딩, Obsidian 노트처럼 데이터가 프로세스나 기기를 떠나지 않는 경로에는
적용하지 않는다(ADR-009 §4의 로컬 면제와 일관).

### 4. 범위와 방식

규칙(정규식) 기반으로 가리고, 의미를 남기는 자리표시자로 바꾼다. LLM이 질문 의도를 계속 이해할 수
있게 하기 위해서다.

| 범주 | 적용 조건 | 자리표시자 |
|---|---|---|
| 이메일, 전화번호, 주민등록번호, 계좌번호, 카드번호 | 항상 | `[이메일]`, `[전화번호]` 등 |
| 보유·거래 수량(예: 300주, 100 shares) | 개인 맥락 표지와 함께 나올 때 | `[수량]` |
| 금액·평단가(예: 7만 원, $20,000) | 개인 맥락 표지와 함께 나올 때 | `[금액]` |

개인 맥락 표지는 "내·제·저의, 보유, 매수·매입·매도, 샀·팔았, 평단·평균단가, 투자했·넣었, 손실·수익
(본인 기준), 계좌, 예수금, my, I have, I bought" 같은 표현이다. 퍼센트와 일반 투자 표현(PER 30배,
3분기, 20% 하락, 지수 수치)은 가리지 않는다. 정확한 규칙과 오탐 방지 목록은 설계 문서(#456)에 둔다.

### 5. 무엇을 가렸는지 사용자에게 알린다

게이트웨이는 가린 범주를 결과(`LLMCompletionResult.masked_categories`)로 돌려주고, 서비스는 이를
API 응답 `masked_categories`에 담는다. 값은 `MaskCategory` enum(`EMAIL`, `PHONE`, `RESIDENT_ID`, `CARD`, `ACCOUNT`, `QUANTITY`, `AMOUNT`, 영어 `UPPER_SNAKE`)이다. FE는 "보유 수량·금액을 가리고 전송했습니다"처럼 안내할 수 있다.
원문과 마스킹 결과의 대응표는 저장하지도 로그에 남기지도 않는다.

## Alternatives

- **자유 텍스트 필드 전송 금지.** 기각. 질문과 메모가 기능의 핵심 입력이라 기능 자체가 사라진다.
- **호출부마다 마스킹.** 기각. ADR-009가 기각한 "호출부를 신뢰" 방식과 같은 위험이 있다. 새 기능이
  마스킹을 잊으면 그대로 유출된다.
- **모든 금액·수량을 무조건 마스킹.** 기각. 공개 사실(계약 규모, 매출, 자사주 소각 수량)에 대한 질문의
  의미가 사라진다.
- **로컬 LLM으로 민감 정보 판별.** 보류. 사람 이름처럼 규칙으로 잡기 어려운 정보까지 다룰 수 있지만
  지연과 운영 부담이 크다. 하이브리드 LLM 아키텍처의 로컬 이관(ADR-008 Phase 2)과 함께 다시 검토한다.
- **마스킹 대신 사용자 경고만.** 기각. 경고는 이미 FE 안내 문구로 두기로 했고, 사용자가 놓치면 그대로
  나간다.

## Consequences

- 쉬워지는 것: 자유 텍스트를 받는 클라우드 기능이 늘어도 선언 한 줄로 같은 보호를 받는다. 무엇을
  가렸는지 사용자에게 투명하게 알릴 수 있다.
- 어려워지는 것과 위험
  - 규칙 기반이라 놓치는 정보(사람 이름, 특이한 표기의 금액)가 있다. 이 한계는 문서와 FE 안내로
    밝힌다.
  - 개인 맥락 판정이 틀리면 공개 사실을 가리거나 개인 금액을 놓칠 수 있다. 오탐·미탐 사례를 테스트로
    고정하고, 사례가 쌓이면 규칙을 고친다.
  - 새 `CloudSafePayload`에 사용자 작성 텍스트 필드를 추가할 때 `free_text_fields` 선언을 잊으면
    마스킹되지 않는다. 로컬 리뷰 체크 항목으로 둔다.
- DB 변경은 없다. 두 API 응답에 필드가 추가된다(추가만, 기존 계약 유지). 프라이버시 경계 변경이므로
  구현은 머지 전 사람 리뷰가 필요하다.

## Follow-up
